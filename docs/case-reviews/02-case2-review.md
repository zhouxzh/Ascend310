# 案例 2 审查报告：SSD 检测与多目标跟踪

## 审查范围与方法

本报告审查 `src/experiment/case2.md`、`samples/case2/README.md`、
`samples/case2/requirements.txt` 以及 `samples/case2/ssdlite` 和入口脚本。
结论来自静态文件、目录资产和文档—代码交叉核对；没有在开发机运行 CANN、
ATC、ACL 或板端摄像头测试。

## 总体结论

案例 2 对预处理、SSD 解码、NMS、Kalman/Hungarian 关联以及 CPU/NPU 后端的
教学主线基本清楚，且当前代码确实提供 MobileNet SSD 的 CPU 与 NPU 入口。
但教材宣称的模型矩阵超出仓库当前可见资产，README 有致命依赖路径拼写错误，
后端伪代码不能按真实接口执行，性能数字也缺少实验记录。修订前不宜把
ResNet 分支或 20→26 FPS 说成当前案例的已验证能力。

本报告将“高”对应为 `P1`，“中”对应为 `P2`；没有确认 `P0` 或 `P3` 级问题。

## 已确认问题

### 1. 高：模型矩阵与当前仓库资产不一致

**证据。** 教材 `src/experiment/case2.md:55-67` 声称已有 MobileNet v1–v4
和 ResNet18/34/50/101/151，并把 `ssd300_*` 归为 ResNet；但当前
`samples/case2/models/` 目录审查结果只有 `ssd320_mobilenet*` 的 ONNX/OM，
没有 ResNet 或 `ssd300` 文件。

**影响。** 学习者按章节选择 ResNet 会找不到模型，无法复现实验；“已覆盖”
与“脚本可能支持命名模式”被混为一谈，也无法判断某一精度是否通过转换和
推理验证。

**建议。** 只保留仓库中有下载、合同和验证证据的模型；若要保留 ResNet，需
提供版本化下载清单、输入输出合同和独立转换/推理报告，并把“脚本支持潜在
文件名”与“本案例已验证模型”分开。

### 2. 高：README 的依赖文件命令会直接失败

**证据。** `samples/case2/README.md:57-59` 的目录树写成
`requirementstxt`；`README.md:95-104` 又声明实际文件名是 `requirements.txt`，
但安装命令仍为 `pip install -r requirementstxt`。仓库实际文件为
`samples/case2/requirements.txt`。

**影响。** 按 README 操作会在依赖安装阶段失败，clean clone 无法开始案例。

**建议。** 统一为 `requirements.txt`，在 CI 或文档检查中执行一次命令解析；
同时说明 ONNXRuntime 只用于 CPU，ACL/CANN 由板端环境提供。

### 3. 高：后端选择伪代码不能代表真实接口

**证据。** `src/experiment/case2.md:354-368` 写成
`backend = CpuBackend(model_path) or NpuBackend(model_path)`，没有设备分支、
`device_id` 或资源释放；实际 `scripts/detection_app.py` 默认 CPU，
`scripts/tracking_app.py` 默认 NPU，二者通过后端工厂和不同模型后缀选择。

**影响。** 读者复制伪代码时无法实例化 NPU 后端，也会误解“或”运算为自动
探测/自动回退。教材的概念图与可执行接口不再是同一合同。

**建议。** 明确标注伪代码，给出与 `create_backend` 等真实函数一致的最小调用；
显式传入 `device`、`device_id`、模型格式和 `release`，禁止把异常吞掉后静默
回退到另一后端。

### 4. 高：性能改进数字没有可追溯证据

**证据。** `src/experiment/case2.md:1378` 和 `samples/case2/README.md:411`
声称一台 OrangePi/Ascend 310B 在 `MJPG 1280x720@60`、V4L2 `buffer=1` 下
由约 20 FPS 提升到约 26 FPS，但没有报告路径、日期、模型/精度、预热、采样
次数、统计方法或原始日志。

**影响。** 数字无法复核，也不能区分摄像头采集、解码、推理和显示的贡献；读者
可能将一次设备观察误读为普遍性能结论。

**建议。** 将数字移到带协议和原始日志的实验报告，或改为明确的经验性示例并
删除“实测”措辞。正式结果至少记录硬件计算档位、模型摘要、输入源、warmup、
循环次数和 percentile。

### 5. 中：算法叙述缺少规范引用

**证据。** 章节连续介绍 MobileNet v1–v4、SSD、DeepSORT、Kalman filter 和
Hungarian matching 的历史、设计取舍与能力，但没有为这些主张提供原始论文、
版本或数据集引用。

**影响。** 教材难以区分论文中的方法、当前代码的简化实现和作者的工程判断，
也无法让读者追溯模型或跟踪器的来源。

**建议。** 为每个算法补原始论文/官方实现及版本；明确本项目是“DeepSORT 风格”
的简化关联器还是完整 DeepSORT，并把理论能力与当前代码已实现的分支分开。

### 6. 中：NPU 边界和输入尺寸合同不够明确

**证据。** 章节包含下载、ATC 和 NPU 运行命令（如 `case2.md:30-53`），但没有
在每个实验入口明确“仅板端执行”。实现 `samples/case2/ssdlite/backend_base.py:16-25`
还根据模型文件名推断 `300` 或 `320` 输入；模型被重命名时可能选择错误的预处理
和解码路径。

**影响。** 开发机用户可能尝试运行不可用的 ACL/ATC；文件名漂移会造成张量尺寸、
先验框和后处理不匹配，错误不一定在启动阶段显现。

**建议。** 在教程和 README 增加板端边界及 CPU 等价命令；把输入尺寸、先验数量、
输出顺序写进模型 manifest，并在加载时读取/校验元数据，而不是把文件名当作合同。

### 7. 中：clean clone 的模型可复现性没有闭环

**证据。** 当前 ONNX/OM 资产位于本地 `models/`，并按仓库忽略规则排除；章节
使用“当前仓库模型”的措辞，却没有固定 release、摘要、转换参数和验证报告的
链接。

**影响。** 新 checkout 只能看到代码，无法确定下载到的是哪一模型、哪一精度，
也无法区分“存在文件”和“通过 ONNX/ACL 验证”。

**建议。** 用版本化 manifest 描述模型来源、输入输出、SoC、精度和摘要；将大型
资产留在外部发布位置，但把下载/校验/转换证据纳入文档。板端生成的 OM 和运行
报告继续保持在明确的证据目录，不要误提交二进制。

## 验证要求与未验证边界

1. 尚未联网验证下载脚本的远程 release 是否另有 ResNet/ssd300 资产；即使存在，
   当前仓库目录与章节“已覆盖”仍不一致，需要版本化证明。
2. 尚未在 Ascend 板端执行 ATC、ACL smoke、摄像头采集或跟踪性能测试，因此不
   对任意 FPS、延迟或模型精度作结论。
3. 修订后应运行文档链接检查、CPU 单测和显式板端测试，并记录模型/输入合同。

## 安全与数据边界

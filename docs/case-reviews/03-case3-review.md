# 案例 3 审查报告：Ascend 310B DDSP 智能电子琴

## 审查范围与方法

本报告交叉阅读 `src/experiment/case3.md`、`samples/case3/README.md`、
`samples/case3/doc/` 中的接口与部署说明，并检查章节引用的图像路径和主要
模型/运行时描述。审查仅判断文档与现有源文件的静态一致性；没有在开发机运行
CANN、ATC、PyACL 或音频硬件测试。

## 总体结论

本轮没有发现阻断级或高置信度的 Case 3 文档—实现矛盾。章节已经把三条工作流
的时间模型分开，明确区分作者训练的 Piano-DDSP 与从上游 TFLite 迁移的
MIDI-DDSP/DDSP-VST，也主动限定了摄像头仅作麦克风载体、蓝牙延迟不归因于 NPU、
界面截图不等于性能结果。这些表述与 `samples/case3` 的结构和证据边界总体
一致，适合作为理论教程的主叙事。

严重性约定：本轮没有确认 `P0`/`P1` 阻断问题；下列待核对项属于尚未完成的
证据核验，不等同于缺陷通过或板端验收结果。

## 已核实的良好边界

### 1. 三条工作流与模型来源已分开

`src/experiment/case3.md:17-23` 将实时演奏、MIDI 文件渲染和 DDSP-VST 单音
转换分别列出；`case3.md:174-196,237-252,617-619` 又分别说明 Piano-DDSP
的自训练/ONNX 路径与另外两类模型的上游迁移路径。该分层避免把不同时间尺度、
状态合同和训练来源混写成一个“通用模型”。

### 2. 音频设备与延迟归因表述较为严谨

`src/experiment/case3.md:49-52` 明确支持蓝牙音箱和蓝牙耳机，同时指出编码、
无线传输和播放缓冲会增加实时演奏延迟，并要求优先用有线输出评价模型链路。
这一区分避免把无线设备延迟错误归因于 NPU。

### 3. 截图和性能证据边界清楚

章节在 `case3.md:405` 声明界面截图只说明结构和状态，不是性能证据；
`case3.md:662-677` 将 20 ms/150 ms 写成验收阈值而非已取得的结果，并要求
双工长稳报告才能形成性能结论。这符合“接口连通性、单模型冒烟、页面截图不能
替代实时性能实验”的证据原则。

### 4. 部署与网络边界已有明确提醒

`src/experiment/case3.md:374,617-619,631,650` 要求资源由服务端解析、转换和
PyACL 在真实 Ascend 板端完成、部署先暂存后原子切换，并限制在可信网络中；这些
边界与 `samples/case3` 的部署文档方向一致。

## 安全与数据边界

本次未发现章节把真实音频、MIDI 文件或设备凭据写入仓库的高置信度问题；但 API
鉴权、音频设备访问、日志留存和板端网络隔离仍需按当前样例配置逐项核对。截图、
录音和长稳报告不得包含个人音频、密钥或未脱敏设备标识。

## 验证要求与未验证项（不构成已确认问题）

1. 对照 `samples/case3` 当前发布的 `bundle.json`、模型 manifest 和运行时合同，
   逐项核对章节所列 reverb IR 形状、Feature/Control 输入输出、循环状态和
   音频采样率；静态阅读尚不足以替代结构化元数据检查。
2. 逐项检查章节中所有 REST/WebSocket 路径是否与当前 API 文档及前端调用一致，
   尤其是设备枚举、音频会话和 MIDI 文件子资源；若接口已变更，应只改章节源文档。
3. 在真实板端完成章节规定的长稳双工测试后，才能把性能表或报告数值回填到教材；
   本审查没有运行该测试，也没有确认蓝牙、有线输出或独立单音源的实测延迟。
4. 继续保持图像验收：检查最终 PNG 在 PDF 缩小尺寸下的中文、箭头、裁切和灰度
   可辨性；当前未将截图视觉质量当作代码/模型验证结论。

## 结论

Case 3 当前没有需要立即阻断出版的静态问题。后续工作重点是完成上述资产合同、
API 路径和板端长稳证据的逐项核对；在核对完成前，不应把“文档结构一致”表述为
“模型性能已验证”。

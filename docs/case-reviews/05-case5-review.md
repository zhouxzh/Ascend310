# 案例 5 审查报告：智能数据采集仪

## 审查范围与方法

本报告审查以下内容：

- 教材章节：<code>src/experiment/case5.md</code>；
- 运行样例：<code>samples/case5/README.md</code>、<code>time_frequency_dashboard/</code>、<code>tests/</code>；
- 工程证据：<code>samples/case5/docs/</code>、模型 manifest 和板端连续运行记录的引用。

本次只进行了源码和文档静态审查，没有在本机运行 CANN、ATC、ACL、OM、示波器或 RTL-SDR，也没有重新取得板端 CU8、JSONL 和 QC 报告。Case 5 的目录说明明确要求硬件行为在 Ascend 310B 上验证；本报告不把历史板端记录当作本次新测量。

## 总体结论

案例 5 对采集、CPU 预处理、NPU 推理和证据边界的划分相对严谨，章节也明确承认当前 checkpoint 使用单类训练语义。但运行代码仍按 51 个部署标签执行 argmax 和 class-aware NMS，因而不能把当前检测输出解释为 51 类调制识别。600 秒数字具有报告摘要和哈希，却不随 clean clone 提供原始输入，出版版需要明确其“外部板端证据”属性。

严重性定义：

- P1：会改变模型结果的科学含义或使关键结果无法独立复核，发布前应处理；
- P2：会造成指标、设备条件或复现路径的误解，建议在出版前处理。

## 已核实问题

### 3.1 P1：检测后处理没有遵循当前模型的单类训练合同

**证据**

- <code>samples/case5/time_frequency_dashboard/model/candidate_catalog.py:26-35</code> 提供了 51 个调制类别名称。
- <code>samples/case5/time_frequency_dashboard/inference_processing.py:119-127</code> 将函数描述为“class-aware CPU NMS”。
- 同一文件 <code>:147-163</code> 要求输出恰好为 4 加类别数的列，逐行对 51 个评分取 argmax；<code>:182-206</code> 再按 class index 分组执行 IoU NMS，并把索引映射为标签。
- <code>src/experiment/case5.md:305</code>、<code>:313-315</code> 明确当前 checkpoint 使用 <code>single_cls=True</code>，通道索引只是张量布局兼容信息；<code>:614</code>、<code>:670</code>、<code>:728</code> 又明确说不能把标签、框数或 bpsk 映射解释为类别或真实事件数量。

**影响**

当前代码在接口层产生带有 51 类名称的结果，即使正文提醒读者不要解释这些标签，读者仍可能把 UI、JSONL 或统计表中的 class_index、label 和框数当成模型语义。单类训练下按多个通道分组的 NMS 也不等价于正式的单类后处理，可能改变重叠候选的保留结果。这样得到的输出只能证明张量布局和流水线连通，不能作为调制分类、检测召回或误报率结果。

**修复建议**

1. 若保留当前 checkpoint，将 manifest 和输出合同改为单一候选得分，采用 class-agnostic NMS；结果字段改为候选区域/置信度，不再映射 51 个调制标签。
2. 若确实需要 51 类识别，必须重新取得具有 51 类监督语义的训练权重、类别顺序、验证集和独立精度报告，再同步 ONNX、OM、manifest、后处理和界面。
3. 在模型输入输出合同中把“张量通道索引”和“语义类别”分成不同字段，禁止通过手工修改 status 将当前候选标成多类 accepted。

**验证要求**

- 用两个重叠框、不同评分通道的确定性张量测试单类 class-agnostic NMS，验证保留结果与输出字段；
- 对真实 accepted manifest 检查输出 shape、dtype、分数范围和标签表是否一致；
- 在板端重复一次短运行，确认 JSONL、UI 和报告都不再暗示未经训练支持的类别；
- 若换多类模型，报告数据集、类别顺序、样本数、混淆矩阵/PR 指标和模型工件哈希。

### 3.2 P1：600 秒长稳数字是外部板端证据，clean clone 无法独立重算

**证据**

- <code>src/experiment/case5.md:714-728</code> 给出 600.145 s、1,170/1,170 批次、零丢批和多项 P50/P95/max 数字，并引用配套资料 07。
- <code>samples/case5/docs/07_ascend310b_heterogeneous_signal_processing.md:239-263</code> 给出固定增益、中心频率、天线状态、报告/CU8/manifest SHA256 和详细结果；<code>:253-254</code> 特别说明其中的 pytest/compileall 是历史工作树结果，不是当前工作树结果。
- <code>samples/case5/data/</code> 下的 CU8、JSONL、QC 和运行报告被仓库规则忽略（<code>.gitignore:289</code>），<code>git ls-files samples/case5</code> 不包含这些原始证据。

**影响**

文档中的摘要和 SHA256 可以证明某次板端记录之间的绑定关系，但读者在干净源码副本中无法取得原始 CU8/JSONL 并重新运行只读 QC，也无法确认当前代码、当前 OM 和历史报告完全一致。若表格没有标出这一点，读者会把一次外部设备记录误认为可在本地复现的仓库结果。

**修复建议**

1. 在正文和表题中标注“外部 Ascend 310B 板端记录”，同时保留设备档位、CANN 版本、模型/manifest 版本、输入条件、报告哈希和原始报告的受控获取位置。
2. 为教学复现提供小型脱敏 fixture（例如 JSONL schema 和固定合成 CU8），只用于验证解析器和统计定义，不冒充真实射频结果。
3. 将“当前工作树测试”与“历史板端测试”分开列出；若源代码或 manifest 改变，不能自动沿用旧数字。

**验证要求**

- 在 clean clone 上运行纯解析/统计测试，确认 fixture 能复现字段定义和边界检查；
- 在同一块 Ascend 310B 上重新执行至少 600 秒记录，生成新的 JSONL、QC、CU8 和 sibling manifest；
- 用 <code>--verify-attached</code> 或等价工具从原始文件重新检查字节数、哈希、模型合同和后端字段；
- 章节只回填新报告中的数值，不用旧报告覆盖失败或缺失的本轮结果。

### 3.3 P2：时延指标的起止边界需要在表格层面固定

**证据**

- <code>src/experiment/case5.md:606</code> 把一次 20 批短运行的只读 QC 称为端到端 P95 902.59 ms。
- <code>src/experiment/case5.md:647-670</code> 又以单窗口 512 ms 和 <code>post_capture_pipeline_max_ms</code> 作为连续性检查点。
- <code>src/experiment/case5.md:716-728</code> 说明表中时延从主机取得完整 IQ 批次后开始，并另列主机至主机 NPU 边界、FFTW 和后采集流水线。
- 配套资料 <code>07_ascend310b_heterogeneous_signal_processing.md:260-270</code> 还列出包含采集缓冲的 <code>end_to_end_ms</code>，并明确它不是 RF/ADC 首样本到结果的设备侧时延。

**影响**

这些数字并非必然互相矛盾，但“端到端”“后采集”“NPU 调用边界”和“窗口预算”在同一章出现时，读者可能比较不同计时器并得出错误的实时结论。尤其是 902.59 ms 与 512 ms 的关系若不看脚注，容易被理解为一次验收失败或把主机缓冲延迟误当作模型延迟。

**修复建议**

在每张表的列名中写明起点、终点、是否包含采集/写盘/排队，并统一使用“host-to-host NPU boundary”“post-capture pipeline”等不含歧义的名称。单独列出“RF 首样本到 UI 的总延迟：未测量”，不要用任何现有数字代替。

**验证要求**

- 用同一份 JSONL 逐字段复核计时区间和单位；
- 对短运行、长稳运行和历史记录分别标注版本、输入条件和统计样本数；
- 让只读汇总器拒绝缺少 timer 起止元数据的报告，避免把不同定义混入同一张表。

### 3.4 P2：屏幕尺寸应作为一次实验条件，而非系统适用性声明

**证据**

- <code>src/experiment/case5.md:606</code> 将 HDMI <code>1920x1080</code> 写入一次真实短运行条件。
- <code>src/experiment/case5.md:608-614</code> 将该尺寸用于截图标题和触摸屏可读性说明。
- 长稳表格 <code>:714-728</code> 的性能结果并不依赖显示器像素，但屏幕条件与数据采集、NPU 时延连续出现。

**影响**

一次设备截图的分辨率可以作为可追溯的 UI 观测条件，却不应被读者理解为模型或程序只能在该分辨率下运行。固定尺寸还会掩盖浏览器内容视口、缩放比例和触摸布局的独立影响。

**修复建议**

把表述改为“本次板端观测使用的 HDMI 输出条件”，并将 UI 可读性验收与采集/NPU 性能表分开。正文说明布局应由相对尺寸和内容约束决定，具体截图尺寸放在图注或证据记录中。

**验证要求**

在至少一个不同桌面窗口和一个窄视口中检查图表、结果表和错误提示，不把显示尺寸变化误判为 NPU 性能变化。

## 现有正面控制

- README 和案例文档明确 CPU 只负责 CU8 解码、预处理和确定性后处理，卷积检测必须来自 OM；
- manifest admission 同时检查来源、工件哈希、输入合同、数值比较、P95 预算和实时演示标记；
- 章节明确区分模型准入与整条连续流水线验收；
- 文档主动声明没有地面真值时不报告调制识别准确率，且把 Health=Alarm 作为诊断信息而非单独阻断条件；
- 运行工具保留 CU8、JSONL 和 sibling manifest 的绑定关系，并拒绝用另一份捕获文件覆盖既有报告。

这些控制降低了误报风险，但不能替代语义一致的后处理和当前工作树的重新板测。

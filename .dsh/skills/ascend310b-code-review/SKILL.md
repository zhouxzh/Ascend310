# Ascend 310B 代码审查

本 skill 参考 CANNBot `ascendc-code-review` 的规则组织方式，但平台范围、8T/20T 边界和证据要求已按本仓库重写；不替代 CANNBot 原技能。

## 审查顺序

按影响面从高到低：

1. 平台边界：是否确认 310B1/310B4，是否错误引用 910/950 参数。
2. 合同：输入输出 shape、dtype、layout、预处理和后处理。
3. 设备：上下文、stream、内存分配、同步和释放。
4. 模型：ATC 参数、OM/MindIR 版本、加载和错误处理。
5. 视频：V4L2/DVPP/VENC 格式、buffer、帧率和设备释放。
6. 服务：启动环境、真实推理、超时、取消和资源回收。
7. 证据：版本、命令、日志、哈希、8T/20T 标记和失败边界。

## 必须拒绝的写法

- 把板卡 IP、用户主目录或 checkout 路径写进源码。
- 在默认流程中静默 CPU/云端 fallback。
- 将 8T 与 20T 的性能或精度结果合并。
- 用 `Health: Alarm` 单独阻塞所有任务。
- 用未验证的固件版本作为默认前提。
- 用 `/dev/video0` 固定代表某块板的摄像头。
- 捕获异常后只打印“失败”，不记录返回码、命令、输入和版本。
- 在没有真实板端证据时写 `observed-pass`。

```text
合同问题:
资源/同步问题:
平台适配问题:
缺失的证据:
已运行的测试:
```

## 测试要求

- 纯代码检查可在本机执行。
- Ascend C/ACL/ATC/OM/DVPP/摄像头和 NPU 推理必须在目标板执行。
- 本机缺 `acl`、`cv2` 或 CANN 不是代码失败，必须明确标注为未在本机验证。
- 不能把一次转换通过当作数值、精度或性能通过。

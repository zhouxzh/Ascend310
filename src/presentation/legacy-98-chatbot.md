# 案例 9：智能聊天机器人

把大语言模型装进一块边缘开发板，让它在局域网内回答中文问题

对应教材：`src/experiment/case9.md`

对应代码：`samples/case9`

---

## 为什么要把聊天机器人放到边缘

云端大模型已经很强，但有些场景它进不来：

| 约束 | 后果 |
|---|---|
| 数据不出域 | 对话内容不能离开内网，云端 API 不可用 |
| 网络不可靠 | 断网、弱网环境下仍要能回答 |
| 成本与延迟 | 每次对话都走公网，长尾请求成本高、首字延迟大 |

边缘聊天机器人的目标不是"追上云端效果"，而是**在受限硬件上把一条完整对话链路跑通**。

---

## 本讲的学习目标

1. 说清一个边缘聊天服务由哪几个进程组成，各自的职责边界在哪里
2. 理解为什么模型、网关、界面要拆成三层，而不是写在一个脚本里
3. 会用 OpenAI 兼容接口调用板端服务，并看懂流式输出的意义
4. 能定位"页面能打开但回答出不来"这类问题发生在哪一层

---

## 一条请求要经过四个角色

| 角色 | 监听 | 职责 |
|---|---|---|
| 浏览器 | — | 展示对话界面，只与文字页面通信 |
| 文字界面 | `0.0.0.0:7865` | 可信局域网入口；**密钥保存在服务器端**，不下发浏览器 |
| OpenAI 兼容网关 | `127.0.0.1:7861` | 校验请求与鉴权，把固定的内部模型名转发给 worker |
| MindSpore worker | `127.0.0.1:8090` | 在 NPU 上串行执行生成，不向网络暴露 |

浏览器**不直接访问模型，也不知道网关密钥**——这是整套设计的起点。

---

## 为什么这样分层

分层的收益有两条，缺一条都不成立：

**信任边界**
- 越靠近模型的组件，暴露面越小：worker 只监听回环，网关只接受带密钥的请求
- 网页没有登录功能，所以它只能待在可信局域网里

**算力边界**
- 边缘只有一块 NPU，多个请求并发会互相争抢显存与算力
- worker 串行执行，把"排队"这件事收敛在一个组件里，而不是让每个调用方自己处理

---

## 三个端口，三种暴露面

| 端口 | 绑定 | 谁可以访问 | 红线 |
|---|---|---|---|
| `7865` | `0.0.0.0` | 同一可信网段的任何主机 | 不做端口映射，不放在公网反向代理后面 |
| `7861` | `127.0.0.1` | 仅本机进程 | 必须带 Bearer 密钥 |
| `8090` | `127.0.0.1` | 仅本机进程 | 永不暴露 |

网页没有登录功能——**能访问 7865 的人就能让这块板子回答任何问题**，这句话决定了它的部署边界。

---

## 模型与工件：先锁版本，再谈效果

模型来自 Qwen1.5-0.5B-Chat，但程序**不会根据模型名自动下载任何版本**。

它读取 `samples/case9/configs/release-model.json` 中锁定的 revision、文件名、大小与 SHA-256：

| 工件 | 用途 |
|---|---|
| `model.safetensors` | 模型权重 |
| `tokenizer.json`、`vocab.json`、`merges.txt` | 分词数据与词表 |
| `config.json`、`tokenizer_config.json` | 结构与分词配置 |
| `generation_config.json` | 生成参数默认值 |

锁版本的目的是**可复现**：同一份清单，任何人装出来的服务都该是同一个。

## 环境前提：不装、不升级、不降级

| 层 | 前提 |
|---|---|
| 硬件 | Ascend 310B 系列板卡 |
| 驱动与 CANN | 板端已按厂商配套安装 |
| 框架 | MindSpore、MindNLP 已在同一 conda 环境中可用 |
| Python | 与上述框架匹配的版本 |

本案例**只使用**已就绪的环境：

- 不安装、不升级驱动、CANN 与框架
- 缺依赖时**明确失败**并给出提示，而不是偷偷换一条能跑的路径

本仓库的实测口径是 Ascend 310B4 / 8T；20T（310B1）不继承本案例结论。

---

## 启动顺序：worker → gateway → UI

三个进程，三个终端，顺序不能颠倒——后面的依赖前面的：

```bash
# 终端一：NPU 推理 worker
bash scripts/run/start-worker.sh

# 终端二：OpenAI 兼容网关
bash scripts/run/start-gateway.sh

# 终端三：文字页面
bash scripts/run/start-ui.sh
```

以上脚本位于 `samples/case9/scripts/run/`；自动化脚本也可以用 `ascend-edge-chat` 命令行，它提供 `worker`、`gateway`、`ui` 等工作模式。

---

## OpenAI 兼容接口

服务对外只暴露两个端点，用法与云端一致：

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/v1/models` | 列出可用模型名 |
| `POST` | `/v1/chat/completions` | 提交对话，返回 JSON 或 SSE 流 |

```bash
curl -s http://127.0.0.1:7861/v1/chat/completions \
  -H "Authorization: Bearer $ASCEND_EDGE_CHAT_GATEWAY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"ascend-edge-chat","messages":[{"role":"user","content":"你好"}],"stream":true}'
```

兼容 OpenAI 格式的价值：现有客户端与库可以**不改代码**接进来。

## 一次请求的完整链路

| 步骤 | 发生什么 |
|---|---|
| 1 | 浏览器把消息提交给文字页面 |
| 2 | 页面在服务器端补上 Bearer 密钥，转给回环网关 |
| 3 | 网关校验鉴权与请求格式，把固定的内部模型名转给 worker |
| 4 | worker 在 NPU 上执行生成，逐个 token 产出 |
| 5 | 结果沿原路返回；`stream: true` 时以 SSE 逐段推给浏览器 |

链路上任何一环失败，错误都**在出错的那一层**报出来，而不是笼统地说"服务不可用"。

---

## 流式输出为什么重要

一段 200 字的回答，全部生成完再返回和边生成边返回，用户体验完全不同：

| 方式 | 首字延迟 | 总耗时 |
|---|---|---|
| 一次性返回 | 等于总生成时间 | 相同 |
| SSE 流式 | 第一个 token 生成完即可显示 | 相同 |

流式不减少总耗时，但把**等待的空白**填上了——这是边缘小模型最值得做的一处优化。

代价：调用方要能处理分块响应，并且在中断时正确关闭连接。

---

## 单 worker 串行：边缘算力的现实

为什么不让 worker 并发处理多个请求？

- 一块边缘 NPU 的显存与算力是固定的，并发只会让每个请求都变慢
- 串行让"排队"行为可预测：先到先服务，不会出现两个请求互相拖垮
- 需要更高吞吐时，正确做法是**换硬件或换模型**，不是在这里加并发

这是边缘部署与云端部署最本质的差别之一：**资源是硬的，不是弹性的**。

---

## 失败关闭：拒绝服务，而不是降级

以下情况，服务应当直接拒绝，而不是找一条"还能跑"的路：

| 情况 | 正确反应 |
|---|---|
| 未配置网关密钥 | 网关启动失败并指名缺哪个变量 |
| 模型工件缺失或校验不符 | 拒绝启动，提示哪个文件不对 |
| conda 环境或 CANN 未激活 | 明确报错，**不退回 CPU 推理** |
| worker 未就绪 | 网关报上游不可达，而不是返回空回答 |

理由很直接：一个"看起来能用"的错误回答，比一个明确的失败更难排查。

## 排障顺序：从前到后，一次只查一层

| 现象 | 先查 | 再查 |
|---|---|---|
| 页面打不开 | 文字页面进程与 `7865` | 板卡网络与防火墙 |
| 页面能开但回答出不来 | worker 是否在 `8090` | 网关是否在 `7861` 且带密钥 |
| 网关启动即退出 | 密钥与上游地址配置 | `gateway --check-config` 的输出 |
| worker 报导入错误 | conda 环境是否激活 | 同一 shell 是否 source 了 CANN |

原则：**只改一层，只验一层**；一次动三个进程，出了问题就无法归因。

---

## 课堂任务

1. **跑通链路**：按 worker → gateway → UI 的顺序启动三个进程，在浏览器里完成一次中文对话
2. **绕过界面**：用 `curl` 直接调用 `/v1/chat/completions`，分别试 `stream: true` 与 `false`，比较两者返回的差别
3. **改一个变量**：把 worker 的 system prompt 换成自定义内容，观察同一条用户消息的回答如何变化

完成第 2 项时请留意：直接调网关需要密钥，而**浏览器拿不到这个密钥**——这正是分层设计想要的结果。

---

## 小结

1. **四个角色、三条边界**：浏览器 / 文字页面 / 网关 / worker，每一层只信任下一层
2. **先锁版本再谈效果**：模型 revision 与工件校验是复现的前提
3. **资源是硬的**：单 worker 串行不是妥协，而是对边缘算力的正确描述
4. **失败要明确**：拒绝服务优于"看起来能用"的错误回答

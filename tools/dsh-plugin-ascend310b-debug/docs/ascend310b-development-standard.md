# 昇腾310B程序开发、工程目录与文档规范

| 项目 | 内容 |
| --- | --- |
| 规范编号 | `ASCEND310B-ENG-001` |
| 版本 | 1.0 |
| 状态 | 本仓库执行 |
| 发布日期 | 2026-10-17 |
| 适用范围 | 昇腾 310B1（20T）与 310B4（8T） |
| 配套插件 | `dsh-plugin-ascend310b-debug` |

本文规定昇腾 310B 程序的设计、编码、工程目录、文档和验收要求，目标是让代码能够在目标板上重复构建、重复运行、分层定位失败，并让后来者只读文档和证据就能判断结论是否可信。

本文是项目工程规范，不替代华为昇腾官方文档、CANN 发布说明或具体芯片的接口手册。厂商文档与本文冲突时，先核对目标板实测版本和官方文档，再修订本文，不能反过来用本文覆盖板端事实。

规范性用语的含义：

- **必须**：不满足即不能进入验收或交付。
- **应当**：默认执行；偏离时必须在评审记录中写明原因。
- **可以**：按项目需要选择。
- **禁止**：不得以临时开关、隐藏回退或手工改生成物的方式绕过。

## 1. 基本原则

1. **目标板是最终事实源。** SoC、CANN、驱动、Python、框架和设备状态的结论必须来自目标板探测；本地编译通过不等于板端运行通过。当前 310B 的非特权探测不采集固件版本；没有可信来源时不要把驱动号当作固件号。
2. **失败必须留在发生它的层。** 设备、CANN、转换、加载、输入输出合同、数值、任务指标、性能和服务的证据不能互相替代。
3. **默认 fail closed。** 缺少 NPU、CANN、模型、合同或必要权限时拒绝运行，禁止静默回退到 CPU、云端或另一个未验收模型。
4. **先最小烟测，再做完整任务。** 依次验证导入、设备、Context、模型加载、一次推理、合同、数值、任务指标和性能。
5. **运行资产与源码分离。** 模型、OM、数据集、运行日志、未脱敏截图、临时报告和板端状态不进普通 Git 提交；为文档明确设计的小型匿名截图或测试夹具除外。
6. **文档必须可执行。** 每条部署命令必须写明执行位置、前置环境、预期结果和失败停止条件。
7. **证据必须可追溯。** 结论必须绑定 SoC 档位、软件版本、模型摘要、输入合同、命令、日期和原始报告位置。
8. **8T 与 20T 分开留证。** 两块板的结果是两个证据集，不得合并、互相替代或跨档位复用性能数字。
9. **发布测试从公开来源重建。** 案例程序从 GitHub 的完整 commit 获取，模型从 Hugging Face 的固定 revision 下载；`scp`/`rsync` 本地源码或模型只能作为明确标注的开发/离线例外，不能充当公开复现证据。完整流程见 `ascend310b-case-testing`。

## 2. 开发基线

### 2.1 适用芯片

| SoC | 计算档位 | 本规范行为 |
| --- | --- | --- |
| `Ascend310B1` | 20T | 建立独立证据集 |
| `Ascend310B4` | 8T | 建立独立证据集 |
| 其他 Ascend SoC | 不适用 | 使用对应芯片自己的工具链和规范 |
| 未识别 SoC | 未知 | 先补探测，不推断兼容性 |

芯片档位按 `SoC + 计算档位` 标识，不按主板商品名、主机名或 IP 标识。

### 2.2 版本记录

每个可交付程序必须能够报告并归档以下信息：

- `npu-smi` 版本、驱动版本；固件版本只在目标板提供可信、可读来源时记录，不能用驱动号代替；
- CANN Toolkit、NNAL/ops 等实际安装组件版本；
- Python 解释器路径、PyACL/Python 包来源；
- MindSpore、MindSpore Lite、torch_npu 等框架版本（使用到时）；
- ATC 参数、ONNX/OM 摘要和模型合同；
- 服务启动命令、环境变量名称和监听地址；
- 目标 SoC、计算档位、板卡标识、系统日期。

禁止只写 `latest`、`默认版本`、`最新环境` 作为版本结论。`latest` 可以出现在安装路径中，但验收记录必须解析出实际版本。

### 2.3 环境分层

控制机、普通容器、板端 conda 环境和板端 CANN shell 是四个不同环境。文档和测试必须写清命令在哪里执行：

- 控制机可以做语法、纯 Python、前端、静态 ONNX 和文档检查；
- 控制机不得被描述成可以执行 CANN、ATC、ACL、OM、DVPP、V4L2 或 `npu-smi`；
- 板端运行必须使用实际启动服务的同一个 shell、同一个解释器和同一套 CANN 环境；
- 虚拟环境、`PYTHONPATH`、`PYTHONNOUSERSITE` 和服务启动器必须一起记录。

## 3. 代码仓库工程目录规范

### 3.1 本仓库目录职责

本仓库的目录唯一真源是 `docs/governance/repository-structure.md`。本节给出开发时的执行摘要；如果路径规则发生冲突，以该文件为准并同步修订本节。

| 路径 | 职责 | 禁止放入 |
| --- | --- | --- |
| `README.md` | 项目定位和最短起步 | 长篇原理、历史报告、完整模型矩阵 |
| `docs/` | 仓库级结构、治理和跨案例审查 | 教材正文、运行资产 |
| `src/book/` | 理论书稿源文件 | 可执行案例的完整实现 |
| `src/experiment/` | 案例教程正文 | 运行时日志和模型二进制 |
| `src/appendix/` | 附录正文 | 临时排障记录 |
| `src/.vuepress/` | 站点配置和公开静态资源 | 大模型、数据集、私人截图 |
| `samples/` | 与章节和案例配套的可运行代码 | 教材章节正文 |
| `scripts/` | 仓库级构建、发布和文档工具 | 单个案例的私有业务代码 |
| `latex/` | 生成的 LaTeX/PDF | 手工修改的源文件 |
| `tools/` | 可独立安装的仓库工具和 DSH 插件 | 板端私有配置和凭据 |
| `notebook/` | 辅助学习材料 | 生产服务入口 |

### 3.2 案例目录契约

新增案例必须使用稳定的 `samples/caseN/` 路径，并按以下角色组织：

```text
samples/caseN/
├── README.md                 # 最短运行、部署、验证和故障入口
├── app.py 或语义包/          # 正式运行入口和业务代码
├── configs/                  # 可审计的配置模板
├── scripts/                  # 准备、部署、诊断、验收脚本
├── tests/                    # 单元、合同、集成测试
├── docs/                     # 编号工程文档和证据记录
├── frontend/ 或 web/         # 前端源码；没有前端时不创建
├── models/                   # 模型元数据；二进制默认忽略
├── data/                     # 数据和运行状态；默认忽略
├── reports/                  # 测试和性能报告；默认忽略
└── third_party/              # 必要的第三方代码和许可证
```

规则：

1. `caseN` 是机器稳定 ID，语义名称由索引和 README 提供；不得为了改显示名称重命名稳定目录。
2. `README.md` 负责最短可运行路径，不复制编号文档的长篇内容。
3. 正式入口必须稳定。`app.py` 或语义包入口确定后，不得在不同启动脚本中指向不同实现。
4. 运行代码、测试、配置、脚本和文档必须分目录；禁止把模型文件、日志、截图和源码混在同一目录。
5. `models/`、`data/`、`reports/` 默认由 `.gitignore` 排除；只有明确设计的小型测试夹具可以提交。
6. 旧目录为兼容可以保留，但新增文件必须进入本规范定义的目录，并在 README 说明历史目录的边界。

### 3.3 章节示例目录

章节级示例使用 `samples/chapterN/`，至少包含：

- `README.md`：说明学习目标、前置环境、运行入口、预期输出和失败停止条件；
- 可运行脚本或语义清晰的源码；
- 必要的输入样例或配置模板；
- 需要板端运行的命令必须标注板端环境。

章节代码服务于教学，不得被案例服务直接当作生产模块导入。需要共享时，应提取到明确的公共包并补测试，而不是跨章节使用相对路径引用。

### 3.4 独立 310B 项目的最小目录

不在本教材仓库内创建的新项目，应当采用以下最小结构；目录名可以按语言调整，但职责不得合并：

```text
project/
├── README.md
├── pyproject.toml 或 CMakeLists.txt
├── src/<package>/
│   ├── runtime/              # 设备、Context、Stream、ACL 封装
│   ├── model/                # ATC/OM 合同和加载
│   ├── service/              # 对外 API 或 CLI
│   └── config/               # 配置解析和校验
├── configs/                  # 示例配置，不含秘密
├── scripts/                  # 构建、部署、诊断、验收
├── tests/                    # 默认无板可跑的测试
├── docs/                     # 编号工程文档
├── artifacts/                # OM、模型和构建产物；默认忽略
├── reports/                  # 运行和性能证据；默认忽略
└── .github/                  # CI 和仓库自动化
```

### 3.5 命名和资产边界

- Python 模块使用小写 `snake_case`；类使用 `PascalCase`；常量使用 `UPPER_SNAKE_CASE`。
- Shell 脚本使用动词开头的 `kebab-case` 或既有仓库风格，例如 `run_*`、`check_*`、`provision_*`。
- 文档使用两位数字前缀加 ASCII slug，例如 `04-om-contract.md`。
- 环境变量统一使用项目前缀，例如 `CASE9_*` 或 `APP_*`，不得使用含义不明的 `ROOT`、`MODEL`。
- 设备号、IP、SSH 用户、仓库绝对路径、token 和密码不得硬编码在源码、文档示例或测试快照中。
- 模型权重、ONNX、OM、数据集、检查点、运行日志、未脱敏截图、临时报告和数据库文件禁止进入普通 Git；提交前用 `git diff --cached --name-only` 复核。文档所需的匿名截图必须是小尺寸、可追溯、无个人数据并已在正文引用的明确夹具。
- 构建产物必须由源文件生成。禁止手工修改 `latex/`、`dist/`、生成的 LaTeX 或其它带生成标记的目录。

## 4. 程序开发规范

### 4.1 通用结构

程序必须把以下职责分开：

1. 配置读取和校验；
2. 设备与环境初始化；
3. 模型/OM 合同加载；
4. 输入预处理；
5. 推理执行；
6. 后处理和结果校验；
7. 资源释放；
8. 健康检查、日志和错误返回。

禁止把设备初始化、模型加载、推理和 HTTP 路由写成一个无法单独测试的函数。每个阶段必须有明确的输入、输出、失败状态和停止条件。

### 4.2 初始化顺序

推荐并默认采用以下逻辑顺序，具体 API 名称以目标 CANN 版本为准：

```text
读取配置
  -> 校验 SoC/档位与模型合同
  -> 检查设备可见性
  -> 创建 Context
  -> 创建 Stream
  -> 加载 OM
  -> 创建输入输出描述
  -> 分配设备/主机内存
  -> 执行一次最小推理
  -> 进入服务或批处理循环
  -> 同步
  -> 释放缓冲区、描述、模型、Stream、Context
```

每一步必须检查返回值。初始化失败必须停止后续步骤，并释放已经创建的资源；禁止在设备或模型状态未知时继续执行推理。

### 4.3 ACL 资源生命周期

以下对象必须有明确的创建者和释放者：

- Device 与 Context；
- Stream；
- Model/ModelDesc；
- Dataset 与 DataBuffer；
- 输入输出设备内存；
- DVPP Channel、帧、队列和回调上下文；
- 文件句柄、socket、线程和临时目录。

实现要求：

- 资源创建后立即登记，失败路径按创建的逆序释放。
- 禁止仅依赖进程退出释放 Context、Stream 或设备内存。
- 释放函数必须可重复调用且可安全处理空句柄。
- 推理循环前后必须记录设备内存，长循环按固定间隔采样，不能只比较单次瞬时值。
- 任何未释放资源、设备 reset、进程段错误或内存持续增长都必须作为失败证据记录。
- 不得把 `Health: Alarm` 单独当作资源释放失败的证据；必须结合具体 API、日志、退出码和内存曲线定位。

### 4.4 ATC、ONNX 与 OM 合同

每次模型转换必须归档一份机器可读合同，至少包含：

```json
{
  "modelName": "<model-name>",
  "sourceRevision": "<source-revision>",
  "sourceSha256": "<source-sha256>",
  "onnxSha256": "<onnx-sha256>",
  "omSha256": "<om-sha256>",
  "socVersion": "Ascend310B1 或 Ascend310B4",
  "cannVersion": "<actual-version>",
  "atcCommand": "<exact-command>",
  "inputs": [],
  "outputs": [],
  "precision": "<declared-precision>",
  "status": "observed-pass 或 observed-fail",
  "logPath": "<evidence-path>"
}
```

每个输入输出项必须记录名称、shape、dtype、布局和字节数。运行时必须在送入模型前校验实际数组与合同一致。以下情况禁止进入数值验收：

- 只检查 OM 文件存在，没有成功加载；
- 输入名称、shape、dtype 或字节数不一致；
- 转换日志缺失或退出码非零；
- 使用与目标 SoC 不匹配的 OM；
- 用旧模型性能数字代替当前模型结果。

### 4.5 内存、Stream 与并发

- 默认单进程单 Context、有限 Stream；扩大并发前必须有内存和延迟证据。
- 不得在未同步的线程之间共享同一个 Stream、输入缓冲区或 Dataset。
- 同一输出缓冲区不得被多个请求并发复用。
- 服务必须设置最大并发、队列长度、请求超时和优雅退出时间。
- 推理请求失败时不得返回伪造结果、空结果或 CPU 回退结果。
- 长序列、动态 shape 和大模型必须设置显存、内存、时间和输出长度上限。
- 性能测试必须区分首次加载、warmup、稳态推理和端到端请求。

### 4.6 DVPP、VENC 与摄像头

- 摄像头必须记录设备节点、实际分辨率、像素格式、帧率、缓冲区数量和协商结果。
- V4L2 打开、查询、映射、入队、出队和关闭必须成对，异常路径必须释放。
- DVPP/VENC Channel 和帧必须显式销毁，不能依赖解释器回收。
- 预览和推理不得无界并发；默认保持采集与预览串行，必要时使用有界队列。
- 摄像头失败必须与模型失败分开报告；不得把静态图片测试通过写成摄像头链路通过。
- 涉及个人图像、摄像头画面或生物特征时，必须使用合成样例或匿名化素材做文档和测试。

### 4.7 服务与命令行入口

服务必须提供：

- `/health` 或等价健康检查；
- `/bootstrap` 或配置/模型状态接口；
- 一次真实推理请求路径；
- 明确的启动失败原因和退出码；
- 初始化、请求、超时和关闭日志；
- 监听地址和端口的显式配置。

健康检查通过不等于推理通过。验收必须至少执行一次真实请求，并在请求前后采集 NPU 内存、设备状态和服务日志。

服务启动脚本必须在启动进程的同一 shell 中加载 CANN 和 conda 环境。禁止让服务在未加载 CANN 的 shell 中“健康启动”后才发现 `import acl` 失败。

### 4.8 错误、日志和退出码

- 禁止空 `except`、只打印不返回、吞掉非零退出码或把失败转换成成功的默认值。
- 错误信息必须包含阶段、API/命令、错误码、输入摘要和可执行下一步。
- 日志不得输出 token、密码、私钥、完整请求正文或真实个人图像。
- CLI 失败必须返回非零退出码；服务初始化失败必须 fail closed。
- 日志应同时保留人类可读摘要和机器可解析结果，便于后续归档。

### 4.9 性能与可复现性

性能结论至少记录：

- SoC 与计算档位；
- 模型摘要和精度；
- 输入形状、batch、序列长度和预处理；
- warmup 次数、计时循环数、重复次数和线程数；
- P50/P95 或明确的统计方法；
- 端到端与纯推理是否分开；
- 原始报告路径和采集时间。

不得只报告单次最好值，不得把 20T 数字写成 8T 结果，不得用旧模型或旧 CANN 组合的基准替代当前组合。

### 4.10 依赖与构建可复现性

- Python 项目必须声明解释器版本范围和直接依赖；生产环境必须使用锁文件或 constraints，不能只依赖当前机器已安装的包。
- C/C++ 项目必须提交构建入口和最低工具链要求；CANN 头文件、库路径和目标 SoC 编译参数必须显式传入。
- 前端项目必须提交 lockfile，板端只部署已构建产物；板端是否需要 Node.js 必须在 README 中写清。
- 构建脚本必须能在干净检出上执行，禁止依赖未记录的全局安装、个人 shell 别名或手工复制的缓存。
- 构建输出必须记录版本、目标 SoC、依赖摘要和产物摘要；生成物不得反向成为源文件。
- 依赖升级、CANN 升级和模型转换必须在同一批变更中更新合同、锁文件和验收证据。

### 4.11 安全边界

- 只读诊断使用 `ascend_board_exec`；下载、ATC、Python、pytest、msame 和教程脚本只能通过 `ascend_board_run` 执行，且必须显式设置 `allowStateChange:true`。
- HF 下载使用 `https://hf-mirror.com`；GitHub 下载使用网页代理；华为云 OBS 直连。下载目标限制在工作区或 `/tmp`。
- 案例发布复现使用 GitHub 完整 commit 和 Hugging Face 固定 revision 的板端下载；不得用控制器本地模型、ONNX/OM、数据集或未提交源码的 `scp`/`rsync` 副本替代。
- 优先使用 SSH 公钥认证；禁止在仓库、脚本参数或日志中保存密码。
- 只读诊断和状态修改必须分开。安装、升级、重启、改权限和写设备只能由用户明确执行。
- 部署脚本不得使用未经验证的递归删除或宽泛同步目标。
- `sudo`、设备写操作和固件/驱动变更必须提供目标、影响、验证和回退步骤。
- 文档中的 IP、用户名和本机路径必须使用占位符，部署配置只放本机 profile 或环境配置。

## 5. 文档规范

### 5.1 文档入口职责

| 文档 | 读者 | 必须回答 |
| --- | --- | --- |
| 根 `README.md` | 第一次访问者 | 项目是什么、如何起步、入口在哪里 |
| 仓库 `docs/README.md` | 维护者 | 工程文档如何按任务查找 |
| `src/README.md` | 教材读者 | 如何阅读教程站点 |
| `samples/README.md` | 操作者 | 案例代码在哪里、如何进入 |
| `samples/caseN/README.md` | 单案例操作者 | 最短启动、验证和排障路径 |
| `samples/caseN/docs/README.md` | 单案例维护者 | 该案例的证据和专题文档地图 |

同一个内容只能有一个主入口。README 可以摘要并链接专题文档，但不得成为同一套长文的第二份副本。

### 5.2 文档类型和文件命名

- 案例 README 固定为 `README.md`，只保留运行、部署、验证和常见故障。
- 案例专题文档放在 `docs/`，使用两位数字前缀和 ASCII 描述，例如 `04-acl-resource-lifecycle.md`。
- 文档编号在单案例内保持稳定；重命名必须同步更新 `docs/README.md`、案例 README 和所有相对链接。
- 证据文档必须包含日期、板卡/SoC、软件组合、命令、结果、失败原因和原始报告位置。
- 生成物和手工源文件必须分开；生成目录不得出现手工修订。

### 5.3 标题和结构

- 每篇文档只有一个一级标题，标题直接描述内容，不使用“结果”“说明”“其它”这类脱离上下文的泛称。
- 标题层级连续，不得从 H2 跳到 H4。
- 标题下必须紧跟正文，不能把标题当作孤立装饰。
- 需要固定交叉引用时，显式锚点必须使用可预测的 ASCII ID；生成物中的锚点必须与源 Markdown 对应。
- 理论章节、实践案例和附录的公开名称遵守仓库冻结表，不得只改 sidebar、索引或页面标题中的一处。

### 5.4 案例 README 模板

所有新案例 README 必须包含以下部分，标题可以按案例语义调整：

```markdown
# 案例 N：<冻结名称>

## 1. 目标与边界
说明业务目标、硬件边界、NPU-only 范围和明确不做的事情。

## 2. 前置条件
列出控制机、板端、CANN、conda、设备和模型资产。标明哪些检查只能在板端执行。

## 3. 最短运行
按顺序给出准备、构建、部署、启动和一条真实请求命令。

## 4. 验证
分开列出静态、设备、转换、加载、合同、数值、任务指标和性能检查。

## 5. 证据
给出当前证据的记录入口、日期、SoC/档位和原始报告路径。

## 6. 常见故障
只写可复现症状、检查顺序、停止条件和不安全操作边界。

## 7. 关联文档
链接到技术专题、证据索引、模型合同和上游 README。
```

README 不应包含：

- 长篇理论推导；
- 没有日期的历史日志；
- 从其它 README 复制的完整文档；
- 真实模型二进制、私人图像或凭据；
- 把本地检查写成板端通过的结论。

### 5.5 证据记录模板

每份验收记录至少包含：

1. 结论和证据等级；
2. 日期、操作者、SoC、计算档位；
3. CANN、驱动、固件、Python、框架和模型组合；
4. 原始命令和完整环境变量（脱敏后）；
5. 输入合同、模型摘要和配置摘要；
6. 观测到的输出、错误码、日志路径和退出码；
7. 哪些门已通过、哪些未测试、哪些失败；
8. 失败时的最小复现和停止条件；
9. 8T/20T 是否属于同一证据集；
10. 后续动作和需要用户执行的板端变更。

只允许使用以下证据词：

| 证据词 | 含义 |
| --- | --- |
| `documented` | 官方或仓库文档明确记录，但本次未在目标板执行 |
| `inferred` | 由已知事实推导，不能当作板端实测 |
| `observed-pass` | 在记录的组合上实际通过 |
| `observed-fail` | 在记录的组合上实际失败 |
| `untested` | 尚未验证 |

文档未列出某个组合只能写 `unknown`/`untested`，不能单独升级为 `unsupported`。

### 5.6 命令、链接和代码块

- 每个命令代码块必须能看出是在控制机、板端 shell、conda 环境还是容器中执行。
- 占位符使用 `<model.onnx>`、`<board-ip>`、`<evidence-path>`，不得写真实凭据或本机绝对路径。
- 续行符、引号和 PowerShell/Bash 差异必须明确；不要混用两种 shell 语法。
- 相对链接必须指向仓库内真实文件；图片必须有相对路径、可访问目标和必要的截图边界说明。
- 代码块必须标注语言；命令后的预期输出应与实际命令相邻。
- 生成物必须标明“生成，不手工修改”，并链接回源文件或生成脚本。

### 5.7 文档审查

文档改动提交前至少检查：

```bash
git diff --check
rg -n "^#|^##|^###" <changed-docs>
rg -n "<board-ip>|<model>|<evidence-path>|TODO|TBD" <changed-docs>
```

同时确认：

- 所有相对链接和图片目标存在；
- 标题层级连续且没有无意义的泛称；
- 中文正文标点和代码内标点已分开；
- 证据等级、板卡档位和日期没有混用；
- README、索引和专题文档没有互相矛盾的启动命令；
- 生成物没有被手工修改。

## 6. 验收门与完成定义

### 6.1 分层验收门

| 门 | 检查 | 通过条件 | 失败时停止在哪里 |
| --- | --- | --- | --- |
| M0 静态 | 语法、单测、前端、Markdown、链接 | 全部通过，无未解释警告 | 源码或文档 |
| M1 设备 | `npu-smi`、设备节点、驱动 | 目标 310B 可见且状态可解释 | 设备/驱动 |
| M2 CANN | `import acl`、ATC、解释器 | 启动 shell 与实际服务环境一致 | CANN/环境 |
| M3 转换 | ONNX 合同、ATC 日志、OM 摘要 | ATC 返回 0，合同和摘要归档 | ATC/模型 |
| M4 加载 | ACL 加载和一次最小执行 | OM 可加载并完成一次执行 | 运行时/模型加载 |
| M5 合同 | 名称、shape、dtype、字节数 | 运行时描述与模型一致 | 输入输出合同 |
| M6 数值 | 参考输出与 NPU 输出 | 在声明容差内 | 数值/算子 |
| M7 任务 | 业务指标和完整请求 | 达到声明协议和阈值 | 任务质量 |
| M8 性能与服务 | 延迟、并发、健康检查、真实请求 | 指标有协议，服务真实走 NPU | 性能/服务 |

任何门失败，后续门最多只能标记为 `untested`，不得用后续步骤的结果掩盖前一层失败。

插件的调试计划使用更细的内部 gate ID，但推进顺序与上面一致：`sanity` 对应 M0，`device` 对应 M1，`cann` 对应 M2，`conversion` 对应 M3，`load` 对应 M4，`contract` 对应 M5，`numerical` 对应 M6，`task` 对应 M7，`performance` 与 `service` 对应 M8。量化和框架适配是横切检查，不能替代任一门的板端证据。

### 6.2 8T/20T 验收矩阵

每个目标至少记录：

| 字段 | 8T | 20T |
| --- | --- | --- |
| SoC | `Ascend310B4` | `Ascend310B1` |
| 计算档位 | 8T | 20T |
| CANN/驱动/固件 | 实测版本 | 单独实测版本 |
| 设备门 | observed-pass/fail/untested | 单独判定 |
| 转换门 | 单独记录 | 单独记录 |
| 数值/任务 | 单独记录 | 单独记录 |
| 性能 | 不跨档位复用 | 不跨档位复用 |

### 6.3 完成定义

一个昇腾 310B 程序只有在以下条件同时满足时才算完成：

- [ ] 目标 SoC 和计算档位明确；
- [ ] 版本、环境、解释器和启动 shell 已记录；
- [ ] 运行入口、配置模板和一键验证命令存在；
- [ ] ACL/DVPP/Stream/缓冲区生命周期有显式释放；
- [ ] ATC/OM 合同和模型摘要已归档；
- [ ] 至少完成一次真实 NPU 推理；
- [ ] 输入合同、数值和任务指标分开记录；
- [ ] 8T 与 20T 结果没有合并；
- [ ] 服务的健康检查、真实请求和失败退出已验证；
- [ ] 工程目录符合规范，运行资产没有进入源码提交；
- [ ] README、编号文档、证据记录和索引互相链接；
- [ ] 所有未执行项明确标记为 `untested`。

## 7. 变更与评审

1. 开始修改前检查工作区和相关 `AGENTS.md`，保留无关用户改动。
2. 目录移动前先更新 README、索引、导入、脚本、CI 和文档链接；不得只移动文件。
3. ATC、ACL、DVPP、摄像头或服务路径变化时，必须补对应门的回归证据。
4. 只改调试文档不等于改程序验收结论；代码、合同、证据和文档必须同批更新。
5. `latex/`、`dist/`、生成的 LaTeX、缓存和临时报告不得手工修改。
6. 提交说明必须写明改动范围、已执行的本地检查、板端检查和仍未验证项。
7. 板端验证失败时，先记录最小复现和停止层，不要在未定位前连续安装或升级组件。

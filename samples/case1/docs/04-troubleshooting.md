## CASE1-ISS-20261022-01：摄像头设备可打开但没有首帧

### 状态与影响

- 状态：`unverified`
- 级别：`major`
- 影响对象：`device / camera`
- 影响范围：该次 8T 板端验收窗口内的摄像头视频链路
- 是否阻塞发布：不影响 API/ACL 烟测结论，但阻塞摄像头功能闭环结论

### 预期行为

摄像头设备打开后产生有效首帧，MJPEG 和抓拍接口返回真实图像。

### 实际症状

摄像头节点可以打开，但测试窗口内没有产生首帧。服务因此报告 `camera_ready=false`、`status=degraded`；抓拍和 MJPEG 请求返回预期的 HTTP `503`，没有返回空成功结果。

### 复现步骤

1. 在 8T 板端激活 CANN 与 `base` Python。
2. 启动案例 1 服务并访问健康接口。
3. 打开摄像头并请求抓拍或 MJPEG 首帧。
4. 观察健康状态、摄像头错误和 HTTP 返回。

### 原始证据

证据摘要见 [板端验收记录](03-board-acceptance.md) 的“本次板端验证记录”。该文件说明原始日志和运行资产已按隔离目录协议清理，未复制到 Git。

### 判定层级

`camera/device`。ACL、FastAPI、SQLite 和并发检查均未出现异常；失败发生在视频首帧之前。

### 根因状态

- 根因结论：`unknown`
- 结论说明：现有文档只证明视频节点没有输出有效帧，没有采集到摄像头固件、供电、线缆、格式协商或驱动层原始日志。

### 临时处理与修复

- 临时处理：保持 fail-closed，抓拍和 MJPEG 返回明确 `503`，不伪造空图像。
- 代码/配置修复：无。
- 未采用方案：没有把 ACL 成功或 HTTP 合同成功写成摄像头通过。

# 案例 6 审查报告：智能小车视觉感知

## 审查范围与方法

本报告审查 `src/experiment/case6.md`、`samples/case6/README.md`、`app.py`、
`lane_detector.py`、`scene_classifier.py`、`prepare_models.py`、`setup.sh` 和
当前生成的 `latex/cases/case6.tex`。审查采用正文—代码—部署脚本—生成产物的
静态交叉核对；没有在开发机运行 CANN、ATC、PyACL、OM、摄像头或 NPU 测试。

## 总体结论

案例 6 的教学目标是合理的：用经典视觉方法提取车道线，再用 NPU 分类器处理
场景语义。但当前版本把一个随机初始化的分类基线、未闭合的转换流程和若干预期
性能数字写成接近验收结果；同时输入颜色、ROI 几何、ACL 资源生命周期和网络
暴露边界没有形成一致合同。生成的 PDF 还把 Mermaid 源码作为 listing 输出。
在修复模型证据和运行时安全问题前，不宜将本案描述为已经完成的实时智能小车
感知系统。

## 已核实问题

### P1-1 输入颜色合同存在 RGB/BGR 双重转换风险

**证据。** `samples/case6/app.py:55-74,184-186` 使用 `gr.Image(type="numpy")`，
Gradio 默认提供 RGB 数组；`lane_detector.py` 按 BGR 解释输入，而
`scene_classifier.py:235-242` 又执行 BGR 到 RGB 的转换。当前代码路径没有用
显式的颜色格式字段或测试固定这一约定。

**影响。** 上传图像可能在车道线阈值和分类预处理前发生通道交换，导致颜色敏感
的 Canny/ROI 结果和模型输入与教材描述不一致。即使某些灰度道路图片看起来正常，
也不能据此证明颜色合同正确。

**建议。** 在入口处明确 `RGB`，进入经典 CV 前只做一次 `RGB -> BGR`；或全链路
统一为 RGB 并移除多余转换。增加红蓝通道可区分的固定夹具和单元测试，记录模型
预处理的通道顺序。

**验证要求。** 用合成红蓝图像分别检查车道线和分类张量的通道值；再在无 NPU 的
纯 Python 测试中验证入口、预处理和模型合同。

### P1-2 ROI 文档与实现几何不一致

**证据。** 正文 `src/experiment/case6.md:106-133` 将 ROI 描述为道路梯形并在
流程图中暗示只保留道路区域；`samples/case6/lane_detector.py:34-36,151-164`
实际建立的是从 `ROI_TOP` 到图像底部的全宽矩形蒙版，没有梯形顶点或左右边界。

**影响。** 读者按章节调参时会认为算法利用了车道透视几何，实际却把天空、建筑
或相邻车道区域带入 Hough 变换，结果和复杂场景下的预期鲁棒性不同。

**建议。** 选择一个真实合同：实现带四个顶点的梯形 ROI 并增加边界测试，或把正文
和图改为“下半部矩形 ROI”，同时降低对弯道和遮挡场景的结论强度。

**验证要求。** 对不同宽高比和 ROI_TOP 生成 mask 快照，断言保留区域与图示一致；
在直线、弯道、阴影和无车道线样本上分别记录误检和漏检。

### P1-3 随机分类头与正文性能/准确率结论冲突

**证据。** `samples/case6/prepare_models.py:49-64,157-190` 默认创建
ImageNet 骨干加随机初始化的五类分类头，正文 `src/experiment/case6.md:260-274`
也承认该基线预测是随机的；但 `case6.md:430-447` 仍列出清晰标线率大于 90%、
分类准确率大于 85%、NPU 10--15 ms、总延迟约 20 ms 和 OM 约 45 MB 的表格，未
给出训练数据、评测集或原始报告。

**影响。** 随机模型不能支持任务准确率结论；单张示例图或设计目标也不能支持
延迟和实时性结论。读者可能把“目标/预期”误读成已测结果。

**建议。** 将表格改为明确的设计目标或 `N/A`，直到有固定训练权重、独立验证集、
混淆矩阵和板端报告。性能报告应单独区分 OM 纯推理、预处理、车道线检测和端到端
UI 延迟。

**验证要求。** 在明确的驾驶场景数据集上训练并固定 checkpoint；在目标
Ascend 310B4/8T 上记录 warmup、循环、重复、P50/P95、输入形状、CANN 版本和
模型摘要，再回填正文。

### P1-4 转换失败和 SoC 不确定时没有 fail-closed

**证据。** `prepare_models.py:157-190` 捕获 ATC 异常后只打印错误；
`prepare_models.py:33-46` 在找不到 `npu-smi` 时静默使用 `Ascend310B4` 默认值。

**影响。** 转换失败可能仍留下看似成功的流程状态，错误 SoC 也可能生成不兼容
的命令。后续 ACL 失败会被推迟到运行时，难以区分模型问题和环境问题。

**建议。** ATC 非零退出必须传播为非零状态并清理不完整输出；SoC 必须由显式参数
或已验证的板端探测提供，探测失败即停止，不用猜测值。把命令、日志、CANN 版本
和输出摘要写入单独报告。

**验证要求。** 使用不存在的 ONNX、错误 SoC 和模拟 ATC 非零返回测试脚本；确认
不会生成可被服务误认的 OM，也不会把候选模型标记为 ready。

### P1-5 Web 服务默认暴露且缺少认证边界

**证据。** `samples/case6/app.py:259-263` 绑定 `0.0.0.0`；
`samples/case6/README.md:63-77` 推荐使用 `--share`，没有认证或 TLS 方案。服务
接收用户上传的道路图像。

**影响。** 未授权局域网或 Gradio 分享链路可访问摄像头/上传接口，扩大图像和系统
信息的暴露面。教程未明确这是仅限可信实验网的临时配置。

**建议。** 默认监听 loopback；跨机器访问必须显式参数、反向代理/认证和受控网络，
删除或强烈限制 `--share` 示例。说明仅使用合成或匿名图片，并规定日志和上传文件
留存策略。

**验证要求。** 检查默认监听地址、未认证请求、跨网段访问和停止服务后的临时文件；
在板端再做网络隔离和实际摄像头权限测试。

### P1-6 ACL 资源和张量合同未闭合

**证据。** `samples/case6/scene_classifier.py:34-63,94-167` 的部分初始化异常
路径没有完整资源清理，`add_dataset_buffer` 返回值未检查，数据 buffer 没有明确
销毁；`execute/classify`（约 `:269-279`）也未严格校验输入字节数、输出 shape、
dtype，直接按 `float32` 解码。

**影响。** 连续请求或初始化失败可能泄漏设备资源；FP16/不同输出布局的 OM 可能
被错误解释，产生看似合理但语义错误的概率。

**建议。** 采用明确的 context/stream/model/buffer 生命周期和异常清理；从 manifest
读取输入输出合同，校验字节数、shape、dtype、有限值和类别数；任何不匹配都显式
失败，禁止静默转换。

**验证要求。** 在板端执行重复初始化、异常中断、错误输入尺寸和 FP16 输出测试，
观察资源计数、ACL 返回码和进程退出状态。

## 其他教学与实现问题

### P2-1 安装脚本越过本地/板端边界

`samples/case6/setup.sh:7-18` 自动执行 `sudo apt`、`pip install` 和模型导出，
而教程把它作为常规入口。这会把系统修改、依赖版本和可能的 CANN/ATC 操作混在
一个不可审计脚本中。应拆分开发机依赖、板端准备和模型转换步骤，并锁定依赖版本。

### P2-2 空示例入口与正文不一致

`samples/case6/app.py:189-193` 创建 `gr.Examples(examples=[])`，但文档写成将图片
放入 `photos/` 后会自动显示。应实现目录扫描，或删除该操作说明。

### P2-3 车道区域叠加不是半透明

`lane_detector.py:122-145` 在已经混合的图像上直接 `fillPoly`，正文却称填充区域
为半透明。应使用单独 overlay 后 alpha blend，或把文案改为不透明填充。

### P2-4 PDF 将 Mermaid 当作代码输出

当前 `src/experiment/case6.md` 含六段 Mermaid；生成的 `latex/cases/case6.tex`
相应位置（如第 70、204、295、386、575 行附近）仍是 `lstlisting`。PDF 因此不能
提供正文所需的硬件、算法和界面结构图，应替换为静态 PNG/确定性矢量图后重新构建。

## 未验证项目与板端边界

1. RGB/BGR 路径的最终行为仍应以真实 Gradio 版本和固定色彩图夹具运行确认；本报告
   将其列为高风险合同问题，不把单一灰度样本视为通过。
2. 没有在开发机执行 CANN、ATC、PyACL、OM、摄像头或 NPU；所有准确率、延迟、帧率
   和设备兼容性数字均未由本次审查重新测量。
3. 修复后须分别完成纯 Python 单测、板端模型转换/ACL smoke、摄像头采集和浏览器
   UI 检查；任何一个门禁失败都应保留失败证据，而不是回退到随机或 CPU 结果。

## 发布前顺序

1. 先闭合颜色、ROI、模型输出和 ACL 生命周期合同。
2. 再拆分安装/转换脚本并收紧网络监听和数据边界。
3. 删除无证据性能表，完成训练与板端测量后再回填。
4. 替换所有 Mermaid、重建 PDF 并检查缺字、溢出和图示清晰度。

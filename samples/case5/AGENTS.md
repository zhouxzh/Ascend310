# Case 5 目录级开发说明

## 案例定位

Case 5 是一个基于昇腾 310B 开发板的“智能数据采集仪”教学案例。案例面向边缘 AI 和嵌入式数据处理的学习者，目标是展示从真实信号采集、数据整理、实时分析到结果展示的完整链路，而不是只做一个传感器数据记录程序。

本案例必须同时包含：

1. 数据采集：连续采集并保存电压、电流等时序信号，保留时间戳、采样率、通道和设备信息。
2. 数据分析：对正在采集的数据进行实时处理，输出可解释的统计量、波形/频谱特征、状态判断或异常告警。
3. 边缘 AI 推理：将有实际教学意义的分析任务部署到昇腾 310B 的 NPU 上执行。

如果只有采集、存储或 CPU 端离线分析，而没有使用 310B NPU 完成核心分析任务，则不满足本案例的目标。

## 目标硬件链路

教学案例优先采用以下开放硬件组合：

- 汉泰开源示波器：采集被测对象的电压波形。
- 开源电流探头：采集与电压同步或可对齐的电流波形。
- 昇腾 310B 开发板：负责数据接入、预处理、实时特征分析和 NPU 推理。

具体接口（USB、串口、网络或其他方式）、协议和采样率必须以手头硬件的实际文档和设备日志为准，不能凭假设写死。电压与电流通道应尽可能使用统一时钟或明确记录时间偏移，以便计算相位、功率和异常关联特征。

接入真实电气信号时，必须先确认探头量程、隔离方式、接地方式、带宽和校准参数。示例代码可以提供模拟数据模式，但模拟模式只用于教学开发和软件回归测试，不能替代真实硬件验收。

## 推荐教学流程

案例实现应让读者能够沿着下面的流程学习和复现：

1. 从示波器和电流探头读取原始电压/电流采样，并进行时间戳、单位换算、校准和丢包检查。
2. 以固定窗口构建实时数据帧，完成去直流、滤波、归一化、重采样或窗口函数等预处理。
3. 在 CPU 上完成必要的轻量数据搬运和确定性预处理，在 NPU 上完成核心模型推理或高计算量分析。
4. 输出波形、频谱/时频图、RMS、峰值、峰峰值、功率相关量、功率因数（适用时）以及异常/状态分类结果。
5. 在仪表盘中同时展示原始采集状态、分析延迟、NPU 后端、模型版本和告警原因，并将关键结果与原始窗口关联保存。

分析任务可以从电压/电流状态识别、负载变化检测、谐波/异常检测或故障分类中选择，但必须说明输入窗口、标签或阈值、模型输出和实时性指标。模型应优先使用适合 310B 的 ONNX/OM 推理链路；Python/CPU 结果可作为数值基线和对照，不得悄悄成为默认的“完成方案”。

## NPU 使用要求

- 核心分析路径必须明确调用昇腾 ACL/CANN 推理接口或等价的 310B NPU 运行时，并加载经过验证的 OM 模型。
- 程序启动和仪表盘状态中应清楚显示实际后端（例如 `NPU (Ascend 310B)`），记录模型输入输出形状、推理耗时和错误信息。
- CPU 代码可以承担采集、队列、预处理、日志和界面工作，也可以提供开发期基线；CPU fallback 必须显式标注为降级或模拟模式，不能伪装成 NPU 结果。
- `time_frequency_dashboard/model/prepare_models.py` 中涉及 ONNX 导出和 ATC/OM 转换的步骤属于昇腾设备操作。不要在普通本地开发机上安装或运行设备专用组件；上板后再完成转换和 NPU 验证。
- 没有可用 310B 或 OM 模型时，软件可以运行模拟/基线模式帮助教学，但文档和验收结果必须明确说明“尚未完成 NPU 验证”。

## 数据与实时性约定

原始数据和派生结果应可追溯。建议至少记录：采集时间戳、窗口起止时间、通道名、采样率、原始值或文件引用、校准版本、特征、模型版本、推理后端、结果、置信度和处理耗时。

实时处理应使用有界缓冲区和固定窗口，明确窗口长度、步长、允许延迟、丢帧策略和背压行为。不能因为界面刷新而无限制增长内存，也不能只显示最新结果而丢失分析所依据的数据上下文。

## 教学和代码规范

- 代码、`README.md` 和相关实验文档应保持一致；新增硬件接口时同时补充协议、接线假设和运行步骤。
- 示例应优先清晰、可观察、可复现，避免把复杂框架封装到读者无法理解的黑盒中。
- 对真实硬件、量程、安全和性能的描述必须以设备资料或实测日志为依据，不作未经验证的昇腾架构或实时性承诺。
- 本地可进行 Python 语法检查、pytest 单元测试和模拟数据测试；涉及 CANN、ACL、ATC、OM、`npu-smi` 或硬件采集的行为，必须在真实昇腾 310B 开发板上验证。

## 目录与命名规范

- 开发板上的 Case 5 项目根目录固定为 `~/Documents/case5`。文档、同步命令和运行命令不得放在临时工作目录下，脚本应从自身位置解析项目根目录。
- 主运行包固定命名为 `time_frequency_dashboard/`。名称必须表达“时频分析仪表盘”的功能，不能使用 `case5_app`、`app` 等缺乏含义的名字，也不能把包名绑定到 Hantek 或其他单一示波器品牌。
- 后续更换或增加开源示波器时，只在 `time_frequency_dashboard/acquisition/` 下新增独立采集适配器；公共帧协议、预处理、NPU、存储和界面层不得依赖具体示波器品牌。
- `time_frequency_dashboard/model/` 只存放固定 NPU DFT 设计、NumPy 数值参考、ONNX 原生图生成、ATC/OM 准备和 NPU 数值校验代码。
- `models/` 只存放板端生成的 ONNX、OM 和元数据产物；`data/` 只存放运行时会话数据。生成物不得与源码混放，默认不得提交。
- 案例根目录不得散落业务 `.py` 文件。Python 源码只能位于 `time_frequency_dashboard/` 或 `tests/`；根目录只保留入口文档、开发说明、pytest 配置、依赖声明和职责明确的子目录。
- `scripts/` 只保留当前可执行的板端准备、启动脚本及脚本索引。已停用的 OpenHantek 桥接补丁、编译脚本和旧振动案例脚本不得继续留在主目录误导读者。
- 目录和文件名必须让读者不打开文件也能判断职责。重组目录后，必须同步更新 Python 导入、Shell 命令、README、实验章节链接和板端运行路径。

当前推荐结构如下：

```text
case5/
├── time_frequency_dashboard/   # 采集、处理、NPU、会话和触摸界面
│   ├── acquisition/            # 不同示波器和模拟采集适配器
│   └── model/                  # NPU DFT 模型与 ONNX/OM 工具
├── docs/                       # 01/02/03 编号教学文档
├── scripts/                    # 板端准备与启动脚本
├── tests/                      # pytest 测试
├── models/                     # 板端生成模型
└── data/                       # 运行时会话
```

## 采集实现规范

- 当前 Hantek 6022BE 主路径统一使用系统 `libsigrok` 的 `hantek-6xxx` 驱动，并通过 `time_frequency_dashboard/acquisition/native/sigrok_capture_bridge.c` 输出 BridgeFrameV1；不要再把 `pyhantek6022` 或 OpenHantek 编译桥接作为运行前置条件。
- `libsigrok-dev`、`sigrok-cli`、`gcc` 和 `pkg-config` 是板端 sigrok 桥编译依赖，必须由用户手动安装；Python `base` 环境只安装 `requirements-board.txt` 中的用户态包。
- 所有硬件源必须输出统一的双通道帧契约，至少包含帧序号、主机接收时间、实际采样率、通道样本、削顶和连接状态。后续处理层不得直接解析某个示波器库的私有返回格式。
- 板端用户态依赖统一记录在 `requirements-board.txt`；USB 排查先运行
  `python -m time_frequency_dashboard.acquisition.usb_diagnostics`，该程序只能枚举设备，
  不得在诊断阶段打开设备或上传固件。
- PulseView、`sigrok-cli` 和仪表盘不能同时占用同一台 6022BE。切换程序前必须关闭占用程序；如果设备仍处于 `1d50:608e` 的 `fx2lafw` 固件状态，物理拔插设备后再启动下一个 sigrok session。
- GitHub 下载必须显式通过用户指定的 Clash 代理。使用 `CASE5_CLASH_PROXY` 或命令级代理参数，不得把某台开发主机的固定局域网 IP 写死到源码。
- 如果运行所需的系统软件包缺失，必须先报告准确包名、用途和手动安装命令，并同步写入文档。不得自行执行 sudo 安装；等待用户手动安装完成后再继续板端验证。

## 文档规范

- `README.md` 是唯一总入口，必须按“阅读导航、目录职责、固定分析契约、板端准备、模型生成、仪表盘启动、测试、安全边界”的顺序组织。
- `docs/` 当前文档数量较少，不再设置 `docs/hardware/` 中间目录。文档直接按学习顺序编号，例如 `01_hantek6022be.md`、`02_little_bee_b1.md`、`03_architecture.md`。
- 文档文件名和一级标题都必须带相同序号；新增文档时保持连续编号，并更新 README 导航。
- Hantek 6022BE 和 Little Bee B1 必须维持两份独立文档。硬件资料、采购记录、接线、驱动、固件、标定、安全限制和实测状态不得混成一个难以维护的大文件。
- 文档中的实机截图必须注明信号来源、接线方式和验证范围。现有 PulseView 截图来自探头接触 6022BE `CAL` 标准测试输出，只证明真实采集链路连通，不代表幅值、带宽、双通道或 NPU 已验收。
- Markdown 源文件是内容真源。修改案例内容时先更新 `samples/case5/README.md`、`samples/case5/docs/` 和 `src/experiment/case5.md`；不要直接修改生成的 LaTeX。

## 测试规范

- `tests/` 中所有测试必须使用 pytest，不得新增 `unittest.TestCase`、`unittest.skipIf` 或 `python -m unittest` 入口。
- 普通测试使用 `assert`、`pytest.raises` 和 `pytest.approx`；NumPy 数值比较使用 `numpy.testing`；可选依赖使用 `pytest.importorskip` 明确跳过。
- pytest 固定通过根目录 `pytest.ini` 从 `tests/` 收集，并使用 `--import-mode=importlib`，避免板端残留同名测试文件造成导入冲突。
- 本地至少执行 `python -m pytest -q` 和 `python -m compileall -q time_frequency_dashboard`。ONNX 图测试必须与 NumPy 数值参考进行对照，不能因缺少训练框架而跳过。
- 板端纯 Python pytest 可以在既有 `base` Conda 环境运行；USB、PySide6、CANN、ATC、ACL、OM 和 NPU 行为仍需单独进行真实硬件验收，不能由 pytest 模拟结果替代。
- 真实硬件集成测试固定为 `tests/test_hardware_capture_and_inference.py`，只有设置 `CASE5_RUN_HARDWARE_TESTS=1` 才运行；测试必须先取得真实双通道窗口，再调用 OM 推理。

## 昇腾模型实现规范

- 昇腾 310B 程序禁止依赖 PyTorch、`torch`、`torch_npu` 或 `torch.onnx`。不得为了导出 ONNX、运行测试或提供 CPU fallback 而引入这些包。
- 固定 Hann 窗正弦/余弦 DFT 投影权重使用 NumPy 生成；ONNX 模型必须通过 `onnx.helper` 和标准 ONNX 算子直接构建，再由板端 ATC 转换为 OM。频谱功率、频谱曲线和瀑布必须来自 OM；CPU 不得生成或显示 FFT 频谱替代结果。
- 板端运行路径只加载 OM 并通过 `aclruntime.InferenceSession` 执行真实 NPU 推理。NumPy 和 ONNX Runtime 只用于模型准备与数值基线，不得成为仪表盘的 NPU 替代后端。
- 如未来需要训练可学习模型，训练工程必须与本案例的 310B 部署程序隔离；部署仓库只接收经过审查的 ONNX/OM 产物及其元数据。

## 验收标准

完成本案例至少应能证明：

1. 能从示波器和电流探头（或明确标注的模拟适配层）获得带时间信息的电压、电流数据。
2. 能对连续窗口进行实时分析，并展示分析结果及其依据，而非只保存 CSV。
3. 在昇腾 310B 上能成功加载 OM 模型并由 NPU 完成核心分析；日志或界面能证明实际后端和推理耗时。
4. NPU 不可用时，程序会明确报告降级状态，且不会把 CPU 模拟结果误报为 NPU 结果。
5. 教学文档能说明数据流、预处理、模型输入输出、硬件连接、运行命令和设备端验证步骤。

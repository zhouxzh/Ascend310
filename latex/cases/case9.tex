\chapter{案例
9：智能聊天机器人}\label{ux6848ux4f8b-9ux667aux80fdux804aux5929ux673aux5668ux4eba}

本案例实现 \textbf{Ascend Edge
Chat}：一个部署在昇腾边缘设备上的文字聊天服务。它将浏览器文字界面、带
Bearer 鉴权的 OpenAI 兼容网关和 MindSpore 推理 worker
分成三个进程。这样既能在局域网中提供易用的聊天页面，也能让后续应用通过标准接口调用模型。

本案例的发布基线是 Ascend 310B1 / 20T，默认模型为
Qwen1.5-0.5B-Chat。它是技术预览；文字聊天是当前唯一有 20T
运行证据的发布链。源码包含默认关闭的浏览器与板端双模式语音控制面，但
ASR/TTS、USB/3.5mm 录放音、HTTPS
浏览器语音和设备协议均未通过验收，不能写成发布能力。教学目录还保留所有已经出现技术运行证据的模型；模型是否能运行与中文回答质量分开判断。其他硬件、模型或软件版本不能直接继承本案例的结论，必须重新执行本章的验证门。

\end{enumerate}

\section{系统架构}\label{ux7cfbux7edfux67b6ux6784}

浏览器不接触模型和网关密钥。密钥保存在 UI
服务进程中；请求经回环地址上的网关鉴权后，再由网关转发给 MindSpore
worker。worker 一次只加载一个模型
profile，并按顺序执行生成，避免多个模型同时占用
NPU。切换到教学模型时，服务端会停止旧 worker、启动指定
profile、检查健康状态并清空会话。客户端只能选择已注册的
profile，不能提交任意模型路径或替换模型代码。

板端模式的路径是：

\begin{lstlisting}
USB 麦克风 -> voice-agent -> VAD -> ASR -> :7861 网关 -> :8090 worker
USB 音箱   <- voice-agent <- TTS <- 完整文本或按句文本
\end{lstlisting}

第一版板端模式必须半双工运行：\passthrough{\lstinline!LISTENING -> SPEECH -> SILENCE\_HOLD -> ASR -> LLM -> TTS -> PLAYING -> COOLDOWN!}。
播放时停止采集，或在将来以独立证据验证回声控制；不能一边播放一边把扬声器声音当作下一轮输入。VAD
阈值、静音时长、最大话语时长和冷却时长均为待测参数，不能从文字聊天的成功推导。

浏览器模式的路径是：\passthrough{\lstinline!HTTPS 浏览器录音 -> UI 代理 -> loopback voice-agent -> ASR -> 网关/worker -> TTS -> UI 代理 -> 浏览器播放!}。远程浏览器的麦克风权限要求安全上下文；当前
\passthrough{\lstinline!http://<board-ip>:7865/!}
的文字页面不能被当作浏览器录音已可用的证据。浏览器不能直接访问
\passthrough{\lstinline!127.0.0.1:7862!}，因为那是浏览器自身的
loopback；也不能访问开发板 ALSA 或直接访问 voice-agent。

当前语音核心的源码合同已限制为
\passthrough{\lstinline!disabled!}、\passthrough{\lstinline!browser!} 和
\passthrough{\lstinline!board!}
三种模式。\passthrough{\lstinline!browser!} 模式只处理受限的 16
kHz、单声道、S16 WAV；\passthrough{\lstinline!board!} 模式才会枚举和打开
ALSA。源码合同不等同于当前 20T 语音服务、ASR 或 TTS 已通过。

20T 板的 ALSA 枚举会随 USB
外设连接状态变化。\passthrough{\lstinline!2026-10-20!}
的只读快照曾看到板载 \passthrough{\lstinline!ascend310b!} ALSA
卡的播放节点 \passthrough{\lstinline!/dev/snd/pcmC0D0p!}、采集节点
\passthrough{\lstinline!/dev/snd/pcmC0D1c!}，以及 Jieli USB Composite
Device 的采集节点 \passthrough{\lstinline!/dev/snd/pcmC1D0c!}；未看到
USB playback PCM。\passthrough{\lstinline!2026-10-21!}
的一次重新枚举只保留板载 card 0，Jieli USB 设备已不在当前系统中；连接
UGREEN 1080P 摄像头后，系统又枚举到 \passthrough{\lstinline!hw:1,0!} 的
USB capture 端。其实际参数是 S16\_LE、双声道、16--48 kHz，不能套用强制
单声道采集；语音模块会在内存中下混为 ASR/VAD 所需的 16 kHz 单声道
PCM。没有 USB playback PCM 条目，且两次快照中节点均为
\passthrough{\lstinline!root:audio!}、模式
\passthrough{\lstinline!0660!}， \passthrough{\lstinline!HwHiAiUser!}
未显示在 \passthrough{\lstinline!audio!} 组中。USB
枚举不等于已成功录音或播放；实际启用前，管理员需按当前板端枚举审查账户权限，例如选择加入
\passthrough{\lstinline!audio!} 组后重新登录并用
\passthrough{\lstinline!id -nG!} 复核，不能让服务以 root 身份绕过权限。

两种模式的 USB/3.5mm
采集播放、权限生效、HTTPS、浏览器权限、VAD、ASR、TTS、隐私和十轮闭环均为
\passthrough{\lstinline!untested!}。ASR/TTS 即使先在 CPU
隔离进程运行，也只能说明音频服务路径，不构成 NPU
语音推理证据。详细的模型锁、隐私边界和分模式人工验收门见\href{https://github.com/zhouxzh/Ascend310/blob/main/samples/case9/docs/08-board-voice-terminal-plan.md}{语音模式与板端终端方案}。

\section{环境准备}\label{ux73afux5883ux51c6ux5907}

本案例不安装或升级驱动、固件、CANN、OPP、MindSpore 或
MindNLP。先在目标开发板上选择一个已经验证的 Conda 环境，再在同一个 shell
中激活 CANN 环境。

\begin{lstlisting}[language=bash]
cd /opt/ascend-edge-chat
export ASCEND_EDGE_CHAT_CONDA_ENV='<已验证的 Conda 环境名称>'
source /usr/local/miniconda3/etc/profile.d/conda.sh
conda activate "$ASCEND_EDGE_CHAT_CONDA_ENV"
python -m pip install --no-deps .
export ASCEND_EDGE_CHAT_DATA_DIR=/opt/ascend-edge-chat-data
cp configs/release.env.example .env
chmod 600 .env
\end{lstlisting}

编辑 \passthrough{\lstinline!.env!}，将
\passthrough{\lstinline!ASCEND\_EDGE\_CHAT\_GATEWAY\_API\_KEY!} 改成至少
24 个 ASCII 字符的随机值。不要将密钥写入源代码、浏览器
JavaScript、终端截图或 Git 提交。

若预检发现当前环境缺少 FastAPI、Pydantic、Uvicorn 或 dotenv，不要依赖
user-site。应先准备经过审核的本地 wheel
目录，再执行带哈希的最小服务依赖安装：

\begin{lstlisting}[language=bash]
export ASCEND_EDGE_CHAT_WHEELHOUSE=/opt/ascend-edge-chat-wheelhouse
bash scripts/verify/install-service-dependencies.sh
\end{lstlisting}

该脚本使用
\passthrough{\lstinline!--no-index --no-deps --require-hashes!}，只安装发布锁中的服务层依赖，不升级
CANN、MindSpore、MindNLP，也不安装新的模型推理框架。

执行环境预检：

\begin{lstlisting}[language=bash]
bash scripts/verify/release-preflight.sh
\end{lstlisting}

预检会显示 Python 可执行文件，导入
\passthrough{\lstinline!acl!}、MindSpore 与 MindNLP，显示
\passthrough{\lstinline!npu-smi info!}，核对所有模型文件，并解析网关配置。预检失败时应先定位环境、CANN
或模型文件问题；不能为了获得响应而自动改用 CPU、云端或其他推理框架。

\section{获取或导入模型}\label{ux83b7ux53d6ux6216ux5bfcux5165ux6a21ux578b}

通过镜像下载时：

\begin{lstlisting}[language=bash]
bash scripts/import/download-model.sh
\end{lstlisting}

通过离线目录导入时：

\begin{lstlisting}[language=bash]

\begin{lstlisting}[language=bash]
ascend-edge-chat verify --data-dir "$ASCEND_EDGE_CHAT_DATA_DIR"
\end{lstlisting}

\section{启动服务}\label{ux542fux52a8ux670dux52a1}

分别打开三个终端，在项目根目录执行：

\begin{lstlisting}[language=bash]
# 终端一：NPU worker
bash scripts/run/start-worker.sh

# 终端二：网关
bash scripts/run/start-gateway.sh

# 终端三：文字页面
bash scripts/run/start-ui.sh
\end{lstlisting}

三个脚本都在前台运行，便于查看错误并按 \passthrough{\lstinline!Ctrl+C!}
停止对应进程。不要使用宽泛的进程名匹配来结束其他 NPU 任务。

命令行入口等价于：

\begin{lstlisting}[language=bash]
ascend-edge-chat worker
ascend-edge-chat gateway --check-config
ascend-edge-chat ui
\end{lstlisting}

\subsection{选择教学模型}\label{ux9009ux62e9ux6559ux5b66ux6a21ux578b}

页面会列出教学目录。\passthrough{\lstinline!selectable=true!}
表示已有技术运行证据，哪怕 \passthrough{\lstinline!quality\_status!} 是
\passthrough{\lstinline!failed!} 或 \passthrough{\lstinline!pending!}
也仍可选；\passthrough{\lstinline!blocked!}/\passthrough{\lstinline!not-run!}
表示 尚未完成 loader、工件或 NPU
前置门，暂时不能启动。页面选择不同模型后会执行 受控的 worker
重启：先检查固定 registry 和本地缓存，停止当前 worker，使用 CANN
启动脚本加载目标 profile，并等待 \passthrough{\lstinline!/health!}
返回目标模型。切换成功后会清空
浏览器会话；若目标启动失败，会尝试恢复原模型。它不是在同一进程中同时加载多个
模型，也不允许网页提交路径、shell 命令或 Python
表达式。生成期间，页面会禁用 选择器；收到终止 SSE
事件后，服务端还会等待一个短暂的流式收尾窗口再开始切换。

\begin{lstlisting}[language=bash]
export ASCEND_EDGE_CHAT_PROFILE=qwen2-1.5b-instruct-mindspore
ascend-edge-chat worker \
  --profile "$ASCEND_EDGE_CHAT_PROFILE" \
  --registry configs/tutorial-models.json
\end{lstlisting}

如果选择的模型没有完整本地缓存，页面会在停止当前 worker
前报告失败；它不会 自动改用
CPU、云端或未锁定的远程权重。下面的命令仍可用于无浏览器的恢复操作，
或者在自动回滚也失败后恢复默认 profile：

\begin{lstlisting}[language=bash]
ascend-edge-chat worker --profile qwen1.5-0.5b-chat
\end{lstlisting}

\passthrough{\lstinline!app.py!} 与
\passthrough{\lstinline!text\_chat\_app.py!}
仅为短期兼容包装器。新部署和二次开发脚本应使用
\passthrough{\lstinline!ascend-edge-chat!} 命令。

\section{调用 OpenAI
兼容接口}\label{ux8c03ux7528-openai-ux517cux5bb9ux63a5ux53e3}

网关公开模型名固定为
\passthrough{\lstinline!ascend-edge-chat!}。调用方必须携带 Bearer 密钥。

\begin{lstlisting}[language=bash]
curl http://127.0.0.1:7861/v1/models \
  -H "Authorization: Bearer $ASCEND_EDGE_CHAT_GATEWAY_API_KEY"

curl http://127.0.0.1:7861/v1/chat/completions \
  -H "Authorization: Bearer $ASCEND_EDGE_CHAT_GATEWAY_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "model":"ascend-edge-chat",
    "messages":[{"role":"user","content":"请用一句中文介绍你自己。"}],
    "temperature":0,
    "top_p":1,
    "max_tokens":32
  }'
\end{lstlisting}

将 \passthrough{\lstinline!stream!} 设置为
\passthrough{\lstinline!true!} 可获得 Server-Sent Events。网关会将
worker 的内部模型名改写为公开模型名，再把增量返回给客户端。

接口限制如下：

\begin{itemize}
\tightlist
\item
  仅接受
  \passthrough{\lstinline!system!}、\passthrough{\lstinline!user!}、\passthrough{\lstinline!assistant!}
  三种角色；
\item
  仅支持 greedy
  解码：\passthrough{\lstinline!temperature=0!}、\passthrough{\lstinline!top\_p=1!}；
\item
  最大上下文为 1024 token；网页默认输出预算为 128 token，服务硬上限为
  256 token，具体 profile 可以声明更小上限；
\item
  单进程、单请求串行执行；
\item
  请求体最大 256 KiB；
\item
  超时或运行时错误时 fail-closed，不自动切换后端。
\end{itemize}

浏览器会话只保存在 UI 进程内存中，最多保留 4 条消息和 4,000
个字符。清空会话、重启页面服务或停止进程都会丢弃这些消息。

\section{验收方法}\label{ux9a8cux6536ux65b9ux6cd5}

不能用``服务已启动''代替模型验收。每个目标板都应独立记录以下证据：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  SoC、CANN、Python、MindSpore、MindNLP、驱动和模型 SHA-256；
\item
  worker NPU 初始化和单 token 生成；
\item
  \passthrough{\lstinline!/health!}、\passthrough{\lstinline!/v1/models!}、JSON
  与 SSE；
\item
  \passthrough{\lstinline!8!}、\passthrough{\lstinline!16!}、\passthrough{\lstinline!32!}、\passthrough{\lstinline!64!}、\passthrough{\lstinline!128!}、\passthrough{\lstinline!256!}
  token 的 UTF-8、结束原因和截断检查；
\item
  连续 10 轮短请求的 PID、RSS、文件描述符和 NPU 快照；
\item
  浏览器页面通过网关完成一次对话；
\item
  明确 warmup、轮数、百分位算法的首 token、总延迟和 token/s；
\item
  保存中文和英文完整响应，分别标注``可理解、部分可理解、不可理解''；
\item
  将技术门和质量门分别写入报告，不因为质量失败而删除可运行模型。
\end{enumerate}

\subsection{长度、文本完整性与中文语义质量}\label{ux957fux5ea6ux6587ux672cux5b8cux6574ux6027ux4e0eux4e2dux6587ux8bedux4e49ux8d28ux91cf}

\passthrough{\lstinline!max\_tokens!} 是本轮\textbf{最多新生成多少
tokenizer token}，不是``最多多少汉字''。 同一段中文可能被分成一个或多个
token；它还受
\passthrough{\lstinline!prompt\_tokens + max\_tokens <= 1024!}
的上下文上限约束。页面默认发出
\passthrough{\lstinline!128!}，可以在页面的``最大输出 token''
下拉菜单中选择当前模型允许的档位；普通 Qwen 教学 profile 当前可选
\passthrough{\lstinline!32/64/96/128/192/256!}。如果模型没有在上限前输出
EOS，接口返回 \passthrough{\lstinline!finish\_reason=length!}，页面会
保留已生成文本并提示截断。这是长度门结果，不是模型崩溃，也不能直接作为中文
质量差的证据。

质量验收必须单独进行。针对每个 profile，以新会话、greedy
解码、\passthrough{\lstinline!max\_tokens=256!} （或该 profile
的已验证上限）运行同一组 10 条中文提示，保存完整 JSON/SSE、模型
revision、提示与完成 token
数、\passthrough{\lstinline!finish\_reason!}。先标注是否出现
\passthrough{\lstinline!U+FFFD!} 等文本
完整性异常；\passthrough{\lstinline!finish\_reason=length!}
的回答标为``未完成''，不计入语义失败。随后由
至少两名评审者对相关性、事实性、流畅性和完成度分别打 0/1/2
分，并保留分歧。 只有该人工流程才能把
\passthrough{\lstinline!quality\_status!}
标为通过或失败；历史短预算中的替换字符 只能保留为
tokenizer/解码的待复核观察。

\subsection{20T
长输出边界实测示例}\label{t-ux957fux8f93ux51faux8fb9ux754cux5b9eux6d4bux793aux4f8b}

不要把配置文件中的 \passthrough{\lstinline!max\_tokens!}
当作已验证能力。以 20T 的 \passthrough{\lstinline!Qwen2 1.5B Instruct!}
为例，在 \passthrough{\lstinline!Ascend310B1!}、CANN
\passthrough{\lstinline!8.0.0!}、MindSpore
\passthrough{\lstinline!2.4.10!}、MindNLP
\passthrough{\lstinline!0.4.1!} 上，先发现其 tokenizer 目录没有
\passthrough{\lstinline!tokenizer\_config.json!}，默认模板为空。旧通用回退错误使用
Qwen1.5 风格的 \passthrough{\lstinline!<|user|>!} /
\passthrough{\lstinline!<|assistant|>!}，于是模型在第一轮回答后继续生成下一轮角色标记。将
审核后的 Qwen2 ChatML 模板固定到 profile 后，经网页 SSE
链路的强制长输出测试中： \passthrough{\lstinline!64!} token 在
\passthrough{\lstinline!80.029 s!}、\passthrough{\lstinline!128!} token
在 \passthrough{\lstinline!158.946 s!}、\passthrough{\lstinline!192!}
token 在 \passthrough{\lstinline!238.133 s!} 均跑满，三轮都返回
\passthrough{\lstinline!finish\_reason=length!}，无
\passthrough{\lstinline!U+FFFD!} 和角色标记， worker
恢复健康。\passthrough{\lstinline!256!} token 请求仍在产生长段 SSE
输出后失去 worker 终态， 日志含 TBE
\passthrough{\lstinline!main process disappeared!}
与资源清理警告，而不是显存用尽记录。因此该 profile 的页面下拉菜单和
worker 当前只允许到 \passthrough{\lstinline!192!}，服务的全局
\passthrough{\lstinline!256!} 上限仍保留给 需要单独验收的其他 profile。

这组数据说明三件事：token
预算与汉字数无一一对应；速度和可完成的最大长度必须 分开测量；一次 worker
退出只能说明该软件、模型 revision、提示词和 watchdog 组合
的失败，不能外推成整个 310B 产品族不支持该模型。学生应保存每一档的 SSE、
\passthrough{\lstinline!finish\_reason!}、完成 token 数、worker
健康状态和 \passthrough{\lstinline!npu-smi!} 快照，再更新 profile
的可选档位。

可在板端以如下命令重复长度门。应从较小档位逐级升高，并在前一档 worker
已恢复 健康后才运行后一档：

\begin{lstlisting}[language=bash]
python scripts/verify/output_budget_probe.py \
  --profile qwen2-1.5b-instruct-mindspore \
  --budgets 128,192 \
  --timeout 330 \
  --output run/output-budget-$(date -u +%Y%m%dT%H%M%SZ).json
\end{lstlisting}

该工具调用和网页相同的 SSE 路由。若 worker
消失，它会保留``unavailable''观察，
不能把该次运行写成成功，也不能用配置中的全局上限代替板端结果。

\section{二次开发}\label{ux4e8cux6b21ux5f00ux53d1}

新模型不是通过任意请求参数注入路径或 Python 代码。教学模型通过受控
registry 和目录加入页面；正式发布模型仍需要独立锁文件。新模型需要实现
\passthrough{\lstinline!BackendProvider!} 协议，并提供：

\begin{itemize}
\tightlist
\item
  \passthrough{\lstinline!start()!}：加载已验证工件并初始化设备；
\item
  \passthrough{\lstinline!healthy!}：报告是否可以继续服务；
\item
  \passthrough{\lstinline!status()!}：返回不含密钥的运行状态；
\item
  \passthrough{\lstinline!stream()!}：为一次 greedy 请求产生累计文本与
  token 数；
\item
  \passthrough{\lstinline!close()!}：按确定顺序释放模型和设备资源。
\end{itemize}

为新模型建立固定 revision、文件大小、SHA-256、tokenizer、chat
template、许可证、目标 SoC 和运行时指纹。先完成本地 JSON/SSE
契约测试，再在每一种目标硬件上完成上述
NPU、稳定性、性能和人工质量门。技术门通过即可进入教学目录；质量结论必须原样保留。只有经过独立复核并人工批准的模型才能进入正式发布配置。

\section{小结}\label{ux5c0fux7ed3}

Ascend Edge Chat 将网页、鉴权网关和 NPU worker
分离，使文字聊天服务具备清晰的网络边界、模型完整性边界和二次开发边界。固定发布模型和严格工件校验提高了复现性；回环
worker、Bearer
网关和局域网安全提示降低了误配置风险。后续扩展应以实测硬件证据为准，而不是以目录中存在的历史实验、模型名称或文档推断为准。

\section{🎯
案例目标与问题定义}\label{ux6848ux4f8bux76eeux6807ux4e0eux95eeux9898ux5b9aux4e49}

传统电子相册只会按文件名或固定顺序轮播。Case7
要解决的是一个更完整的问题：照片由手机上传到局域网服务器，服务器在
Ascend 310B
上建立语义索引，再根据中文/英文查询、日期、天气和最近显示历史选择合适照片；同一份选择结果既服务开发板上的
10 寸触摸屏，也服务已登记的 ESP32 电子纸终端。本轮实测目标是新的
Waveshare ESP32-S3-PhotoPainter，Seeed Studio reTerminal E1002
只作为历史对照 profile。Orange Pi 的 SPI/GPIO 直连微雪 E6
是独立的本机输出路径，不是第三种可注册 ESP32 相册。

因此，Case7 不是单独的``图片分类脚本''，而是一条端到端链路：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{照片进入}：手机上传或扫描目录，经过内容
  hash、解码、尺寸和路径安全检查；
\item
  \textbf{照片理解}：NPU 图像编码器生成归一化 embedding，SQLite
  保存元数据，FAISS 保存逐模型检索结构；
\item
  \textbf{照片选择}：中文/英文文本查询、相似图查询和日期/天气智能选图使用相应模型空间；
\item
  \textbf{照片显示}：FastAPI 静态页面、JPEG 设备接口和 E6 dry-run
  使用同一个选择状态；
\item
  \textbf{设备协同}：ESP32 通过能力握手、manifest、ETag 和按需 content
  获取照片。
\end{enumerate}

生产服务只接受已准入的 Ascend OM，不回退 CPU/PyTorch 推理。CPU
负责图像解码、OpenCV Haar 人数计数、FAISS、JPEG/E6 准备和离线 ONNX
数值参考。

\section{🧠
多模型语义检索方法}\label{ux591aux6a21ux578bux8bedux4e49ux68c0ux7d22ux65b9ux6cd5}

\subsection{CLIP
的共同向量空间}\label{clip-ux7684ux5171ux540cux5411ux91cfux7a7aux95f4}

CLIP
使用图像编码器和文本编码器把两个模态投影到同一个向量空间。图像查询先编码成向量，文本查询也编码成向量，二者做
L2
归一化后使用内积近似余弦相似度。相似度高表示模型训练中认为图像和文本语义更接近。

Case7
不把三个模型的数值直接相加：不同训练数据、投影层和维度形成不同坐标空间。模型
ID 是索引隔离和 API 路由的边界。

\subsection{MobileCLIP-S0}\label{mobileclip-s0}

MobileCLIP-S0 面向英文和通用语义，图像输入固定为
\passthrough{\lstinline!1x3x256x256!}，文本输入固定为
\passthrough{\lstinline!1x77!}，输出 embedding 为 512
维。图像和文本组件分别导出 ONNX，再分别转换成 OM。

\begin{lstlisting}
flowchart LR
    accTitle: MobileCLIP 编码结构
    accDescr: MobileCLIP-S0 分别编码图像和英文文本，再投影到 512 维归一化空间进行检索

    image[📥 RGB 图像 256x256] --> image_encoder[🧠 MobileCLIP 图像编码器]
    text[📥 英文文本 77 tokens] --> text_encoder[🧠 MobileCLIP 文本编码器]
    image_encoder --> image_projection[⚙️ 图像投影层]
    text_encoder --> text_projection[⚙️ 文本投影层]
    image_projection --> image_vector[🏷️ 512 维 L2 归一化]
    text_projection --> text_vector[🏷️ 512 维 L2 归一化]
    image_vector --> similarity[🔍 FAISS 内积或余弦相似度]
    text_vector --> similarity
\end{lstlisting}

\passthrough{\lstinline!1x52!}，输出 embedding 为 1024 维。文本
tokenizer 使用 BERT 风格的
\passthrough{\lstinline!vocab.txt!}、\passthrough{\lstinline![CLS]!}、\passthrough{\lstinline![SEP]!}、\passthrough{\lstinline![PAD]!}
和 \passthrough{\lstinline![UNK]!} 合同；tokenizer
的物理行读取规则必须和固定上游实现一致。

\begin{lstlisting}

\section{🔧 昇腾 310B
模型迁移方法}\label{ux6607ux817e-310b-ux6a21ux578bux8fc1ux79fbux65b9ux6cd5}

模型迁移分为四个可审计阶段：

\begin{lstlisting}
checkpoint / tokenizer
        ↓ 离线导出
FP32 ONNX（固定 batch=1）
        ↓ 板端 ATC
Ascend310B4 mixed-FP16 OM
        ↓ PyACL / ACL
NPU embedding + FAISS 检索
\end{lstlisting}

导出阶段记录输入名称、shape、dtype、输出维度和 ONNX
SHA-256。转换阶段使用
\passthrough{\lstinline!--soc\_version Ascend310B4!} 和
\passthrough{\lstinline!--precision\_mode allow\_fp32\_to\_fp16!}。MobileCLIP
图像组件的当前生产 OM 已通过选择性精度扫描，使用 C0 的零节点 FP32
白名单；任何未来的例外仍必须写入 ATC 证据，而不能更换模型。

310B 板端内存有限，ATC
强制单线程：\passthrough{\lstinline!MAX\_COMPILE\_CORE\_NUMBER=1!}、\passthrough{\lstinline!TBE\_PARALLEL\_COMPILER=0!}、\passthrough{\lstinline!ASCENDC\_PAR\_COMPILE\_JOB=0!}、\passthrough{\lstinline!TILINGKEY\_PAR\_COMPILE=0!}、\passthrough{\lstinline!OMP\_NUM\_THREADS=1!}
和 \passthrough{\lstinline!OPENBLAS\_NUM\_THREADS=1!}。不添加 swap
或编译缓存，不开启并行图编译；转换器只在旧版确实提供该参数时选择
\passthrough{\lstinline!--enable\_graph\_parallel=0!}。CANN 8.x 的
\passthrough{\lstinline!--ac\_parallel\_enable!} 是动态 shape 执行阶段的
AI CPU/Core 并行选项，不等价于图编译开关，不能把它写成 ATC 并行门禁。

MobileCLIP 和 Chinese-CLIP 文本图目前登记为
\passthrough{\lstinline!int64!} 输入。这个类型是否能被目标 CANN 版本的
ONNX 到 ATC 链路接受，必须用板端最小文本图预检；若失败，应重新导出并验证
\passthrough{\lstinline!int32!} 合同，同时更新 tokenizer、ACL
输入检查、hash 和准入报告，而不是只改模型清单。

准入脚本先验证 ACL
初始化，再验证输入字节数、dtype、输出字节数、维度和有限值，最后比较 ONNX
与 OM 的归一化向量，余弦相似度门槛为
\passthrough{\lstinline!0.995!}。只有
\passthrough{\lstinline!models/registry.json!} 中 hash 一致且
\passthrough{\lstinline!status=admitted!} 的 OM 才会被服务加载。

\subsection{310B4/8T 与 310B1/20T 的跨板 OM
兼容性实验}\label{b48t-ux4e0e-310b120t-ux7684ux8de8ux677f-om-ux517cux5bb9ux6027ux5b9eux9a8c}

MobileCLIP 的 OM 不是脱离目标芯片的通用二进制。为了区分``ATC
转换成功''\,``本机 ACL 可执行''和``跨 SoC 可移植''，Case7
对图像、文本两个组件分别建立 8T/20T 对照矩阵：8T 使用
\passthrough{\lstinline!--soc\_version=Ascend310B4!} 重新转换，20T
使用已经生成的 \passthrough{\lstinline!--soc\_version=Ascend310B1!} OM
做原生复验，然后把两套 OM
在两块板上各运行一次。完整命令、版本原文、哈希和错误日志保存在
\passthrough{\lstinline!samples/case7/docs/12-mobileclip-cross-board-compatibility.md!}。

\begin{lstlisting}
flowchart LR
    onnx[锁定 MobileCLIP ONNX] --> atc8[8T ATC\nAscend310B4]
    onnx --> atc20[20T ATC/复用\nAscend310B1]
    atc8 --> om8[8T image/text OM]
    atc20 --> om20[20T image/text OM]
    om8 --> run8[8T ACL 原生]
    om8 --> run20[20T ACL 跨板]
    om20 --> run20n[20T ACL 原生]
    om20 --> run8x[8T ACL 跨板]
\end{lstlisting}

每个矩阵单元都重新检查 ACL 初始化、输入字节数和 dtype、512
维有限输出，以及与同一 ONNX 参考向量的归一化余弦
\passthrough{\lstinline!>= 0.995!}。\passthrough{\lstinline!load\_rejected!}、\passthrough{\lstinline!execute\_failed!}、\passthrough{\lstinline!output\_contract\_mismatch!}、\passthrough{\lstinline!numerical\_mismatch!}
和 \passthrough{\lstinline!non\_finite!} 必须保留原始错误，不能通过 CPU
fallback 或再次编译隐藏。原生通过而跨板失败，说明该 OM 在观测到的
SoC/运行栈组合下有兼容性边界；原生和跨板都通过，也只代表本次版本组合和
fixture，不代表所有 310B 型号通用。

本次实测使用 CANN
\passthrough{\lstinline!7.6.0.1.220:8.0.0!}、driver/npu-smi

\subsubsection{CANN、驱动、固件和目标 SoC
的关系}\label{cannux9a71ux52a8ux56faux4ef6ux548cux76eeux6807-soc-ux7684ux5173ux7cfb}

\passthrough{\lstinline!--soc\_version!} 决定 ATC 为哪一类 NPU
生成算子和执行计划；CANN Toolkit/ATC、板端 CANN Runtime/PyACL、驱动和

\passthrough{\lstinline!npu-smi info!} 软件版本均为
\passthrough{\lstinline!25.2.0!}，历史 CANN
\passthrough{\lstinline!8.3.0.1.200:8.3.RC1!} 批次出现 MobileCLIP 图像
ATC/ACL 异常，换为 CANN \passthrough{\lstinline!7.6.0.1.220:8.0.0!} 后

用户空间转换栈，但仍是版本对照相关性，不能冒充唯一因果证明。同时升级时遵循

\subsection{选择性 FP32/FP16
与误差定位}\label{ux9009ux62e9ux6027-fp32fp16-ux4e0eux8befux5deeux5b9aux4f4d}

\passthrough{\lstinline!allow\_fp32\_to\_fp16!}
是一种转换许可，不是``整张图强制 FP16''。图像浮点输入和 embedding
输出仍按 FP32 ONNX 合同处理；文本 token 输入是
\passthrough{\lstinline!int64!}。ATC 会在允许的节点上选择 FP16
实现，未被转换或被 \passthrough{\lstinline!keep\_dtype!}
白名单保护的节点仍可沿用 FP32。这个区别很重要：MobileCLIP
图像分支当前生产 OM 的组件级策略是
\passthrough{\lstinline!allow\_fp32\_to\_fp16!}，并已推广 C0 的零节点
FP32 白名单。推广前的
\passthrough{\lstinline!must\_keep\_origin\_dtype!} OM 及其
\passthrough{\lstinline!mobileclip\_s0\_image\_keep\_dtype.cfg!}
仅保留为 诊断和候选节点清单。MobileCLIP 文本、Chinese-CLIP 两个分支和
ResNet50 图像分支使用模型级
\passthrough{\lstinline!allow\_fp32\_to\_fp16!}。详细的命令、清单和证据字段见
\href{https://github.com/zhouxzh/Ascend310/blob/main/samples/case7/docs/08-model-pipeline-and-npu-admission.md}{\passthrough{\lstinline!docs/08-model-pipeline-and-npu-admission.md!}}。

\passthrough{\lstinline!network.4!} 的加法节点记录余弦
\passthrough{\lstinline!0.9994069!}，在

\passthrough{\lstinline!0.7932538!}；同一分组还出现 SE

\passthrough{\lstinline!0.7223154!}、主乘法
\passthrough{\lstinline!0.2903332!} 和 \passthrough{\lstinline!proj.1!}

\passthrough{\lstinline!network.5/proj/proj.1/activation/Mul\_1!} 为

\section{⚙️ NPU
运行时与串行资源管理}\label{npu-ux8fd0ux884cux65f6ux4e0eux4e32ux884cux8d44ux6e90ux7ba1ux7406}

\passthrough{\lstinline!embedding\_backend.py!} 用一个 ACL
资源管理器拥有 device、context、stream 和
model。\passthrough{\lstinline!ModelManager!} 按需加载图像/文本
OM；切换模型前释放旧
model，避免多个大模型同时占用内存。获取模型、构造输入、执行和释放由同一把锁保护。

服务的索引任务、ATC 转换和单次 embedding
都是串行的。这样牺牲并发换取可预测的 NPU
内存峰值和板端稳定性。CPU/PyTorch 不作为生产 fallback，因为 fallback
会掩盖 OM 缺失、ACL
初始化失败或模型合同错误；这些错误必须直接返回并写入健康状态。

\section{🌦️
智能选图与天气方法}\label{ux667aux80fdux9009ux56feux4e0eux5929ux6c14ux65b9ux6cd5}

候选照片必须可用且未删除。默认总分为：

\begin{lstlisting}
总分 = 0.60 * Chinese-CLIP 语义相似度
     + 0.25 * 日期、月份、星期和时段匹配
     + 0.15 * 天气与兼容元数据匹配
\end{lstlisting}

照片时间优先 EXIF
\passthrough{\lstinline!DateTimeOriginal!}，缺失时使用上传时间。天气默认来自
Open-Meteo；请求失败时保留最后有效状态。历史迁移照片若包含兼容
\passthrough{\lstinline!tags!}，可参与天气匹配；新上传照片不接受手工标签，缺少该元数据时该项得分为零。最近显示的
12 张照片进入重复抑制窗口，无匹配时回退到最新照片。

天气在后台按 \passthrough{\lstinline!weather.refresh\_seconds!}
更新；\passthrough{\lstinline!next!}、\passthrough{\lstinline!previous!}、图库点选和相似图查询复用已有天气状态，不主动访问天气服务。服务器在空闲调度周期中用已准入
Chinese-CLIP 文本编码器查询语义空间，并把 FAISS 排序后的照片 ID
放入易失的内存候选队列；手动 \passthrough{\lstinline!next!} 消费这份 NPU
语义计划，因此不是按文件名绕过模型。队列因天气、配置、图库变化而失效或耗尽时，下一次操作会在缓存天气下补做一次串行
NPU
排序。这样连续点击不会重复请求天气或反复加载模型，同时每个候选顺序仍由
NPU 语义分数参与决定。触摸屏自动选图默认每 60 秒执行，普通电脑网页每 30
秒轮询显示元数据；网页比较 ETag，未变化时不重新下载
JPEG。电子纸物理刷新使用独立的 30 分钟周期，也可明确设置为 10
分钟，暂停相册会暂停这些自动动作。

手动切图的控制请求和图像显示是两个阶段：前者提交 NPU 预选队列中的照片
ID（冷队列时先完成一次 NPU 文本推理和 FAISS
排序），浏览器随后按实际视口请求一次性 JPEG。高分辨率原图的 EXIF
旋转、缩放和 JPEG 编码通常比温热队列的选择状态更新更耗时；服务器使用
\passthrough{\lstinline!Image.draft!} 作为当前 JPEG
解码的尺寸提示，但不写入缩略图或其他派生缓存。首页不预加载整个图库，图库面板打开后才创建网格，网格图片使用浏览器懒加载和异步解码，避免原图请求与主屏渲染争用板端资源。

\passthrough{\lstinline!selection\_revision!}
在上传、天气变化、配置变化和轮播时隙到达时递增。每个 profile 的 current
photo、pause 状态和 history 写入 SQLite，重启后恢复而不是重新随机选择。

\subsection{ESP32 与 PhotoPainter}\label{esp32-ux4e0e-photopainter}

\passthrough{\lstinline!portrait!}；\href{https://wiki.seeedstudio.com/getting_started_with_reterminal_e1002/}{Seeed
Studio reTerminal E1002 官方 Wiki} 为 ACeP / Spectra 6 全彩
800x480，Case7 将它固定为
\passthrough{\lstinline!landscape!}。方向字段只允许
\passthrough{\lstinline!landscape!}、\passthrough{\lstinline!portrait!}，不支持

\passthrough{\lstinline!portrait!} 请求必须拒绝。Seeed

URL-only：不生成、不显示、也不要求设备令牌。服务设置私有、重新验证缓存语义和
\passthrough{\lstinline!Vary!}，不把真实文件路径暴露给设备。禁用设备返回
\passthrough{\lstinline!404!}；访问边界依赖可信局域网和服务器端设备启停状态，而不是旧固件令牌。

\subsection{从串口启动日志取得 PhotoPainter 的 IPv4
地址}\label{ux4eceux4e32ux53e3ux542fux52a8ux65e5ux5fd7ux53d6ux5f97-photopainter-ux7684-ipv4-ux5730ux5740}

设备网页地址由路由器 DHCP 分配，不能从设备名称、MAC
或旧的租约记录推断。实际操作时只连接当前
PhotoPainter，打开串口监视器并按一次 \passthrough{\lstinline!BOOT/KEY!}
唤醒，再按复位键观察完整启动过程：

\begin{lstlisting}
$idfPython = 'C:\Espressif\tools\python\v6.0.2\venv\Scripts\python.exe'
& $idfPython -m serial.tools.miniterm COM17 115200
\end{lstlisting}

日志中出现
\passthrough{\lstinline!No WiFi credentials found - Starting AP mode!}
表示设备还在临时配网 AP；连接形如
\passthrough{\lstinline!PhotoFrame - XXXXX!} 的 2.4 GHz AP
后配置家庭网络。配网成功必须同时看到
\passthrough{\lstinline!sta ip: ...!}、
\passthrough{\lstinline!HTTP server started!} 和
\passthrough{\lstinline!Web interface available at: http://...!}。本次新微雪设备的证据是：

\begin{lstlisting}
profile: waveshare_photopainter_73
serial: COM17
firmware: esp32-photoframe v2.18.0
sta ip: 192.168.1.137
web: http://192.168.1.137/
\end{lstlisting}

在同一局域网电脑上用这个 IPv4 地址验证，而不是登录
\passthrough{\lstinline!photoframe.local!}：

\begin{lstlisting}
$photoIp = '192.168.1.137'
curl.exe --noproxy "*" "http://$photoIp/api/system-info"
curl.exe --noproxy "*" -I "http://$photoIp/"
\end{lstlisting}

\passthrough{\lstinline!photoframe.local!} 只是可选 mDNS
别名，Windows、VPN 或路由器不支持解析时仍属正常；它不是账号、
密码或必须的登录入口。\passthrough{\lstinline!192.168.1.135:7860!} 是
310B 相册服务器，\passthrough{\lstinline!192.168.1.117!} 是旧 E1002
记录，均不能代替当前串口日志中的地址。每次重启、换路由器或重新配网后都要重新读取
\passthrough{\lstinline!sta ip!}。 完整的端口枚举、日志保存、DHCP
变化和故障排查步骤见仓库中的
\href{https://github.com/zhouxzh/Ascend310/blob/main/samples/case7/docs/13-photopainter-serial-ip-and-wifi.md}{PhotoPainter
串口读取 IP 与 Wi-Fi 配网手册}。

\subsection{横竖屏图像方向}\label{ux6a2aux7ad6ux5c4fux56feux50cfux65b9ux5411}

照片显示先执行 EXIF Orientation 校正，再应用设备 profile 的
\passthrough{\lstinline!orientation!}（\passthrough{\lstinline!landscape!}
或 \passthrough{\lstinline!portrait!}）。默认
\passthrough{\lstinline!orientation\_mode=auto!}
保持照片本身的横竖构图，只将其按 \passthrough{\lstinline!cover!} 或
\passthrough{\lstinline!fit!} 放进目标画布；这是人像
照片的安全默认值。需要让最终编码帧严格匹配显示器横竖方向时，可启用
\passthrough{\lstinline!orientation\_mode=match\_display!}，服务会按
profile 选择 \passthrough{\lstinline!landscape!} 或
\passthrough{\lstinline!portrait!} 目标；E1002 的
\passthrough{\lstinline!portrait!}
请求直接拒绝，不通过隐式交换宽高放行。

设备可用 \passthrough{\lstinline!X-Display-Width!} 和
\passthrough{\lstinline!X-Display-Height!} 在\textbf{其已登记 profile
允许范围内}协商当前能力： 只有 PhotoPainter 可以使用
\passthrough{\lstinline!480x800!} 竖屏，E1002
的这类请求会拒绝；不可沿用旧的方向标签。JPEG 响应中的
\passthrough{\lstinline!X-Album-Orientation!} 是实际像素方向，
\passthrough{\lstinline!X-Album-Target-Orientation!}
是目标显示方向，因此 \passthrough{\lstinline!auto!}
模式下两者可以不同。尺寸、方向模式和安装 方向都会进入 JPEG 的
ETag。触摸屏 \passthrough{\lstinline!display.*!} 与 E6
\passthrough{\lstinline!epaper.*!} 的方向设置相互独立；E6 仍是固定
\passthrough{\lstinline!800x480!}、192000-byte
线协议，天气刷新或触摸屏方向变化不会让同一 E6 图帧失效并触发额外刷新。

\section{🎨
触摸屏交互设计}\label{ux89e6ux6478ux5c4fux4ea4ux4e92ux8bbeux8ba1}

触摸屏首页把照片作为第一视觉层，天气卡片和状态信息使用高对比度实体背景。五个首页动作收拢为一个紧凑工具栏；文件名作为同一工具栏内的非交互文本，设置页有``显示文件名水印''开关。8
秒无操作时工具栏和文件名一起淡出，触摸照片唤醒。

底部导航打开图库、智能搜索、上传、设备和设置五个全屏面板。按钮最小高度为
56px，图片网格固定宽高比；1920x1080、1280x800、1024x600 和 400x900
视口均禁止页面横向滚动。

\section{🖨️ E6
图像处理方法}\label{e6-ux56feux50cfux5904ux7406ux65b9ux6cd5}

\passthrough{\lstinline!epaper\_display.py!} 在 CPU 上执行：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  读取 EXIF 方向并旋转；
\item
  将图像居中裁剪到 800x480；
\item
  量化到 E6 六色调色板；
\item
  使用官方稀疏颜色编号：黑 0、白 1、黄 2、红 3、保留黑 4、蓝 5、绿 6；
\item
  两个像素按高半字节优先打包，输出
  \passthrough{\lstinline!800*480/2 = 192000!} bytes；
\item
  dry-run 验证初始化、刷新、BUSY 和休眠命令序列。
\end{enumerate}

真实硬件模式必须显式提供 SPI 设备、gpiochip 和 DC/RST/BUSY line
offset。当前驱动板型号和接线尚未确认，PNG/帧 dry-run
只能证明协议编码，不能宣称微雪实屏刷新通过。PhotoPainter
六色路径同样不能由 E6 六色帧结果替代。

\section{🧪
测试、性能与验收方法}\label{ux6d4bux8bd5ux6027ux80fdux4e0eux9a8cux6536ux65b9ux6cd5}

测试把不同证据分开：

\begin{itemize}
\tightlist
\item
  单元测试覆盖模型合同、ACL 模拟、索引隔离、上传安全、配置
  revision、显示历史、设备握手/ETag 和 E6 帧；
\item
  模型准入覆盖 ONNX 合同、ATC 日志、OM hash、ACL 数值和有限值；
\item
  COCO-CN 检索覆盖 20 条中文和 20 条英文查询，Recall@3 门槛均为 80\%；
\item
  性能使用单线程、20 次预热、100 次计时、3
  轮重复，报告图像/文本编码、FAISS 和 API P50/P95；
\item
  UI 验收覆盖 1920x1080、1280x800、1024x600 和
  400x900，无横向滚动、控件重叠或文字溢出；
\item
  E6 dry-run 覆盖 EXIF、裁剪、六色、颜色编号、192000 bytes、BUSY
  超时和无 GPIO 拒绝。
\end{itemize}

历史 310B4/8T 报告曾记录 COCO-CN 英文 MobileCLIP Recall@1/3/5 =
\passthrough{\lstinline!0.90/1.00/1.00!}、中文 Chinese-CLIP =
\passthrough{\lstinline!0.80/0.95/1.00!}，以及 MobileCLIP 图像编码
P50/P95 \passthrough{\lstinline!55.898/56.106 ms!}、 Chinese-CLIP
文本编码 \passthrough{\lstinline!11.988/12.048 ms!}、FAISS 搜索
\passthrough{\lstinline!0.413/0.449 ms!}。这些数字属于历史
证据，不能移植到其他板卡。当前验收目标是
\passthrough{\lstinline!192.168.8.180!}；其 2026-08-27 复核报告显示 500
张 COCO-CN 图片已建立三个模型的各 500 个 embedding，英文 Recall@1/3/5 为
\passthrough{\lstinline!0.90/1.00/1.00!}， 中文为
\passthrough{\lstinline!0.80/0.95/1.00!}，三个模型均为
\passthrough{\lstinline!admitted!}。当前板端性能和模型 hash 以
\passthrough{\lstinline!reports/benchmarks/coco\_cn\_case7\_performance\_20260827\_newboard.json!}、
\passthrough{\lstinline!reports/datasets/coco\_cn\_case7\_retrieval\_20260827\_newboard.json!}

\passthrough{\lstinline!reports/model\_pipeline/board-20260827/acl\_numerical\_validation.json!}

\passthrough{\lstinline!reports/display-restart-recovery-20260827.json!}（SHA-256

\section{⚠️
限制、许可证与后续工作}\label{ux9650ux5236ux8bb8ux53efux8bc1ux4e0eux540eux7eedux5de5ux4f5c}

\begin{itemize}
\tightlist
\item
  MobileCLIP 使用 Apple Machine Learning Research Model
  License，按清单中的非商业研究/教育边界使用；Chinese-CLIP
  代码和权重许可应以固定上游仓库为准；ResNet50 使用 torchvision/ImageNet
  研究教育资产。
\item
  COCO-CN 是唯一公开测试集；图像来源于 COCO-CN/MS-COCO，使用时必须保留
  manifest 的来源和许可证字段。
\item
  Open-Meteo 是默认天气服务，网络失败时只能使用最后有效状态。
\item
  PhotoPainter 使用上游 \passthrough{\lstinline!v2.18.0!} 固件；Case7
  不维护自定义 ESP32 固件分支。
\item
  服务无管理员登录，只适合可信局域网，禁止公网暴露。
\item
  微雪 E6 驱动板型号和 GPIO/SPI
  接线尚未确认，真实实屏刷新是独立后续验收。
\item
  通用 ESP-IDF 客户端需要具体 ESP32
  变体、显示控制器、总线、GPIO、电源、Flash/PSRAM 和 IDF
  版本后才能安全实现；当前先使用 HTTP 协议和上游 PhotoFrame。
\end{itemize}

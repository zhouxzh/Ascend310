\section{7.1 性能优化先从可测量开始}\label{src-book-chapter7-h1}

\section{7.4 案例一：建立同步推理基线}\label{src-book-chapter7-h9}

先运行基线：

\begin{lstlisting}[language=bash]
python3 01_baseline_resnet_sync.py --runs 100
\end{lstlisting}

这个脚本故意采用低效写法：每一帧都申请 Device 输入输出内存、创建
Dataset、执行推理、复制输出、释放资源。它的价值不是快，而是让问题暴露出来。

核心流程如下：

\begin{lstlisting}[language=Python]
input_ptr = acl.rt.malloc(input_size, ACL_MEM_MALLOC_HUGE_FIRST)
output_ptr = acl.rt.malloc(output_size, ACL_MEM_MALLOC_HUGE_FIRST)
input_dataset = acl.mdl.create_dataset()
output_dataset = acl.mdl.create_dataset()
acl.rt.memcpy(input_ptr, input_size, host_ptr, input_size, ACL_MEMCPY_HOST_TO_DEVICE)
acl.mdl.execute(model_id, input_dataset, output_dataset)
acl.rt.memcpy(host_out, output_size, output_ptr, output_size, ACL_MEMCPY_DEVICE_TO_HOST)
\end{lstlisting}

基线需要记录以下阶段：

{ % do not increment counter
\begin{longtable}[]{@{}ll@{}}
\toprule\noalign{}
阶段 & 含义 \\
\midrule\noalign{}
\endhead
\bottomrule\noalign{}
\endlastfoot
\passthrough{\lstinline!preprocess!} & RGB 输入转换为 NCHW float32 \\
\passthrough{\lstinline!alloc\_dataset!} & 申请输入输出 Buffer 并创建
Dataset \\
\passthrough{\lstinline!h2d!} & Host 输入复制到 Device \\
\passthrough{\lstinline!execute!} & 模型执行 \\
\passthrough{\lstinline!d2h!} & Device 输出复制回 Host \\
\passthrough{\lstinline!free\_dataset!} & 销毁 Dataset 并释放 Buffer \\
\passthrough{\lstinline!postprocess!} & \passthrough{\lstinline!argmax!}
等轻量后处理 \\
\passthrough{\lstinline!end\_to\_end!} & 单帧端到端耗时 \\
\end{longtable}
}

如果 \passthrough{\lstinline!alloc\_dataset!} 和
\passthrough{\lstinline!free\_dataset!}
占比明显，说明优化方向不是模型，而是资源生命周期。

\section{7.5 案例二：复用 ACL Buffer 和
Dataset}\label{src-book-chapter7-h10}

推理服务通常会长时间运行，输入输出张量大小也是固定的。因此更合理的做法是在模型加载后一次性创建输入输出
Buffer 和 Dataset，在每帧循环里只做数据拷贝和执行：

\begin{lstlisting}[language=bash]
python3 02_buffer_reuse_benchmark.py --runs 100
\end{lstlisting}

优化后的流程：

\begin{lstlisting}
初始化阶段：load model -> create dataset -> malloc input/output buffer
循环阶段：H2D -> execute -> D2H -> postprocess
退出阶段：destroy dataset -> free buffer -> unload model
\end{lstlisting}

这项优化的判断标准很直接：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \passthrough{\lstinline!alloc\_dataset!} 和
  \passthrough{\lstinline!free\_dataset!} 从每帧计时中消失。
\item
  \passthrough{\lstinline!end\_to\_end!} 平均耗时下降。
\item
  \passthrough{\lstinline!msprof!} Timeline 中 Host 侧 ACL Runtime
  调用密度更高，计算任务之间的空白减少。
\end{enumerate}

如果模型很小，Buffer
复用的收益会特别明显；如果模型本身很大，收益占比会下降，但仍然能减少长尾抖动。

\section{7.6 案例三：CPU
预处理为什么容易成为瓶颈}\label{src-book-chapter7-h11}

很多边缘视觉应用在 NPU 推理前会做 resize、颜色转换、归一化和 HWC 到 CHW
转换。脚本 \passthrough{\lstinline!03\_cpu\_preprocess\_benchmark.py!}
用确定性 RGB 图像模拟 1080p 摄像头帧：

\begin{lstlisting}[language=bash]
python3 03_cpu_preprocess_benchmark.py --runs 100 --resolution 1920x1080
\end{lstlisting}

如果想观察更稳定的统计结果，可以在确认本机内存充足后把
\passthrough{\lstinline!--runs!} 增加到 500 或 1000。

脚本比较两种方式：

{ % do not increment counter
\begin{longtable}[]{@{}ll@{}}
\toprule\noalign{}
方式 & 特点 \\
\midrule\noalign{}
\endhead
\bottomrule\noalign{}
\endlastfoot
\passthrough{\lstinline!naive\_numpy!} & 每帧创建 resize、float32、NCHW
等中间数组 \\
\passthrough{\lstinline!workspace\_reuse!} &
预先创建工作区，循环中复用数组 \\
\end{longtable}
}

这个案例的学习重点不是把 CPU 预处理调到极致，而是理解何时应该停止优化
CPU。若预处理耗时已经接近或超过模型执行耗时，应优先考虑：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  使用 DVPP VPC 做 resize/crop。
\item
  使用 AIPP 做归一化和部分颜色格式处理。
\item
  使用视频链路时，让 VDEC/JPEGD 的输出直接衔接 VPC 或模型输入。
\end{enumerate}

\section{7.7 案例四：DVPP VPC resize 与 CPU
resize}\label{src-book-chapter7-h12}

脚本 \passthrough{\lstinline!04\_dvpp\_resize\_vs\_cpu.py!} 生成 NV12
测试帧，将 1080p 图像缩小到 540p，对比 CPU resize 和 DVPP VPC resize：

\begin{lstlisting}[language=bash]
python3 04_dvpp_resize_vs_cpu.py --frames 60 --resolution 1920x1080
\end{lstlisting}

该脚本包含 H2D、VPC resize、同步和
D2H，因此测到的是一个完整调用成本，而不是 VPC 内核的裸耗时。如果 DVPP
仍然明显领先 CPU，说明把 resize 从 Host
下沉到设备侧很有价值。如果差距不明显，要继续检查：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  输入尺寸是否太小，导致调用开销大于计算收益。
\item
  是否每帧都重复创建 DVPP Channel、Stream 或配置对象。
\item
  是否存在多余的 H2D/D2H 拷贝。
\end{enumerate}

\section{7.8 案例五：AIPP
把归一化下沉到模型输入侧}\label{src-book-chapter7-h13}

前面的基线脚本使用 CPU 完成 resize、归一化和 HWC 到 CHW 转换，然后把
\passthrough{\lstinline!float32 NCHW!} 输入拷贝到 Device。AIPP
的思路不同：让模型接收 \passthrough{\lstinline!RGB888\_U8!}
图像，在模型输入侧完成均值、方差等处理。这样可以减少 Host CPU
的像素遍历，也能减少输入拷贝字节数。

本章提供静态 AIPP 配置：

\begin{lstlisting}
model/resnet18_rgb_static_aipp.cfg
\end{lstlisting}

先下载本章模型资产：

\begin{lstlisting}[language=bash]
python3 tools/download_model.py --all
\end{lstlisting}

\passthrough{\lstinline!--all!} 会把普通 OM、ONNX、AIPP OM 和 AIPP
配置都下载到 \passthrough{\lstinline!model/!}。如果 Hugging Face
仓库中已经有
\passthrough{\lstinline!model/resnet18\_tiny\_imagenet\_aipp.om!}，可以直接运行后面的对比脚本，不必自己转换。

如果需要在板端重新生成 AIPP OM，再运行独立 shell 脚本：

\begin{lstlisting}[language=bash]
bash tools/convert_aipp_resnet18.sh
\end{lstlisting}

脚本默认生成
\passthrough{\lstinline!model/resnet18\_tiny\_imagenet\_aipp.om!}。转换或下载完成后，再运行
Python 对比脚本：

\begin{lstlisting}[language=bash]
python3 06_aipp_preprocess_compare.py --runs 100
\end{lstlisting}

这里故意把 ATC 转换和 Python 推理对比分成两步。ATC
是离线模型转换，可能耗时较长，也可能受板端内存和 CANN 环境影响；Python
脚本只加载已有 OM 做性能测试，不会在测试过程中调用 ATC。

对比脚本会执行两条路径：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  使用原始 OM 跑
  \passthrough{\lstinline!CPU preprocess -> H2D -> execute -> D2H -> argmax!}。
\item
  使用 AIPP OM 跑
  \passthrough{\lstinline!RGB888\_U8 prepare -> H2D -> AIPP+execute -> D2H -> argmax!}，并比较输出差异。
\end{enumerate}

需要注意，AIPP OM 的输入不再是
\passthrough{\lstinline!float32 NCHW!}，而是
\passthrough{\lstinline!uint8 HWC RGB!}。因此不能直接拿
\passthrough{\lstinline!01\_baseline\_resnet\_sync.py!} 去跑 AIPP
OM，必须使用本节的对比脚本或在自己的程序中按 AIPP 配置准备输入。

对外部读者来说，还有两个容易踩坑的地方：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  运行转换脚本前，需要先完成 CANN 环境配置，并确认当前终端可以直接使用
  \passthrough{\lstinline!atc!}。
\item
  CANN 8.3 对 \passthrough{\lstinline!RGB888\_U8!} 的
  \passthrough{\lstinline!mean\_chn\_*!} 字段按整数解析，不能直接写
  \passthrough{\lstinline!123.675!} 这样的浮点均值。本章配置使用
  \passthrough{\lstinline!mean\_chn\_*: 0!} 加浮点
  \passthrough{\lstinline!min\_chn\_*!} 表达 ImageNet 均值，并用
  \passthrough{\lstinline!var\_reci\_chn\_*!} 表达
  \passthrough{\lstinline!1 / (255 * std)!}。
\end{enumerate}

ATC
是离线转换步骤，第一次编译可能明显慢于普通推理脚本。如果转换耗时异常，应先检查板端负载、可用内存、CANN
日志和 AIPP 配置，再重新运行转换脚本。

\section{7.9 案例六：串行流程与 Queue
Pipeline}\label{src-book-chapter7-h14}

串行流程的单帧耗时为：

\begin{lstlisting}
T = T_pre + T_infer + T_post
\end{lstlisting}

三段流水线稳定后的吞吐上限更接近：

\begin{lstlisting}
FPS = 1000 / max(T_pre, T_infer, T_post)
\end{lstlisting}

先在本地使用模拟模式理解这个关系：

\begin{lstlisting}[language=bash]
python3 05_pipeline_queue_demo.py --simulate --frames 200
\end{lstlisting}

再在 Ascend 310B 上使用 PyACL 模式：

\begin{lstlisting}[language=bash]
python3 05_pipeline_queue_demo.py --frames 100
\end{lstlisting}

流水线优化的目标不是降低单帧端到端延迟，而是提高稳态吞吐。它会引入队列等待，因此
p95 latency 可能上升；如果业务目标是交互式低延迟，需要谨慎扩大队列深度。

从这组数据可以得到五个结论：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Buffer 复用是确定有效的优化。ResNet18 端到端平均耗时从 4.6047 ms 降到
  3.2072 ms，提升约 1.436 倍。
\item
  CPU 预处理里的中间数组分配值得优化。复用工作区后，预处理平均耗时从
  0.62 ms 降到 0.3583 ms。
\item
  DVPP 不是简单替换 API 就一定更快。本章脚本为了教学完整性包含每帧
  \passthrough{\lstinline!dvpp\_malloc/free!}、H2D 和 D2H，结果 DVPP VPC
  resize 平均 3.5966 ms，慢于 CPU resize 的 2.6013
  ms。真实视频流水线应复用 DVPP 资源，并尽量让 VDEC/JPEGD/VPC
  输出继续留在设备侧。
\item
  AIPP 在本章模型上有明确收益。原始 OM 的 CPU 预处理路径平均耗时为
  3.2319 ms，AIPP OM 的 \passthrough{\lstinline!RGB888\_U8!}
  输入路径降到 2.6076 ms，提升约 1.239 倍；100 次测试中 top1 匹配率为
  1.0，最大单点输出差异为 0.007812。AIPP
  改变了模型输入格式，正确的比较对象不是``同一个 OM 换输入''，而是原始
  OM 的 CPU 预处理路径与 AIPP OM 的 \passthrough{\lstinline!RGB888\_U8!}
  输入路径。
\item
  Pipeline 需要足够重的阶段才有收益。模拟场景中队列流水线从 65.8947 FPS
  提升到 123.1021 FPS；但 ResNet18 小模型的 PyACL
  场景中，队列和线程上下文开销使 FPS 从 313.0536 降到 250.4402，且 p95
  latency 明显变差。
\end{enumerate}

\section{7.13 小结}\label{src-book-chapter7-h18}

Ascend 310B
性能优化的核心是先定位瓶颈，再把瓶颈映射到合适的硬件或软件策略。小模型场景中，内存申请、同步和
Host 预处理往往比模型执行更值得关注；视频场景中，DVPP、AIPP
和流水线调度决定了端到端吞吐。调优的最终依据不是经验判断，而是可复现的指标、Timeline
和对比报告。

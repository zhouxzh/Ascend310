Ascend 310B 芯片内置了 \textbf{DVPP（Digital Vision Pre-Processing）}
硬件加速引擎，提供视频编解码（VENC/VDEC）、图像处理（VPC）和 JPEG
编解码能力。本章从基础概念出发，逐步深入到各子模块的 API
使用、性能调优和实战集成。

\section{DVPP 基础概念与编程模型}\label{dvpp-basics}

DVPP（Digital Vision Pre-Processing）是 Ascend
芯片内部的一组\textbf{硬件加速模块}，专门处理图像和视频数据。它独立于
NPU 的 AI Core（推理引擎），不占用 AI 算力。PyACL 通过
\passthrough{\lstinline!acl.media!} 接口对外暴露这些能力。

\begin{quote}
本节覆盖所有 DVPP
子模块（VENC、VDEC、VPC、JPEGE、JPEGD）共享的基础概念。初次接触 DVPP
时，建议先阅读本节，再进入具体子模块的内容。
\end{quote}

\subsection{DVPP 在芯片中的位置}\label{src-book-chapter5-h1}

Ascend 310B4 可从应用开发视角理解为以下几类片上资源：

\begin{itemize}
\tightlist
\item
  \textbf{AI Core × 1}: DaVinci V300（矩阵运算，NPU 推理主力）
\item
  \textbf{片上 CPU × 4}: 4 个 64 位 ARMv8-A
  通用处理核。\passthrough{\lstinline!npu-smi!} 可按 AI CPU / control
  CPU / data CPU 查询和配置数量，默认配比为
  \passthrough{\lstinline!1:3:0!}；这是启动配置，修改后需要复位生效，不是运行时动态划分
\item
  \textbf{DVPP}: 独立视觉/媒体处理硬件单元（独立于 AI Core，也不是
  CPU/AICPU 上的软件模块）

  \begin{itemize}
  \tightlist
  \item
    VENC: 视频编码
  \item
    VDEC: 视频解码
  \item
    VPC: 图像处理（resize/crop/csc）
  \item
    JPEGE: JPEG 编码
  \item
    JPEGD: JPEG 解码
  \end{itemize}
\item
  \textbf{设备内存与内部总线}: AI Core、DVPP 与片上 CPU
  通过设备内存和内部总线交换数据
\end{itemize}

\textbf{关键要点}：DVPP 与 AI Core 是芯片上两个独立的硬件域。DVPP 编码
1080p 视频与 AI Core 执行 YOLO
推理可以并行运行，二者不竞争同一计算单元；CPU
侧主要负责内存、描述符和任务下发，不执行像素级编解码计算。

\subsection{DVPP 数据流}\label{src-book-chapter5-h2}

DVPP 接收来自 \textbf{DDR 内存} 的数据，处理后写回 DDR。CPU
侧的工作是准备输入描述符、下发任务、等待回调或 Stream
同步完成------不参与实际像素级处理。

数据流五步：(1) CPU 侧分配设备内存并拷贝数据到设备 -\textgreater{} (2)
DVPP 硬件通过内部总线读取 -\textgreater{} (3) 处理后将结果写入输出缓冲区
-\textgreater{} (4) DVPP 通过回调或 Stream 完成事件通知 CPU 侧
-\textgreater{} (5) CPU 侧按需从设备内存拷回结果。

\textbf{核心机制}：DVPP 直接访问 DDR，不经过 CPU
执行像素级处理。这是它能比 CPU 软件处理快得多的根本原因。

\subsection{AIPP vs DVPP（何时用哪个）}\label{src-book-chapter5-h3}

PyACL 的媒体处理分两类能力：

\begin{itemize}
\tightlist
\item
  \textbf{DVPP}：适合执行``低级别''的高吞吐预处理------JPEG/视频解码、YUV
  与 RGB 转换、缩放、裁剪等。优点是速度快、CPU
  负载低，但受格式与对齐约束。
\item
  \textbf{AIPP}（Artificial Intelligence
  Pre-Processing）：适合执行``模型输入级''的精确预处理------统一色域/像素变换、量化/去均值、通道顺序等。AIPP
  分静态（在模型转换时固化到 .om）与动态（运行时通过接口设置）两种模式。
\end{itemize}

\textbf{常见组合}：先用 DVPP 完成解码与粗略 resize/crop，再用
AIPP（静态或动态）做最后的色域和像素级处理，保证与模型输入要求一致。

\subsection{H.264 与 H.265 编解码基础}\label{h264-h265-basics}

VENC 和 VDEC 都围绕 H.264/H.265 工作。理解这些编码标准的基本概念，是使用
DVPP 编解码模块的前提。

\textbf{什么是 H.264}

H.264（也叫
AVC）是目前全球使用最广泛的视频编码标准。核心思想是去除视频中的冗余：空间冗余通过帧内预测消除，时间冗余通过帧间预测消除，统计冗余通过熵编码消除。

单元组成（SPS、PPS、IDR Slice、Non-IDR Slice、SEI）。Annex-B
格式用起始码 \passthrough{\lstinline!0x00000001!} 分隔每个 NAL
单元。VDEC 要求输入必须是 Annex-B 格式。

\subsection{ACL 初始化------四步必要步骤}\label{acl-init}

任何使用 DVPP 的 Python
进程，都必须在开头执行这四个调用，顺序固定不可变：

\begin{lstlisting}[language=Python]
import acl

ret = acl.init()                    # (1) 初始化 ACL 运行时
ret = acl.rt.set_device(0)          # (2) 选择 NPU 设备 0
ctx, ret = acl.rt.create_context(0) # (3) 在设备上创建执行上下文
ret = acl.rt.set_context(ctx)       # (4) 将上下文绑定到当前线程
\end{lstlisting}

\textbf{为什么需要 context}：ACL 的
context（上下文）是\textbf{线程局部}的。每个需要调用 ACL API
的线程都必须绑定自己的 context。回调线程里必须再调一遍
\passthrough{\lstinline!set\_context(ctx)!}------主线程的 context
不会自动传递到回调线程。

\textbf{多线程规则}：一个设备可以创建多个 context，但一个 context
同时只能绑定一个线程，一个线程同时只能绑定一个 context。同一个 context
可以在不同时间绑定到不同线程（但不能同时）。

\subsection{通道模型}\label{channel-model}

VENC 和 VDEC 都采用\textbf{通道（Channel）}模型。通道是 DVPP
硬件资源的抽象------创建一个通道就是向驱动申请一个硬件编码器/解码器实例。

通道创建遵循``描述符 -\textgreater{}
通道''两步模式：先创建通道描述符并设置参数，再调用 create\_channel
申请硬件资源。描述符只是一组参数配置，create 时才真正向驱动申请资源。

\textbf{通道复用 vs 创建/销毁}：每次
\passthrough{\lstinline!创建通道() -> 处理 N 帧 -> 销毁通道()!}
的固定开销约
\textbf{5-10ms}。对于单帧编码场景，创建/销毁的开销远超编解码本身。最佳实践：创建一次通道，连续处理所有帧，最后销毁。

\textbf{通道数是有限的}：Ascend 310B4 的 VENC/VDEC
硬件实例数量有限（通常每种 1-2 个）。

\subsection{回调线程模型}\label{callback-thread-model}

DVPP
是\textbf{异步}的：发送工作请求后立即返回，结果通过\textbf{回调}在另一个线程中返回。

异步处理时序：(1) 主线程发送帧请求后立即返回 -\textgreater{} (2)
主线程阻塞在 \passthrough{\lstinline!Queue.get()!} 等待结果
-\textgreater{} (3) DVPP 硬件完成处理 -\textgreater{} (4)
回调线程收到事件 -\textgreater{} (5) 回调将结果
\passthrough{\lstinline!Queue.put()!} -\textgreater{} (6)
主线程被唤醒得到结果

天然适合``生产者（回调线程）-\textgreater{}
消费者（主线程）''模式------支持缓冲（多帧排队）、阻塞等待（\passthrough{\lstinline!Queue.get(timeout=5.0)!}）、线程安全（无需额外锁）。

\textbf{为什么是
300ms}：\passthrough{\lstinline!process\_report(300ms)!} 阻塞最多 300ms
等待 DVPP 硬件完成通知。太短（如 10ms）会高频 CPU 轮询，太长（如
5000ms）会导致销毁通道时等待过久。300ms 是平衡值。

\subsection{NV12------DVPP 的通用货币}\label{nv12-format}

NV12（也叫 YUV420SP）是 DVPP 所有图像相关模块的首选像素格式。

\textbf{为什么 NV12}：(1) 体积小------每像素 1.5 字节（RGB 是 3
字节），省 50\% 内存和带宽；(2)
人眼匹配------利用人对亮度敏感、对色度不敏感的特性，降低色度分辨率；(3)
硬件原生------VENC/VDEC 硬件内部直接处理 NV12；(4)
摄像头兼容------大多数摄像头输出 YUV 格式，接近 NV12。

\textbf{内存布局}：NV12 缓冲区 = {[}Y 平面{]}（H×W，每像素 1 字节亮度）+
{[}UV 交错平面{]}（H/2 × W，每 2 字节一组 U,V）。总字节数 = H × W ×
3/2。

\textbf{与其他 YUV 格式的区别}：

\subsection{理论背景}\label{src-book-chapter5-h9}

\subsubsection{为什么需要硬件编码}\label{src-book-chapter5-h10}

H.264 视频编码是计算密集型任务。一块 640×480@30fps 的视频流，纯 CPU
软件编码（如 libx264）会占用 ARM Cortex-A55 的大量计算资源。对于 Orange
Pi AI Pro 这样的嵌入式设备，CPU
资源有限，软件编码不仅影响视频质量（可能因算力不足而降低帧率），还挤占了其他任务的
CPU 时间。

昇腾 310B 芯片内部集成了 \textbf{VENC（Video Encoder）} 硬件模块，专用于
H.264/H.265 编码。硬件编码器具有：

\begin{itemize}
\tightlist
\item
  \textbf{固定功能电路}：编码路径完全硬化，功耗和延迟远低于通用 CPU
\item
  \textbf{独立于 AI Core}：不占用 NPU 推理算力
\item
  \textbf{实时性保证}：硬件 pipeline 确保编码在固定时间内完成
\end{itemize}

\passthrough{\lstinline!<toolkit>/python/site-packages!}，\textbf{不是}
\passthrough{\lstinline!<toolkit>/aarch64-linux/python/site-packages!}。\passthrough{\lstinline!aarch64-linux/!}

\textbf{是否在代码中修复？}
示例脚本遵循``环境变量在进程外设置''的原则，不内置

\subsubsection{问题 \#3：venc\_create\_channel 返回 507018 --- bitrate

\textbf{现象}：

\begin{lstlisting}
RuntimeError: venc_create_channel failed: 507018 (0x7bc8a)

我传入了 \passthrough{\lstinline!2\_000\_000!}（2 Mbps 以 bps 表示），被

\textbf{修复}：

\begin{lstlisting}[language=Python]

# 正确
media.venc_set_channel_desc_max_bit_rate(desc, 2_000)       # kbps = 2 Mbps
\end{lstlisting}

\textbf{dmesg 调试技巧}：VENC

\subsubsection{问题 \#4：venc\_create\_channel 返回 507018 --- GOP 为
0}\label{src-book-chapter5-h28}

\textbf{现象}：

\begin{lstlisting}
dmesg: rc_check_com_attr gop 0 err, should be in [1 65536]
dmesg: rc_create_chn check user rc attr err
\end{lstlisting}

\textbf{根因}：\passthrough{\lstinline!key\_frame\_interval!}（即 GOP
--- Group of Pictures）未设置，默认值为 0，不在合法范围 {[}1, 65536{]}
内。

GOP 控制多少个 P/B 帧之间插入一个 I 帧（关键帧）。GOP=30 意味着每 30
帧一个 I 帧，这在 30fps 下相当于每秒一个关键帧。GOP=0
对编码器没有意义（永远不产生 I 帧？），因此被拒绝。

\textbf{修复}：

\begin{lstlisting}[language=Python]
media.venc_set_channel_desc_key_frame_interval(desc, 30)  # GOP=30
\end{lstlisting}

\textbf{现象}：

\begin{lstlisting}
AttributeError: module 'acl.media' has no attribute 'venc_set_channel_desc_channel_id'
\end{lstlisting}

\textbf{根因}：VDEC 有
\passthrough{\lstinline!vdec\_set\_channel\_desc\_channel\_id!}，但 VENC
的 API 中\textbf{没有对应的 setter}。VENC 的 channel\_id
由驱动自动分配，不能手动设置。

这暴露了 CANN API 的一个不对称设计：VDEC 和 VENC
虽然结构相似，但细节不同，不能简单类比。

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{问题 \#6：NumPy
维度索引错误}\label{src-book-chapter5-h30}

\textbf{现象}：

\begin{lstlisting}
ValueError: could not broadcast input array from shape (640,640) into shape (640,)
\end{lstlisting}

\textbf{根因}：NV12 数据是 2D 数组
\passthrough{\lstinline!(H*3/2, W)!}，但代码用 1D 线性偏移去索引：

\begin{lstlisting}[language=Python]
# 错误：nv12_data[src_off : src_off + w] 切出了形状 (w, w) 而非 (w,)
nv12_padded[off : off + w] = nv12_data[src_off : src_off + w]  # 2D -> 1D 广播失败
\end{lstlisting}

当 \passthrough{\lstinline!src\_off = row * w = 0!}
时，\passthrough{\lstinline!nv12\_data[0:640]!} 取到的是整个 Y plane
的前 640 行（即整个 640×640 区域），而不是第 0 行的 640 个像素。

\textbf{修复}：使用 2D 切片明确行列：

\begin{lstlisting}[language=Python]
nv12_padded_2d = np.zeros(stride * h * 3 // 2, dtype=np.uint8).reshape(-1, stride)
nv12_src_2d = nv12_data.reshape(-1, w)

# Y plane
for row in range(h):
    nv12_padded_2d[row, :w] = nv12_src_2d[row, :w]

# UV plane
for row in range(h // 2):
    nv12_padded_2d[h + row, :w] = nv12_src_2d[h + row, :w]

nv12_padded = nv12_padded_2d.ravel()
\end{lstlisting}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{问题 \#7：stride 对齐}\label{src-book-chapter5-h31}

VENC 要求输入帧的宽度\textbf{对齐到 16}（硬件约束）。NV12 数据填充时，Y
plane 每行宽度应为
\passthrough{\lstinline!aligned\_width!}（stride），UV plane 同理。

\begin{lstlisting}[language=Python]
self._align = 16
self._stride = ((width + self._align - 1) // self._align) * self._align
# 640 -> 640 (已对齐)，638 -> 640 (补齐)
\end{lstlisting}

不设置 stride 对齐会导致编码出的画面出现偏移或绿条。

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{问题 \#8：NPU Alarm
状态混淆}\label{src-book-chapter5-h32}

\textbf{现象}：

\begin{lstlisting}

\end{lstlisting}

该状态容易被误认为 VENC 不可用。但实际测试表明 Alarm 不影响

\subsection{VDEC 简介}\label{src-book-chapter5-h50}

\textbf{VDEC}（Video Decoder）是 DVPP 中的硬件视频解码模块。它将
H.264/H.265 压缩码流解码为 NV12 原始帧。

\begin{figure}

\subsubsection{H.264 与 H.265 基础}\label{src-book-chapter5-h51}

H.264/H.265 的帧类型（I/P/B）、GOP、NAL 单元、Annex-B
格式等编解码理论知识，详见 \hyperref[h264-h265-basics]{H.264/H.265
基础}。本文的 VDEC API 示例默认使用 \textbf{H.264
Baseline}，基准脚本同时覆盖 \textbf{H.264 Baseline} 与 \textbf{H.265
Main}。

VDEC 对输入码流只有一个硬性要求：必须是 \textbf{Annex-B 格式}（带
\passthrough{\lstinline!0x00000001!} 起始码的 NAL 单元序列）。H.264
首帧必须包含 SPS + PPS + IDR；H.265 首帧必须包含 VPS + SPS + PPS + IDR。

    ret_code = acl.media.dvpp_get_pic_desc_ret_code(output_pic_desc)

        pass
    else:
        pic_data = acl.media.dvpp_get_pic_desc_data(output_pic_desc)
        pic_size = acl.media.dvpp_get_pic_desc_size(output_pic_desc)
        # ... 拷贝 pic_data 到主机内存 ...

    # 回调负责销毁输入和输出描述符
    acl.media.dvpp_destroy_stream_desc(input_stream_desc)

与 VENC 的关键区别：

\begin{itemize}

\item

\end{itemize}

\subsubsection{\texorpdfstring{附：\texttt{encode\_frames}
参数详解}{附：encode\_frames 参数详解}}\label{src-book-chapter5-h67}

\href{https://github.com/zhouxzh/Ascend310/blob/master/samples/chapter5/vdec/bench_vdec.py}{\passthrough{\lstinline!bench\_vdec.py!}}
中用于生成测试码流的函数，接收原始帧 + 编码器名 + GOP -\textgreater{}

\begin{lstlisting}[language=Python]
def encode_frames(frames: list[np.ndarray], codec_name: str, gop: int
                  ) -> tuple[list[bytes], int, int]:
    import av

    h, w = frames[0].shape[:2]
    level = "31" if w * h <= 1280 * 720 else "40"

    codec = av.CodecContext.create(codec_name, "w")    # (1)
    codec.width = w                                     # (2)
    codec.height = h
    codec.pix_fmt = "yuv420p"                           # (3)
    codec.bit_rate = max(2_000_000,                     # (4)
                         int(w * h * FPS * 0.1))
    codec.framerate = fractions.Fraction(FPS, 1)        # (5)
    codec.time_base = fractions.Fraction(1, FPS)        # (6)
    codec.options = {"level": level,                    # (7)
                     "tune": "zerolatency"}
    if codec_name == "libx265":
        codec.options["x265-params"] = "log-level=error"
    if codec_name == "libx264":
        codec.profile = "Baseline"                      # (8)

    for i, bgr in enumerate(frames):
        frame = av.VideoFrame.from_ndarray(
            bgr[..., ::-1], format="rgb24")             # (9)
        frame.pict_type = (                             # (10)
            av.video.frame.PictureType.I
            if i % gop == 0
            else av.video.frame.PictureType.P)
        data = bytearray()
        for pkt in codec.encode(frame):                 # (11)
            data += bytes(pkt)
        if data:
            streams.append(bytes(data))
    tail = bytearray()
    for pkt in codec.encode(None):                      # (12)
        tail += bytes(pkt)
    if tail:
        if streams:
            streams[-1] += bytes(tail)
        else:
            streams.append(bytes(tail))
    return streams, i_avg, p_avg
\end{lstlisting}

\textbf{(1)
\passthrough{\lstinline!av.CodecContext.create(codec\_name, "w")!}}
创建编码器实例。\passthrough{\lstinline!codec\_name = "libx264"!} 或
\passthrough{\lstinline!"libx265"!}，\passthrough{\lstinline!"w"!}
表示编码模式。 libx264 是 H.264 标准的开源软件实现，运行在 CPU 上。
此处用它来\textbf{生成测试素材}------先软件编码再硬件解码，正好对应需要对比的两条路径。

\textbf{(2) \passthrough{\lstinline!codec.width / codec.height!}}
编码帧的尺寸（像素）。必须与实际输入的 numpy 数组尺寸一致。 VDEC
解码时需传入相同尺寸的
\passthrough{\lstinline!out\_pic\_width/height!}。

\textbf{(3) \passthrough{\lstinline!codec.pix\_fmt = "yuv420p"!}}
编码器\textbf{内部}使用的像素格式。libx264 只接受 YUV 格式，
\passthrough{\lstinline!"yuv420p"!} 是 I420（YUV 4:2:0 planar）。PyAV
会自动将输入的 \passthrough{\lstinline!rgb24!} 帧 转为
\passthrough{\lstinline!yuv420p!} 后再送给编码器。

\textbf{(4)
\passthrough{\lstinline!codec.bit\_rate = max(2\_000\_000, int(w * h * FPS * 0.1))!}}
目标码率，单位 \textbf{bps}。 - \passthrough{\lstinline!2\_000\_000!} =
2 Mbps，是最低可用码率，确保小分辨率不会码率过低。 -
\passthrough{\lstinline!w * h * FPS * 0.1!} = 每像素每秒 0.1
bps，按分辨率和帧率缩放。 例如 640×480×30×0.1 \textasciitilde{} 0.9 Mbps
-\textgreater{} 取 2 Mbps；3840×2160×30×0.1 \textasciitilde{} 25 Mbps。
- \passthrough{\lstinline!max(...)!} 设置 2 Mbps 码率下限。

码率影响帧大小：码率越高字节越多，但硬件解码速度主要和像素数相关，受码率影响很小。

\textbf{(5) \passthrough{\lstinline!codec.framerate!}}
目标帧率（fps）。设为 30 表示编码器按 30fps 场景分配比特预算。
不改变实际编码速度，只影响码率控制算法。

\textbf{(6) \passthrough{\lstinline!codec.time\_base!}}
时间基准，帧率的倒数。\passthrough{\lstinline!Fraction(1, 30)!}
表示每帧间隔 1/30 秒。 影响编码后 Packet 的
\passthrough{\lstinline!pts!}/\passthrough{\lstinline!dts!} 时间戳。

\textbf{(7) \passthrough{\lstinline!codec.options!}} 传递给 libx264
编码器的底层选项：

\begin{itemize}
\tightlist
\item
  \passthrough{\lstinline!"level"!}：H.264 Level。\textless=720p 用
  Level 3.1，\textgreater=1080p 用 Level 4.0。 编码的码流中会嵌入 Level
  标志，VDEC 据此分配解码缓冲区。
\item
  \passthrough{\lstinline!"tune": "zerolatency"!}：低延迟调优。\textbf{禁用
  B 帧}，编码器每收到一帧立即输出，
  不做多帧缓冲。实时通信必须开启，代价是牺牲约 10-15\% 压缩率。
\end{itemize}

H.265 路径也使用 \passthrough{\lstinline!zerolatency!}，并通过
\passthrough{\lstinline!x265-params=log-level=error!} 关闭 x265
的信息日志。

\textbf{(8) \passthrough{\lstinline!codec.profile = "Baseline"!}} H.264
\textbf{档次}。三个常用档次：

\begin{itemize}
\tightlist
\item
  \textbf{Baseline}：最简，无 B 帧，适合实时通信和低功耗设备。
\item
  \textbf{Main}：比 Baseline 多 B 帧，压缩率高 10-15\%，适合广播电视。
\item
  \textbf{High}：在 Main 基础上增加 8×8 变换和量化矩阵，适合高清蓝光。
\end{itemize}

Baseline 是 WebRTC 强制要求的最低档次，且 VDEC
\passthrough{\lstinline!entype=1!} 正好对应 Baseline。 注意：libx265
没有 \passthrough{\lstinline!profile!} 属性（H.265 的 profile 通过
options 设置），所以加了 \passthrough{\lstinline!if!} 判断。

\textbf{(9)
\passthrough{\lstinline!av.VideoFrame.from\_ndarray(bgr[..., ::-1], format="rgb24")!}}
将 numpy BGR 数组转为 PyAV \passthrough{\lstinline!VideoFrame!} 对象。
\passthrough{\lstinline!bgr[..., ::-1]!}
把通道反转：\passthrough{\lstinline!BGR -> RGB!}。

\textbf{(10)
\passthrough{\lstinline!frame.pict\_type = I if i \% gop == 0 else P!}}
按 GOP 间隔设置帧类型。GOP=30 时，帧 0、30、60\ldots{} 为 I 帧，其余为 P
帧。 这是模拟真实视频流的关键------97\% 的帧是 P 帧，3\% 是 I 帧。
与旧版全 I 帧（GOP=1）相比，I 帧体积从 \textasciitilde80KB 降至
\textasciitilde25KB（480p），因为码率预算被 P 帧摊薄。

\textbf{(11) \passthrough{\lstinline!codec.encode(frame)!}}
将一帧送入编码器，返回编码后的 \passthrough{\lstinline!Packet!}
列表。每个 Packet 包含 一个或多个 NAL 单元（SPS/PPS/SEI/IDR Slice 等）。

基准脚本会过滤空 packet，并按实际可用 packet 数量做 warmup
和计时；这也是 H.265 现在能正常出表的原因。

\textbf{(12) \passthrough{\lstinline!codec.encode(None)!}}
\textbf{排空编码器缓冲区}。传入 \passthrough{\lstinline!None!}
强制输出所有剩余数据。 排空后的尾 NAL 追加到最后一帧的码流末尾。

\subsubsection{I 帧数量与解码性能}\label{iframe-performance}

\textbf{基准测试中的 I 帧数量}

每 30 帧一个 I 帧。\passthrough{\lstinline!bench\_vdec.py!} 使用
\passthrough{\lstinline!TEST\_GOP = 30!}，90 帧测试中只有 \textbf{3 个 I
帧}（帧 0、30、60），其余 87 帧是 P 帧。这是模拟真实视频流的配置。

\begin{lstlisting}
基准测试码流（GOP=30）：
  [IDR] [P] [P] ... [P] [IDR] [P] [P] ... [P] [IDR] [P] ...
   ↑ ~25KB@480p     ↑ ~7KB                     I 帧数 = 3/90 ~ 3%

全 I 帧码流（GOP=1，仅供参考）：
  [IDR] [IDR] [IDR] ... [IDR]   ← 所有帧都是关键帧
   ↑ ~80KB@480p 完全相同的大小
\end{lstlisting}

\textbf{为什么用 GOP=30 而不是全 I 帧}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{真实视频流就是这样的}：WebRTC、RTSP、监控摄像头通常使用
  GOP=15\textasciitilde60。 GOP=30 表示每秒一个关键帧（30fps
  下），是实时通信的典型配置。
\item
  \textbf{避免误判 VDEC 性能}：全 I 帧测试中每帧都
  \textasciitilde80KB（480p），VDEC 的硬件并行优势被放大。 而真实流中
  97\% 的帧是小 P 帧（\textasciitilde7KB），CPU 处理 P
  帧极快（只需解运动矢量 + 残差）， VDEC 的固定调度开销反而成了瓶颈。
\item
  \textbf{全 I 帧曾导致错误结论}：本教程早期版本用 GOP=1 测得 VDEC 在
  720p 领先 CPU 10\%、 1080p 领先 43\%。切换到 GOP=30 后，H.264 VDEC 在
  \textless=1080p 全面落后于 CPU。 \textbf{全 I
  帧测试的不是真实场景，测试结果不可用于工程决策。}
\end{enumerate}

P 帧 & \textasciitilde7 KB & 帧间解码（运动矢量 + 残差） &
\textbf{固定开销主导} & 极快（数据量小） \\
\end{longtable}
}

在 GOP=30 混合流中，P 帧占 97\%。P 帧数据量仅为 I 帧的
\textasciitilde30\%， CPU 解码 P 帧的开销远低于 I 帧（只需解残差），而
VDEC 每帧仍需经过完整的
\passthrough{\lstinline!memcpy -> send -> callback -> memcpy -> Queue!}
路径，这部分时间与帧大小关系不大。

\textbf{如何切换测试模式}

修改 \passthrough{\lstinline!bench\_vdec.py!} 顶部的常量即可：

\begin{lstlisting}[language=Python]
# 当前（GOP=30，I/P 混合——真实视频流）
TEST_GOP = 30

# 改为（GOP=1，全 I 帧——最坏情况/最大吞吐测试）
TEST_GOP = 1
\end{lstlisting}

\passthrough{\lstinline!encode\_frames()!} 会根据
\passthrough{\lstinline!gop!} 参数自动设置每帧的
\passthrough{\lstinline!pict\_type!}：
\passthrough{\lstinline!i \% gop == 0!} 时为 I 帧，否则为 P 帧。

\subsection{常见问题与调试}\label{src-book-chapter5-h68}

\subsubsection{\texorpdfstring{问题 \#1：\texttt{channel\_id}
未设置导致通道创建失败}{问题 \#1：channel\_id 未设置导致通道创建失败}}\label{src-book-chapter5-h69}

\textbf{现象}：

\begin{lstlisting}
vdec_create_channel failed: 507018
\end{lstlisting}

\textbf{根因}：VDEC 与 VENC 不同，\textbf{不会}自动分配
\passthrough{\lstinline!channel\_id!}。必须显式调用
\passthrough{\lstinline!vdec\_set\_channel\_desc\_channel\_id(desc, N)!}。

\textbf{修复}：

\begin{lstlisting}[language=Python]
media.vdec_set_channel_desc_channel_id(desc, 0)
\end{lstlisting}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{问题 \#2：回调参数顺序与 VENC
相反}\label{src-book-chapter5-h70}

\textbf{现象}：在回调中调用
\passthrough{\lstinline!dvpp\_get\_pic\_desc\_ret\_code!}
时进程异常终止或返回无效数据。

\textbf{根因}：VENC 回调是
\passthrough{\lstinline!(input\_pic\_desc, output\_stream\_desc)!}，VDEC
回调是
\passthrough{\lstinline!(input\_stream\_desc, output\_pic\_desc)!}。如果按
VENC 习惯写 VDEC 回调，会把 stream\_desc 当成 pic\_desc 来读。

\textbf{记忆方法}：\textbf{第一个参数总是''输入''，第二个参数总是''输出''}。VENC
输入是图片、输出是码流；VDEC 输入是码流、输出是图片。

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{\texorpdfstring{问题 \#3：未检查 \texttt{ret\_code}
导致使用损坏帧}{问题 \#3：未检查 ret\_code 导致使用损坏帧}}\label{src-book-chapter5-h71}

\textbf{现象}：解码后的 NV12 数据是花屏或全黑。

\textbf{根因}：\passthrough{\lstinline!dvpp\_get\_pic\_desc\_ret\_code()!}
返回非 0
表示解码失败------可能是输入码流不完整、帧边界不对、参考帧丢失。直接使用失败帧的数据会得到损坏画面。

\textbf{修复}：

\begin{lstlisting}[language=Python]
ret_code = media.dvpp_get_pic_desc_ret_code(pic_desc)
if ret_code != 0:
    cb_queue.put(None)  # 跳过此帧
    return
\end{lstlisting}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{问题 \#4：回调未销毁输出 pic\_desc
导致内存泄漏}\label{src-book-chapter5-h72}

\textbf{现象}：解码多帧后，\passthrough{\lstinline!dvpp\_malloc!}
返回内存不足。

\textbf{根因}：VDEC 回调负责销毁\textbf{两个}描述符（输入 stream\_desc
和输出 pic\_desc）。VENC 只需要销毁输入，因为输出的 stream\_desc
由调用方管理。如果只销毁了 stream\_desc，pic\_desc 及其关联的 DVPP
内存永远不会释放。

\textbf{修复}：回调 \passthrough{\lstinline!finally!} 块中同时销毁两个：

\begin{lstlisting}[language=Python]
finally:
    media.dvpp_destroy_stream_desc(input_stream_desc)
    media.dvpp_destroy_pic_desc(output_pic_desc)
\end{lstlisting}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{问题 \#5：输入必须用 numpy 包装才能
memcpy}\label{src-book-chapter5-h73}

\textbf{现象}：

\begin{lstlisting}
TypeError: acl.rt.memcpy args parse failed
\end{lstlisting}

\textbf{根因}：\passthrough{\lstinline!acl.rt.memcpy!}
的源地址参数不接受 Python \passthrough{\lstinline!bytes!}
对象。必须将其包装为 numpy 数组或 ctypes 指针。

\textbf{修复}：

\begin{lstlisting}[language=Python]
# 错误
h264 = b"..."
acl.rt.memcpy(in_buf, len(h264), h264, len(h264), 1)  # TypeError

# 正确
h264_arr = np.frombuffer(h264, dtype=np.uint8)
acl.rt.memcpy(in_buf, len(h264), h264_arr.ctypes.data, len(h264), 1)
\end{lstlisting}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{\texorpdfstring{问题 \#6：\texttt{vdec\_destroy\_channel}
顺序错误导致阻塞}{问题 \#6：vdec\_destroy\_channel 顺序错误导致阻塞}}\label{src-book-chapter5-h74}

\textbf{现象}：解码多帧后，\passthrough{\lstinline!media.vdec\_destroy\_channel(desc)!}
永远阻塞，程序卡死。

\textbf{根因}：VDEC 通道销毁时，回调线程必须在
\passthrough{\lstinline!vdec\_destroy\_channel!}
调用期间保持运行------驱动需要在销毁过程中通过回调发送最后的清理通知。如果先停止了回调线程，\passthrough{\lstinline!vdec\_destroy\_channel!}
会无限等待一个永远不会来的回调。

VDEC 的正确销毁顺序与直觉相反：

\begin{lstlisting}[language=Python]
# 错误：先停线程再销毁通道 -> 永远阻塞
running[0] = False                      # 通知线程停止
media.vdec_destroy_frame_config(fcfg)    # 销毁帧配置
media.vdec_destroy_channel(desc)         # 销毁通道 -> 等待回调 -> 永远阻塞！

# 正确：先销毁通道（需要线程活着），再停线程
media.vdec_destroy_channel(desc)         # (1) 先销毁通道（此时线程必须活着）
running[0] = False                      # (2) 通知线程停止
acl.util.stop_thread(tid)               # (3) 停止回调线程
media.vdec_destroy_frame_config(fcfg)    # (4) 最后销毁帧配置
media.vdec_destroy_channel_desc(desc)    # (5) 销毁描述符
\end{lstlisting}

这一步的关键点是销毁通道时回调线程必须仍在运行，否则驱动侧的清理事件无法被处理。

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsubsection{问题 \#7：VDEC
通道复用对码流连续性非常敏感}\label{src-book-chapter5-h75}

\textbf{现象}：通道创建后第一帧解码正常，第二帧
\passthrough{\lstinline!vdec\_send\_frame!} 返回 0 但回调永不触发。

\textbf{根因}：VDEC
期望同一通道上解码的帧来自\textbf{同一个编码器实例}，并且按连续视频流顺序送入。也就是所有帧需要共享兼容的
SPS/PPS（序列参数集/图像参数集），不能把多个互不相关的 IDR
样本直接拼到同一通道里混跑。

\textbf{验证方法}：用单个 libx264 \passthrough{\lstinline!CodecContext!}
连续编码所有测试帧，确保 SPS/PPS
一致，并按同一序列顺序逐帧送入。\passthrough{\lstinline!samples/chapter5/vdec/bench\_vdec.py!}
已新增``单通道复用''路径，并自动尝试不同
\passthrough{\lstinline!pipeline\_depth!} 与
\passthrough{\lstinline!frame\_config!} 策略；在当前 310B
环境下，只有带显式 \passthrough{\lstinline!EOS!} 的
\passthrough{\lstinline!depth=4!} 变体能够稳定排空尾部缓存帧。

\textbf{当前结论}：Ascend 310B4 上不能假设``任意 H.264
样本都能安全复用同一通道''。应先用连续码流验证复用模式，并显式处理解码器尾部
flush；如果复用路径不稳定，再退回每帧独立通道作为兜底方案。独立通道虽然可靠，但固定创建/销毁开销在
640×480 下通常远高于纯 CPU 解码。

\subsubsection{关键发现}\label{src-book-chapter5-h79}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{H.264 低分辨率 VDEC 有固定调度开销}------480p/720p/1080p 下
  VDEC 都是 \textasciitilde59ms/帧，与分辨率无关。
  这说明瓶颈不在硬件解码，而在 Python
  回调-\textgreater 队列-\textgreater 主线程的调度路径。
\item
  \textbf{H.264 高分辨率是 VDEC 的优势区间}------2K
  以上分辨率，硬件解码耗时自然增加， 固定调度开销被摊薄，VDEC
  开始领先单线程 CPU。4K 时领先 2.17×。
\item
  \textbf{H.265 是 VDEC 的优势路径}------720p 以上 H.265 VDEC
  同时领先单线程和多线程 CPU，4K 时对多线程 CPU 也有 3.30× 加速。
\item
  \textbf{I/P 混合流比全 I 帧流更不利于 H.264 VDEC}------详见上文
  \hyperref[iframe-performance]{I 帧数量与解码性能} 的对比分析。全 I
  帧测试曾误导结论，GOP=30 才是真实场景。
\item
  \textbf{零拷贝管道可消除调度开销}------当前实现每次解码都经过
  \passthrough{\lstinline!memcpy!} + Python Queue。 如果 VDEC
  输出直接喂给 VENC（设备内存零拷贝），可消除 \textasciitilde46ms
  的调度+malloc+memcpy 开销。
\end{enumerate}

\section{VPC --- 硬件图像处理}\label{vpc}

\begin{quote}
VPC（Video Pre-Processing
Core）提供硬件加速的缩放、裁剪、色彩空间转换。前置基础：\hyperref[dvpp-basics]{DVPP
基础概念}。
\end{quote}

\subsection{VPC 简介}\label{src-book-chapter5-h84}

\textbf{VPC}（Video Pre-Processing Core）是 DVPP
中的硬件图像处理模块。它提供三大功能：

{ % do not increment counter
\begin{longtable}[]{@{}lll@{}}
\toprule\noalign{}
功能 & 说明 & 典型场景 \\
\midrule\noalign{}
\endhead
\bottomrule\noalign{}
\endlastfoot

\end{lstlisting}

\subsubsection{为什么用 VPC 而不是 OpenCV}\label{src-book-chapter5-h85}

在 Orange Pi AI Pro 上，CPU 做
\passthrough{\lstinline!cv2.cvtColor(YUYV->BGR)!} +
\passthrough{\lstinline!cv2.resize(1080p->720p)!} +
\passthrough{\lstinline!bgr\_to\_nv12()!} 会消耗 ARM Cortex-A55
的宝贵算力。VPC 完全在硬件中完成这些操作，CPU 只负责下发任务和等待完成。

\subsubsection{通道模型对比}\label{src-book-chapter5-h88}

\begin{lstlisting}
VENC/VDEC 专用通道:                VPC 通用通道:

主线程: send_frame -> Queue.get   主线程: vpc_xxx_async -> synchronize_stream
             ↑                                  ↑
回调线程: process_report            (无需回调线程)
          -> callback
          -> Queue.put
\end{lstlisting}

VPC 的 Stream
模型更简单------下发异步任务后直接阻塞等待完成，不需要管理额外的线程和队列。

\subsection{VPC API 详解}\label{src-book-chapter5-h89}

\subsubsection{通用 DVPP 通道创建}\label{src-book-chapter5-h90}

VPC 使用通用的 \passthrough{\lstinline!dvpp\_create\_channel()!}，与
VENC/VDEC 的专用 API 不同。无需设置 mode（310B 不支持
\passthrough{\lstinline!DVPP\_CHANNEL\_MODE!}
常量），也无需创建回调线程：

\begin{lstlisting}[language=Python]
import acl

# 创建通用 DVPP 通道
dvpp_channel_desc = acl.media.dvpp_create_channel_desc()
ret = acl.media.dvpp_create_channel(dvpp_channel_desc)

# 创建 Stream 用于同步等待
stream, ret = acl.rt.create_stream()
\end{lstlisting}

\subsubsection{Resize --- 缩放}\label{src-book-chapter5-h91}

将输入图片缩放到输出尺寸：

\begin{lstlisting}[language=Python]
# 创建 resize 配置
resize_config = acl.media.dvpp_create_resize_config()
# 可选：设置插值算法
# acl.media.dvpp_set_resize_config_interpolation(resize_config, 0)  # 0=bilinear

ret = acl.media.dvpp_vpc_resize_async(
    dvpp_channel_desc,    # DVPP 通道描述符
    input_pic_desc,       # 输入图片描述符（pic_desc）
    output_pic_desc,      # 输出图片描述符（pic_desc）
    resize_config,        # 缩放配置
    stream                # Stream 对象
)
acl.rt.synchronize_stream(stream)  # 等待完成
\end{lstlisting}

\textbf{关键约束}：

\begin{itemize}
\tightlist
\item
  输入/输出 pic\_desc 的宽高必须对齐到 2（VPC 自动处理）
\item
  resize 不会改变像素格式------输入 NV12 则输出也是 NV12
\item
  如需同时改变格式和尺寸，需串联 CSC + Resize
\end{itemize}

\subsubsection{Crop --- 裁剪}\label{src-book-chapter5-h92}

从输入图片中裁剪指定区域：

\begin{lstlisting}[language=Python]
# 创建 ROI 配置：从 (100, 100) 开始裁剪 224×224
# dvpp_create_roi_config 接受 4 个位置参数: (left, right, top, bottom)
crop_area = acl.media.dvpp_create_roi_config(
    100,    # 左边界偏移
    323,    # 右边界偏移 (左+宽-1)
    100,    # 上边界偏移
    323,    # 下边界偏移 (上+高-1)
)

ret = acl.media.dvpp_vpc_crop_async(
    dvpp_channel_desc, input_pic_desc, output_pic_desc, crop_area, stream)
acl.rt.synchronize_stream(stream)
\end{lstlisting}

\subsubsection{Crop + Resize ---
最常用的组合}\label{src-book-chapter5-h93}

裁剪后缩放到目标尺寸，一次调用完成两个操作：

\begin{lstlisting}[language=Python]
# 从 1080p 画面中裁剪中心区域，缩放到 720×480
# 注意：dvpp_create_roi_config 接受 4 个位置参数 (left, right, top, bottom)
crop_area = acl.media.dvpp_create_roi_config(160, 480, 120, 360)

resize_config = acl.media.dvpp_create_resize_config()

ret = acl.media.dvpp_vpc_crop_resize_async(
    dvpp_channel_desc,
    input_pic_desc,       # 1920×1080
    output_pic_desc,      # 720×480
    crop_area,
    resize_config,
    stream
)
acl.rt.synchronize_stream(stream)
\end{lstlisting}

这是 VPC 最高效的使用方式------crop + resize
在一个硬件调用中完成，避免中间缓冲区。

\subsubsection{CSC --- 色彩空间转换（310B 不可用）}\label{vpc-csc}

\textbf{结论}：310B (CANN 8.3.RC1)
上，\passthrough{\lstinline!dvpp\_vpc\_convert\_color\_async!} 返回
\passthrough{\lstinline!ACL\_ERROR\_INVALID\_PARAM!}（100000），\passthrough{\lstinline!himpi.vpc\_convert\_color!}
需要 himpi 通道预配置（Python 接口不支持）。CSC 在 310B
上\textbf{目前不可用}。

\textbf{替代方案}：YUYV-\textgreater NV12 转换使用
CPU（\passthrough{\lstinline!cv2.cvtColor + bgr\_to\_nv12!}），resize
可卸载到 VPC：

\begin{lstlisting}
USB Camera YUYV -> CPU bgr_to_nv12() -> NV12 -> VPC resize -> NV12(720p) -> VENC
                                          ↑                    ↑
                                     CPU 做色彩转换        VPC 硬件缩放
\end{lstlisting}

如果未来 CANN 版本在 310B 上开放 CSC 支持，可通过
\passthrough{\lstinline!dvpp\_vpc\_convert\_color\_async!} 使用与 resize
完全相同的通道+Stream 模式调用。

src_nv12 = make_test_nv12(640, 480)

sh = ((480 + 1) // 2) * 2      # height stride 对齐到 2
in_size = sw * sh * 3 // 2

out_sw = ((320 + 15) // 16) * 16
out_sh = ((240 + 1) // 2) * 2
out_size = out_sw * out_sh * 3 // 2

# 分配设备内存 + 拷贝输入数据
in_buf, _ = media.dvpp_malloc(in_size)
out_buf, _ = media.dvpp_malloc(out_size)
acl.rt.memcpy(in_buf, src_nv12.nbytes, src_nv12.ctypes.data,
              src_nv12.nbytes, ACL_MEMCPY_HOST_TO_DEVICE)

# 构造输入/输出 pic_desc（含 height_stride）
in_pic = create_nv12_pic_desc(in_buf, 640, 480, sw, sh)
out_pic = create_nv12_pic_desc(out_buf, 320, 240, out_sw, out_sh)

# 执行缩放 + 同步等待
resize_cfg = media.dvpp_create_resize_config()
media.dvpp_vpc_resize_async(ch_desc, in_pic, out_pic, resize_cfg, stream)
acl.rt.synchronize_stream(stream)

# 拷回主机内存
host_buf = np.zeros(out_size, dtype=np.uint8)
acl.rt.memcpy(host_buf.ctypes.data, out_size, out_buf, out_size,
              ACL_MEMCPY_DEVICE_TO_HOST)
\end{lstlisting}

\subsection{常见问题与调试}\label{src-book-chapter5-h104}

\subsubsection{问题 \#1：310B 不支持
dvpp\_vpc\_convert\_color\_async}\label{src-book-chapter5-h105}

\textbf{现象}：\passthrough{\lstinline!dvpp\_vpc\_convert\_color\_async!}
返回 \passthrough{\lstinline!100000!}（ACL\_ERROR\_INVALID\_PARAM）。

\textbf{根因}：该接口仅支持 310P 及以上型号。310B（Atlas 200I A2）的
CANN 8.3.RC1 版本不支持。

\textbf{修复}：无 VPC 硬件替代方案。YUYV-\textgreater NV12 使用
CPU：\passthrough{\lstinline!cv2.cvtColor(YUYV->BGR) + bgr\_to\_nv12()!}。VPC
仅卸载 resize 部分。

\subsubsection{问题 \#2：pic\_desc 必须设置
height\_stride}\label{src-book-chapter5-h106}

\textbf{现象}：\passthrough{\lstinline!dvpp\_vpc\_resize\_async!} 返回
\passthrough{\lstinline!100000!}（ACL\_ERROR\_INVALID\_PARAM）。

\textbf{根因}：\passthrough{\lstinline!dvpp\_set\_pic\_desc\_height\_stride!}
未设置，且 \passthrough{\lstinline!dvpp\_set\_pic\_desc\_size!}
使用了未对齐的 \passthrough{\lstinline!W*H*3//2!}。VPC 要求高度 stride
对齐到 2，宽度 stride 对齐到 16，缓冲区大小按 stride 计算。

\textbf{修复}：

\begin{lstlisting}[language=Python]
sw = ((w + 15) // 16) * 16   # width stride
sh = ((h + 1) // 2) * 2     # height stride
size = sw * sh * 3 // 2      # 按 stride 算总大小
media.dvpp_set_pic_desc_width_stride(pic, sw)
media.dvpp_set_pic_desc_height_stride(pic, sh)
media.dvpp_set_pic_desc_size(pic, size)
\end{lstlisting}

\subsubsection{问题 \#3：dvpp\_create\_roi\_config 不接受 keyword
参数}\label{src-book-chapter5-h107}

\textbf{现象}：\passthrough{\lstinline!dvpp\_create\_roi\_config()!} +
\passthrough{\lstinline!dvpp\_set\_roi\_config()!} 不存在或报错。

\textbf{根因}：\passthrough{\lstinline!dvpp\_set\_roi\_config!} 在 CANN
8.3.RC1 的 Python API 中不接受 keyword 参数。正确做法是在
\passthrough{\lstinline!dvpp\_create\_roi\_config()!} 中直接传入 4
个位置参数。

\textbf{修复}：

\begin{lstlisting}[language=Python]
# 正确
crop_area = acl.media.dvpp_create_roi_config(left, right, top, bottom)

# 错误
crop_area = acl.media.dvpp_create_roi_config()
acl.media.dvpp_set_roi_config(crop_area, left, right, top, bottom)
\end{lstlisting}

\subsubsection{问题 \#4：himpi 通道不可从 Python
创建}\label{src-book-chapter5-h108}

\textbf{现象}：\passthrough{\lstinline!himpi.vpc\_create\_chn()!}
无论传什么参数都报 ``args parse failed''。

\textbf{根因}：himpi 接口是 C 扩展的直接映射，需要 C
结构体类型的参数，Python
侧不支持创建这些结构体。\passthrough{\lstinline!vpc\_convert\_color!}
虽然语法上可以调用，但缺少预配置的 himpi 通道，返回硬件错误
\passthrough{\lstinline!0xa0078003!}。

\textbf{当前结论}：310B 上的 VPC CSC 不可用。等待 CANN 后续版本在 310B
上开放 \passthrough{\lstinline!dvpp\_vpc\_convert\_color\_async!} 支持。

\subsubsection{场景决策树}\label{src-book-chapter5-h110}

需要对图像做预处理？

\begin{itemize}
\tightlist

\subsection{JPEGE API 详解}\label{src-book-chapter5-h119}

\subsubsection{编码流程}\label{src-book-chapter5-h120}

\begin{lstlisting}
(1) 创建 jpege_config + 设置质量 -> (2) predict_enc_size 预测输出大小
    -> (3) dvpp_malloc 输出缓冲区 -> (4) jpeg_encode_async 异步编码
    -> (5) synchronize_stream 等待 -> (6) 读取实际 size -> (7) memcpy 取回 JPEG 码流
\end{lstlisting}

唯一参数是 \textbf{quality}（1-100），对应 JPEG

\subsubsection{jpeg\_encode\_async ---
执行编码}\label{src-book-chapter5-h123}

\begin{lstlisting}[language=Python]
import numpy as np

# in/out 参数：传入 max_size，编码后返回实际大小
out_size_arr = np.array([max_size], dtype=np.int32)
if "bytes_to_ptr" in dir(acl.util):
    out_size_ptr = acl.util.bytes_to_ptr(out_size_arr.tobytes())
else:
    out_size_ptr = acl.util.numpy_to_ptr(out_size_arr)

ret = acl.media.dvpp_jpeg_encode_async(
    channel_desc,       # dvpp 通道描述符
    input_pic_desc,     # NV12 输入图片描述符
    output_buffer,      # 输出缓冲区（dvpp_malloc）
    out_size_ptr,       # in/out: [max_size] -> [actual_size]
    jpege_cfg,          # 编码配置
    stream              # Stream 对象
)
acl.rt.synchronize_stream(stream)

# 同步后读取实际编码大小
actual_size = int(out_size_arr[0])
\end{lstlisting}

\textbf{关键点}：\passthrough{\lstinline!out\_size\_ptr!} 是 Python 层用
\passthrough{\lstinline!numpy\_to\_ptr!} 封装的指针，指向一个
\passthrough{\lstinline!int32!}
数组。编码器写入实际大小后，同步完成即可读取。

\subsection{常见问题与调试}\label{src-book-chapter5-h139}

\subsubsection{问题 \#1：JPEGE 输出不是
stream\_desc}\label{src-book-chapter5-h140}

\textbf{现象}：试图用
\passthrough{\lstinline!dvpp\_get\_stream\_desc\_data!}
读取编码输出，得到无效数据。

\textbf{根因}：JPEGE 输出写入裸内存缓冲区，不是
\passthrough{\lstinline!stream\_desc!}。只有 VENC 使用 stream\_desc
输出。

\textbf{修复}：JPEGE 输出直接 \passthrough{\lstinline!memcpy!} 从
\passthrough{\lstinline!out\_buf!} 拷出，实际大小从
\passthrough{\lstinline!out\_size\_ptr!} 读取。

\subsubsection{问题 \#2：out\_size\_ptr
的同步时序}\label{src-book-chapter5-h141}

\textbf{现象}：\passthrough{\lstinline!synchronize\_stream!} 之前读取
\passthrough{\lstinline!out\_size\_arr[0]!}，得到的是 max\_size 而非
actual\_size。

\textbf{根因}：\passthrough{\lstinline!out\_size\_arr!} 是 in/out
参数，编码器在硬件完成后才写入实际值。

\textbf{修复}：\textbf{必须在
\passthrough{\lstinline!synchronize\_stream!} 之后}读取
\passthrough{\lstinline!out\_size\_arr[0]!}。

\subsubsection{问题 \#3：predict\_enc\_size
返回的值远大于实际}\label{src-book-chapter5-h142}

\textbf{现象}：\passthrough{\lstinline!predict\_enc\_size!} 返回
2MB，但编码后只有 30KB。

\textbf{根因}：\passthrough{\lstinline!predict\_enc\_size!}
返回的是\textbf{最坏情况}的缓冲区大小，不是预测值。JPEG
的压缩率取决于图像内容。

\textbf{修复}：按 predict 值分配缓冲区（保障不溢出），编码后通过
\passthrough{\lstinline!out\_size\_arr[0]!} 取实际大小。

\subsection{项目定位}\label{src-book-chapter5-h146}

\begin{lstlisting}

\end{lstlisting}

\subsection{关键模块走读}\label{src-book-chapter5-h148}

\subsubsection{\texorpdfstring{\texttt{server.py} ---
会话控制层}{server.py --- 会话控制层}}\label{src-book-chapter5-h149}

\passthrough{\lstinline!server.py!} 是整个服务的入口。它不直接操作
VENC/JPEGD 描述符，但负责把 WebRTC 协商结果和硬件编码器绑定起来。

\textbf{通用编解码偏好（\passthrough{\lstinline!\_prefer\_video\_codec\_for\_sender!}）}：当启用硬件编码时，服务端在
offer 处理中强制设置 video transceiver 的 codec preference。H.264
路径只允许 \passthrough{\lstinline!video/H264!}，H.265 路径只允许
\passthrough{\lstinline!video/H265!}。这样可以避免浏览器和 aiortc 协商到
VP8 等软件编码格式，导致硬件 VENC 产出的码流无法被对端消费。

\begin{lstlisting}[language=Python]
def _prefer_video_codec_for_sender(pc, sender, mime_type):
    codecs = [
        c for c in RTCRtpSender.getCapabilities("video").codecs
        if c.mimeType.lower() == mime_type.lower()
    ]
    for transceiver in pc.getTransceivers():
        if transceiver.sender == sender:
            transceiver.setCodecPreferences(codecs)
\end{lstlisting}

\textbf{H.264 编码器替换}：\passthrough{\lstinline!--hardware-encode!}
或 \passthrough{\lstinline!--source dvpp\_camera!} 会把 aiortc 的
\passthrough{\lstinline!H264Encoder!} 替换为
\passthrough{\lstinline!CannH264Encoder!}。对于
\passthrough{\lstinline!dvpp\_camera!} 模式下产出的 NV12 帧，VENC
是必要条件；否则需要额外做格式转换再交给 libx264。

\textbf{H.265 能力注册}：aiortc 1.14.0 默认没有完整的 H.265
编码器路径。服务端在 \passthrough{\lstinline!--video-codec h265!}
模式下调用 \passthrough{\lstinline!\_patch\_h265\_encoder()!}：先确认
CANN ACL 可用，再向 aiortc 的 video codec 列表注册
\passthrough{\lstinline!video/H265!}（clock rate 90000），最后把 encoder
factory 指向 \passthrough{\lstinline!CannH265Encoder!}。

\textbf{H.265 offer 校验}：H.265 失败时机不是服务启动，而是浏览器发起
offer。服务端会检查浏览器 SDP 是否包含
\passthrough{\lstinline!H265/90000!}；如果没有，直接返回
\passthrough{\lstinline!HTTP 400!}：

\begin{lstlisting}
Browser offer does not contain video/H265. Use a WebRTC HEVC-capable browser.
\end{lstlisting}

\textbf{目标码率是建连参数}：浏览器页面提交的
\passthrough{\lstinline!bitrate\_kbps!} 会在
\passthrough{\lstinline!POST /offer!}
时进入服务端。服务端根据分辨率、帧率、编码格式和页面选择解析出本次连接的
VENC 目标码率，并在创建编码器/VENC
通道时使用。当前不支持运行中热调码率；要修改码率，需要断开后重新建连。

\textbf{连接关闭时先停源再关
PeerConnection}：\passthrough{\lstinline!close\_peer\_connection()!}
先调用 \passthrough{\lstinline!source\_track.stop()!} 释放
\passthrough{\lstinline!/dev/video0!}，再
\passthrough{\lstinline!await pc.close()!}。这样下一个 offer
请求到达时可以立即复用摄像头设备。

\subsubsection{\texorpdfstring{\texttt{ascend\_source.py} ---
视频源适配层}{ascend\_source.py --- 视频源适配层}}\label{src-book-chapter5-h150}

\passthrough{\lstinline!AscendVideoTrack!} 继承
\passthrough{\lstinline!MediaStreamTrack!}，是 aiortc
获取视频帧的唯一入口。三种模式的差异全部封装在初始化方法和
\passthrough{\lstinline!\_camera\_read()!} 中。

\textbf{\passthrough{\lstinline!demo!} 模式}：纯软件合成帧------x/y
颜色渐变 + 正弦移动白条 + 余弦移动白方块，不需要任何外设或 CANN
依赖。用于验证 aiortc + 浏览器接收链路是否畅通。

\textbf{\passthrough{\lstinline!usb\_camera!} 模式（软件基线）}：V4L2
MJPEG 采集 -\textgreater{} PyAV CPU JPEG 解码 -\textgreater{} RGB
\passthrough{\lstinline!VideoFrame!}。这是为对比 DVPP
路径准备的软件基线，不依赖 CANN。

\textbf{\passthrough{\lstinline!dvpp\_camera!} 模式（全硬件管线）}：

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  V4L2 采集 MJPEG 码流（优先使用
  \passthrough{\lstinline!V4l2RawCapture!} 直采，失败降级到 PyAV）
\item
  \passthrough{\lstinline!DvppJpegDecoder!} 硬件解码为 NV12（含 stride
  对齐）
\item
  返回 NV12 \passthrough{\lstinline!VideoFrame!} 给 aiortc
  -\textgreater{} \passthrough{\lstinline!CannH264Encoder!} 或
  \passthrough{\lstinline!CannH265Encoder!} 直通编码
\end{enumerate}

\textbf{V4L2
双后端策略}：\passthrough{\lstinline!\_init\_dvpp\_camera()!} 优先尝试
\passthrough{\lstinline!v4l2\_raw.py!}（直接 ioctl +
mmap，帧率更高），失败时降级到
\passthrough{\lstinline!v4l2\_capture.py!}（基于
PyAV）。两套后端提供相同的 \passthrough{\lstinline!read(timeout)!}
接口，上层的 \passthrough{\lstinline!\_camera\_read()!}
不需要知道用哪个。

\textbf{性能日志}：\passthrough{\lstinline!recv()!} 每 150 帧打印一次
\passthrough{\lstinline!Track FPS!}，方便在设备端直接观察链路帧率；\passthrough{\lstinline!\_camera\_read()!}
前 5 帧打印单帧解码耗时。

\subsubsection{\texorpdfstring{\texttt{cann\_encoder.py} --- VENC
硬件编码 + aiortc
兼容}{cann\_encoder.py --- VENC 硬件编码 + aiortc 兼容}}\label{src-book-chapter5-h151}

这是连接 CANN VENC 和 aiortc 的桥接层，包含三个核心组件：

\textbf{\passthrough{\lstinline!CannVenc!}} --- 同步封装 VENC 异步回调
API。与第 5 章 VENC 教程中的版本相比，WebRTC 版本增加了：

\begin{itemize}
\tightlist
\item
  \textbf{\passthrough{\lstinline!pre\_padded!} 参数}：JPEGD 输出的 NV12
  已经是 stride 对齐的（宽度对齐到 16），此时跳过 CPU 侧的 stride
  重排循环，直接从 \passthrough{\lstinline!dvpp\_malloc!}
  -\textgreater{} \passthrough{\lstinline!memcpy!} -\textgreater{}
  \passthrough{\lstinline!venc\_send\_frame!}。这是实现''NV12
  零拷贝管道''的关键------整个 JPEGD-\textgreater VENC 路径上 NV12 的
  stride 布局始终一致。
\item
  \textbf{回调队列残留检测}：\passthrough{\lstinline!encode()!} 发送前
  drain 回调队列，若有残留帧则
  warn。这能在日志中暴露''上一帧结果未被消费''的问题，避免静默丢帧。
\item
  \textbf{ACL context 线程安全}：每次 \passthrough{\lstinline!encode()!}
  和回调线程入口都显式
  \passthrough{\lstinline!set\_context(ctx)!}，确保线程池中的 executor
  线程也能正常访问 ACL 资源。
\end{itemize}

\textbf{\passthrough{\lstinline!bgr\_to\_nv12()!}} --- 纯 NumPy 实现的
BGR-\textgreater NV12 转换。旧版依赖 OpenCV
\passthrough{\lstinline!cv2.cvtColor!}，现在完全使用 NumPy
整数运算（ITU-R BT.601 转换公式），消除了 OpenCV 依赖。在
\passthrough{\lstinline!dvpp\_camera!} 模式下此函数不会被调用（NV12 已由
JPEGD 产出）；仅在非 NV12 帧走硬件编码时作为回退路径。

\textbf{\passthrough{\lstinline!CannH264Encoder!}} --- 继承 aiortc 的
\passthrough{\lstinline!H264Encoder!}，只覆盖
\passthrough{\lstinline!\_encode\_frame()!}：

\passthrough{\lstinline!H264Encoder!} (aiortc) 的继承结构------只覆盖
\passthrough{\lstinline!\_encode\_frame()!}，其余 RTP 封装全部继承：

\begin{itemize}
\tightlist
\item
  \passthrough{\lstinline!\_encode\_frame()!} -\textgreater{} CANN VENC
  编码 \textbf{{[}已覆盖{]}}
\item
  \passthrough{\lstinline!\_split\_bitstream()!} -\textgreater{} Annex-B
  -\textgreater{} NAL 分割 \textbf{{[}继承{]}}
\item
  \passthrough{\lstinline!\_packetize()!} -\textgreater{} NAL
  -\textgreater{} RTP 分包 \textbf{{[}继承{]}}
\item
  \passthrough{\lstinline!pack()!} -\textgreater{} RTP 打包逻辑
  \textbf{{[}继承{]}}
\item
  其他全部继承
\end{itemize}

关键设计：

\begin{itemize}
\tightlist
\item
  \textbf{NV12 直通检测}：检查
  \passthrough{\lstinline!frame.format.name == "nv12"!}。DVPP 产出的
  NV12 帧直接调用
  \passthrough{\lstinline!to\_ndarray!}（零格式转换），传入
  \passthrough{\lstinline!pre\_padded=True!} 跳过 CPU stride 重排。
\item
  \textbf{BGR-\textgreater NV12 走 PyAV reformat}：非 NV12 帧（如 demo
  的 RGB 帧）调用
  \passthrough{\lstinline!frame.reformat(format="nv12")!}，由 PyAV 的 C
  实现完成色彩空间转换（比手动 \passthrough{\lstinline!bgr\_to\_nv12()!}
  快得多），再 \passthrough{\lstinline!to\_ndarray!} 取出。
\item
  \textbf{FPS 自适应}：\passthrough{\lstinline!\_estimate\_fps()!}
  从连续帧的 PTS 时间戳差值实时估算实际帧率，据此调整 VENC 的
  \passthrough{\lstinline!src\_rate!}
  参数。当实际帧率因采集链路抖动而变化时，VENC 的码率控制能跟随调整。
\item
  \textbf{CANN
  不可用时自动回退}：\passthrough{\lstinline!\_CANN\_READY!} 为 False
  时走 \passthrough{\lstinline!super().\_encode\_frame()!}（CPU
  libx264），无缝降级。
\end{itemize}

\textbf{\passthrough{\lstinline!CannH265Encoder!}} --- aiortc 兼容的
H.265 编码器。它复用
\passthrough{\lstinline!CannVenc!}，但创建通道时使用
\passthrough{\lstinline!ENTYPE\_H265\_MAIN = 0!}，输出 HEVC Annex-B
码流。与 H.264 路径不同，H.265 路径不继承 aiortc 的 H.264 RTP
封装，也不提供 CPU fallback；CANN 初始化或 VENC 创建失败应视为 H.265
模式不可用。

\subsubsection{\texorpdfstring{\texttt{hevc.py} --- H.265 RTP
分包}{hevc.py --- H.265 RTP 分包}}\label{src-book-chapter5-h152}

H.265 不能复用 H.264 的 RTP
分包格式。\passthrough{\lstinline!webrtc\_app/hevc.py!} 单独实现 HEVC
相关逻辑：

\begin{itemize}
\tightlist
\item
  \passthrough{\lstinline!split\_annexb()!}：按 Annex-B 起始码切分 HEVC
  NAL 单元
\item
  \passthrough{\lstinline!hevc\_nal\_type()!}：从 HEVC 两字节 NAL header
  中提取 NAL type
\item
  \passthrough{\lstinline!packetize\_hevc()!}：小 NAL 直接作为 single
  NAL packet，大 NAL 按 RFC 7798 封装为 Fragmentation Unit
\item
  \passthrough{\lstinline!has\_hevc\_keyframe\_markers()!}：检查
  VPS/SPS/PPS/IDR 等关键 NAL，用于验证 VENC H.265 输出是否像合法 HEVC
  码流
\end{itemize}

\subsubsection{\texorpdfstring{\texttt{dvpp\_jpegd.py} --- DVPP JPEGD
硬件解码器}{dvpp\_jpegd.py --- DVPP JPEGD 硬件解码器}}\label{src-book-chapter5-h153}

封装了 JPEGD 的完整生命周期：DVPP 通道创建 -\textgreater{}
JPEG-\textgreater NV12 解码 -\textgreater{} 输出缓冲区管理。关键设计：

\begin{itemize}
\tightlist
\item
  \textbf{按需分配}：首次解码时通过
  \passthrough{\lstinline!dvpp\_jpeg\_get\_image\_info!}
  获取宽高，\passthrough{\lstinline!dvpp\_jpeg\_predict\_dec\_size!}
  预测输出大小后分配设备缓冲区。后续帧复用已分配的缓冲区，避免每帧
  malloc。
\item
  \textbf{stride 对齐的 NV12 输出}：JPEGD 输出的 NV12 已按 16
  宽度对齐，此 stride 布局与 VENC 的
  \passthrough{\lstinline!pre\_padded=True!} 路径完全匹配。从 JPEGD 到
  VENC，NV12 数据无需 CPU 做任何重排。
\item
  \textbf{线程安全}：\passthrough{\lstinline!decode()!} 入口显式
  \passthrough{\lstinline!set\_context(ctx)!}，因为此方法在线程池的
  executor 线程中被调用。
\end{itemize}

\subsubsection{\texorpdfstring{\texttt{v4l2\_raw.py} --- 高性能 V4L2
采集}{v4l2\_raw.py --- 高性能 V4L2 采集}}\label{src-book-chapter5-h154}

直接在 Python 中通过 \passthrough{\lstinline!fcntl.ioctl!} +
\passthrough{\lstinline!mmap!} 操作 V4L2 设备，绕过 PyAV 的封装层。相比
PyAV 路径（1080p 约 15fps），直接 ioctl 路径可达到摄像头原生帧率（1080p
约 24fps）。两套后端通过相同的 \passthrough{\lstinline!read(timeout)!}
接口互换，上层代码无需感知。

\begin{quote}
\passthrough{\lstinline!v4l2\_raw.py!} 中的
\passthrough{\lstinline!v4l2\_buffer!} 结构体布局（88 字节）是针对
aarch64 Linux 的硬编码值。在 x86-64 机器上此模块不可用，自动降级到
PyAV。
\end{quote}

\subsection{关键结论}\label{src-book-chapter5-h157}

\begin{itemize}
\tightlist
\item
  \textbf{DVPP 模块不能孤立优化}------只用 VENC 而保留 CPU JPEG
  解码，链路仍会卡在 CPU 解码阶段。DVPP 的收益需要全链路协同才能兑现
\item
  \textbf{JPEGD + VENC 是 1080p 实时推流的关键组合}------纯软件路径约
  \passthrough{\lstinline!15 fps!}，全硬件 H.264 管道可以稳定到
  \passthrough{\lstinline!60 fps!}
\item
  \textbf{NV12 stride 对齐的零拷贝交付}------JPEGD 输出的 stride 对齐
  NV12 直接匹配 VENC \passthrough{\lstinline!pre\_padded!}
  输入要求，中间不经过任何 CPU 数据重排
\item
  \textbf{H.264 与 H.265 的工程取舍不同}------H.264 是当前最稳的 1080p60
  WebRTC 路径；H.265 只走 CANN VENC，依赖浏览器暴露
  \passthrough{\lstinline!video/H265!} WebRTC 能力，且本次 311
  实测中有偶发掉帧
\item
  \textbf{码率在建连时确定}------页面目标码率会影响本次 VENC
  通道创建，当前不支持在线热调
\end{itemize}

\subsection{常见问题}\label{src-book-chapter5-h160}

\textbf{Q: 为什么 \passthrough{\lstinline!acl.mdl.execute!} 报错
``Memory Check Failed''?} A: 检查
\passthrough{\lstinline!acl.mdl.get\_input\_size\_by\_index!}
获取的大小是否与 \passthrough{\lstinline!acl.rt.malloc!}
的大小严格一致。

\textbf{Q: DVPP 解码后的图像显示异常？} A: DVPP 输出有宽/高对齐要求（如
128×16 对齐）。读取数据时需要根据 \passthrough{\lstinline!stride!} 跳过
Padding 数据，而不能简单按 \passthrough{\lstinline!width * height!}
读取。

\textbf{Q:
\passthrough{\lstinline!libascendcl.so: cannot open shared object file!}?}
A: 确认 \passthrough{\lstinline!LD\_LIBRARY\_PATH!} 包含
\passthrough{\lstinline!/usr/local/Ascend/ascend-toolkit/latest/aarch64-linux/lib64:/usr/local/Ascend/driver/lib64!}。

\textbf{Q: \passthrough{\lstinline!No module named 'acl'!}?} A: 确认
\passthrough{\lstinline!PYTHONPATH!} 包含
\passthrough{\lstinline!/usr/local/Ascend/ascend-toolkit/latest/python/site-packages!}。

\textbf{Q: VENC 创建通道返回 507018?} A: 常见原因：(1)
\passthrough{\lstinline!max\_bit\_rate!} 单位是 \textbf{kbps} 而非
bps（2000 而非 2000000）；(2)
\passthrough{\lstinline!key\_frame\_interval!}（GOP）为 0，合法范围
\passthrough{\lstinline![1, 65536]!}。

\textbf{Q: VDEC 解码结果为空帧?} A: 检查回调中的
\passthrough{\lstinline!ret\_code!}------非 0
表示解码失败。常见原因：(1) 输入码流不是 Annex-B 格式（缺
\passthrough{\lstinline!0x00000001!} 起始码）；(2) 首帧缺少 SPS + PPS +
IDR；(3) \passthrough{\lstinline!entype!} 与输入码流的编码格式不匹配。

\subsection{使用约束}\label{src-book-chapter5-h161}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Context 线程安全}：一个 Context
  可以在多个线程中使用，但需用户保证并发安全。推荐一线程一 Context。
\item
  \textbf{Stream 约束}：Stream
  上的任务按顺序执行，但异步接口下发后需显式
  \passthrough{\lstinline!synchronize!} 才能确保数据就绪。
\item
  \textbf{内存对齐}：DVPP 对内存地址和图片尺寸有严格对齐要求（宽对齐到
  16，高对齐到 2）。
\item
  \textbf{通道数量有限}：Ascend 310B4 的 VENC/VDEC 硬件实例通常每种只有
  1-2 个。创建通道前确保之前的通道已销毁。
\end{enumerate}
